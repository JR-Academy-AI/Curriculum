考点地图：Domain 3 为什么最容易失分

Domain 3（Claude Code Configuration & Workflows）在官方 blueprint 里占 20%，仅次于 Agentic Architecture 的 27%，和 Prompt Engineering 并列第二（两者都是 20%）。它失分率高的原因很具体：网上大量二手教程把配置层级讲成"更具体的覆盖更宽的"，而官方文档明确否认这套优先级——你如果凭直觉答，会成片踩坑。

这个 domain 的官方描述覆盖五块，按考试出现频率排：

  • CLAUDE.md 层级与 .claude/rules/ — 三级作用域、拼接 vs 覆盖、path-scoped 规则。最高频。
  • settings.json 与权限模式 — 谁是硬强制、permission mode 有哪几个值。
  • hooks — 触发时机、exit code 语义（exit 2 才阻断，exit 1 不阻断，几乎必考一题）。
  • slash commands / skills — project vs personal 作用域（跨版本稳定的核心考点）、frontmatter；新版 docs 已把两者合并，但考试可能锁在合并前的快照。
  • subagents 与 MCP 接入 — 独立 context window、claude mcp add 的三种 transport 和三种 scope。

一句话抓总纲：CLAUDE.md 是"引导"，settings.json 和 hooks 是"强制"。 分不清这两层，Domain 3 至少丢一半分。

第一层：CLAUDE.md 层级 vs settings.json（到底谁说了算）

CLAUDE.md 的四个作用域是"拼接"，不是"覆盖"

CLAUDE.md 按作用域从宽到窄有四处，官方给的精确路径是：

  • Managed policy（组织级，IT 下发）：macOS /Library/Application Support/ClaudeCode/CLAUDE.md、Linux/WSL /etc/claude-code/CLAUDE.md
  • User（个人，跨所有项目）：~/.claude/CLAUDE.md，不进 git
  • Project（团队共享，随 repo）：./CLAUDE.md 或 ./.claude/CLAUDE.md，两个路径都合法
  • Local（个人项目偏好）：./CLAUDE.local.md，按惯例进 .gitignore

这里是最大的考点陷阱。官方原文："All discovered files are concatenated into context rather than overriding each other." 所有文件是拼接进同一个 context，谁都不覆盖谁。加载顺序是从文件系统根往工作目录方向走（宽 scope 先、窄 scope 后），同目录内 CLAUDE.local.md 接在 CLAUDE.md 后面。但"读得晚"不等于"优先级高"——文档说得很直白："if two rules contradict each other, Claude may pick one arbitrarily." 冲突时是随机挑一个，没有胜负规则。

再往深一层：CLAUDE.md 是以 user message 形式投喂给模型的，不进 system prompt，官方原话 "there's no guarantee of strict compliance"。所以它天生就是软约束。

典型考场景（原创版）：匠人做双语客服机器人，Aurora 的机器（Claude）总是只回英文，其他人正常双语。根因几乎永远是——"必须中英双语"这条规则被写进了她的 ~/.claude/CLAUDE.md（user-level，不进 git），队友 clone repo 根本拿不到。修法：把规则从 user-level 挪到项目 ./CLAUDE.md。

要"每次都生效"的硬规则，放 settings.json 或 hook

官方给了一句判据式的原话："Settings rules are enforced by the client regardless of what Claude decides to do. CLAUDE.md instructions shape Claude's behavior but are not a hard enforcement layer." settings 由客户端强制，跟模型怎么想无关；CLAUDE.md 只塑造行为。

settings.json 的作用域有严格优先级（这点和 CLAUDE.md 相反），从高到低：managed（企业托管）> command line > local（.claude/settings.local.json）> project（.claude/settings.json）> user（~/.claude/settings.json）。权限相关字段在 permissions 对象下：allow / deny / ask / defaultMode / additionalDirectories。注意一个细节：优先级链管的是普通设置，而权限规则是跨作用域合并（merge）的，不是简单覆盖——所以某一层加了 deny，别的层删不掉。

要 100% 挡住 Claude 读微信 key，正确姿势是往 permissions.deny 加一行 Read(./.env)，而不是在 CLAUDE.md 写"禁止读 .env"（后者是引导，会被违反）。

defaultMode 的四个合法值要背下来：default（标准，该问就问）、acceptEdits（自动批准文件编辑）、plan（先出计划不动手）、bypassPermissions（完全跳过权限检查）。

还有两个易混工具：/memory 命令只列出当前 session 已加载哪些 CLAUDE.md / rules 文件，是诊断用的，不触发加载、也不强制执行。@path import（如 @docs/git-instructions.md）能把 CLAUDE.md 拆成多个文件，但它是 launch 时原地 inline 加载，拆文件并不省 context——想省 token 要用下面的 .claude/rules/。

第二层：hooks / skills / subagents / MCP（强制、复用、隔离、接入）

hooks —— 唯一的确定性强制层，exit 2 才阻断

hook 是绑在生命周期事件上的 shell 命令，客户端在固定时机执行，跟模型的"意愿"无关。要考的事件名：PreToolUse（工具调用前）、PostToolUse（工具成功后）、UserPromptSubmit（你提交 prompt、Claude 处理前）、SessionStart / SessionEnd、Stop（Claude 回答完）、SubagentStop、PreCompact 等。

最爱考的是 exit code 语义，官方讲得非常死：

  • exit 0：成功。Claude Code 解析 stdout 里的 JSON 输出字段（JSON 只在 exit 0 时被处理）。
  • exit 2：阻断错误。忽略 stdout，把 stderr 当错误信息回传给 Claude。对 PreToolUse 就是阻断这次工具调用，对 UserPromptSubmit 就是拒绝这个 prompt。
  • 其它非零（含 exit 1）：非阻断错误。官方明确警告 "only exit code 2 blocks the action... treats exit code 1 as a non-blocking error and proceeds with the action"——你写 exit 1 想拦命令，命令照跑。要拦就必须 exit 2。

另一条等效阻断路径：PreToolUse 用 exit 0 + 输出 JSON permissionDecision: "deny"，也能确定性拦截并带上理由。想给"每次 commit 前必跑 lint""禁止 rm -rf"这种必须发生在某个时点的规则上强制，答案永远是 hook，不是 CLAUDE.md。

slash commands 与 skills：作用域是硬考点，"合没合并"看版本

官方新版文档原话 "Custom commands have been merged into skills"：.claude/commands/deploy.md 和 .claude/skills/deploy/SKILL.md 都创建同一个 /deploy，旧的 .claude/commands/ 文件继续能用，同名时 skill 形态优先。skill 比旧 command 多三样——SKILL.md 旁的 supporting-files 目录、Claude 按 description 自动发现调用、disable-model-invocation 等 frontmatter 开关。

⚠️ 但"已合并"是版本敏感的断言，别拿它去赌单选。 CCAR-F 通常锁定某个 docs 快照，如果考试所依据的版本里 commands 和 skills 还是两套并列机制，你按"已合并、skill 优先"去答反而可能踩坑。跨版本稳定、也是这个考点真正要考的，是下面的作用域规则——它不受"合没合并"影响。

两级作用域，新旧版本一致：project（.claude/skills/ 或旧的 .claude/commands/，进 git 全队 clone 即得）vs personal（~/.claude/skills/ 或 ~/.claude/commands/，个人机器独占、不进 git）。要"全队 clone 就能用同一个 /deploy"，无论做成 skill 还是 command，都必须放项目级并提交进 git；放 ~/.claude/ 队友 clone 拿不到。场景题落点在这儿，不在"哪种形态更 canonical"。

常考 frontmatter 字段（真实字段名）：description（Claude 判断何时自动调）、allowed-tools（此 skill 活跃时免权限提示的工具，注意它不是"限制工具集"，只是预批准免问）、disallowed-tools（从可用池里移除）、argument-hint、disable-model-invocation: true（只允许用户显式 /name 调，禁止模型自动触发）、context: fork（在 forked subagent 里跑，verbose 输出不污染主对话）。内容里用 $ARGUMENTS 或 $1 接收参数。

什么该做 skill、什么该进 CLAUDE.md？skill = 按需的任务型 workflow（body 只在调用时加载，长参考几乎不占 context）；CLAUDE.md = 每 session 常驻的通用事实。 任务流程塞进 CLAUDE.md，或把常驻标准做成 skill，都是反模式。

path-scoped rules —— 跨目录文件类型约定的正解

.claude/rules/ 下每个 .md 用 YAML frontmatter 的 paths glob，只在 Claude 读到匹配文件时才进 context。它专治一种 root CLAUDE.md 和 directory-level 都搞不定的场景：一种文件类型散落在几十个目录里。比如 .test.ts 分布在 40+ 功能目录，用 directory-level CLAUDE.md 要放 40+ 份拷贝、改一条约定改 40+ 处必然 drift；用 root CLAUDE.md 又会在你写 React 组件时也把测试规则烧进 context。正解是一个文件：

---
paths:
  - "**/*.test.ts"
---
# 测试约定
- 每个测试覆盖 happy path + 边界 + 错误路径

无 paths 的 rules 文件则无条件加载，优先级和 .claude/CLAUDE.md 相同。

subagents —— 用独立 context window 隔离脏活

subagent 是跑在独立 context window里的专用 agent，自带 system prompt、指定工具集和独立权限，官方定位 "runs in its own context window... returns only the summary"。用途是：一个副线任务会往主对话灌一堆 grep 结果 / 日志 / 文件内容，让 subagent 在它自己的 context 里干、只回传结论。文件放 .claude/agents/（project）或 ~/.claude/agents/（user），是 Markdown + YAML frontmatter，必填字段只有 name 和 description，可选 tools、model。Claude 靠 description 决定何时委派——所以 description 要写清"什么时候用我"。想让探索走更便宜的模型，就给它 model: haiku。

MCP —— 把外部工具接进 Claude Code

接一个 MCP server 用 claude mcp add。三种 transport：http（远程，官方推荐）、sse（已 deprecated）、stdio（本地进程）。远程：claude mcp add --transport http notion https://mcp.notion.com/mcp；本地 stdio 用 -- 分隔 Claude 的选项和真正要跑的命令：claude mcp add --transport stdio myserver -- npx server。

三种 scope 决定共享范围，也和前面的模式一致：local（默认，存 ~/.claude.json，只有你自己、只在该项目）、project（--scope project，写进 repo 根的 .mcp.json，随 git 分发全队共享，队友首次需批准）、user（--scope user，你的所有项目）。团队要共用一个 Notion server，就得用 --scope project 让它进 .mcp.json。

SCENARIO：给匠人团队配一套可靠的 AI 工作流

把上面的机制串成一个真实决策。场景：匠人在做"留学生求职工具"这个 monorepo，团队五个人共享一套 Claude Code 配置。需求逐条落到正确的机制上——这正是 Domain 3 场景题的考法。

  • "永远不能提交 .env、不能读客户 PII 目录" → 这是硬红线，必须客户端强制。用 settings.json 的 permissions.deny（如 Read(./secrets/**)）或 PreToolUse hook。不要只写 CLAUDE.md——它是软约束会被违反。
  • "每次改代码后必须自动跑 prettier" → 必须发生在固定时点 → PostToolUse hook。
  • "全队 clone 后就能用同一个 /deploy" → project skill .claude/skills/deploy/SKILL.md，提交进 git。放 ~/.claude/ 只有自己有。
  • "测试文件散在 30+ 目录，测试约定只在编辑测试时加载" → .claude/rules/testing.md 加 paths: ["**/*.test.ts"]。不用 directory-level（会 drift），不用 root CLAUDE.md（烧 token）。
  • "排查一个跨 20 文件的 bug，别让 grep/日志塞满主对话" → subagent 在独立 context 里定位、回传 summary。
  • "团队共用 Notion 知识库当数据源" → claude mcp add --transport http notion <url> --scope project，进 .mcp.json 随 repo 分发。
  • "项目的整体架构、命名规范、AU 本地化（GST、ABN、财年 7 月起）" → 这些是每 session 都要的常驻事实 → 项目 ./CLAUDE.md。

决策口诀：常驻事实 → CLAUDE.md；跨目录文件类型约定 → path rules；按需任务流程 → skill；必须发生在某时点或必须硬拦 → hook / settings；隔离脏活 → subagent；接外部系统 → MCP。

自测 5 题

第 1 题

匠人双语客服机器人 repo 的安全要求：Claude 永远不能读 .env（里面有微信 API key）。你在项目 CLAUDE.md 写了"禁止读取 .env"，但 Claude 偶尔还是打开了它。要真正 100% 挡住，最靠谱的做法是？

  • A. 把禁令改写得更具体、加粗、放到 CLAUDE.md 最顶部
  • B. 在 .claude/settings.json 的 permissions.deny 加一条 Read(./.env)
  • C. 把禁令搬到 ~/.claude/CLAUDE.md，因为 user-level 优先级最高
  • D. 运行 /memory 强制重新加载规则

正确答案：B

  • A 错：CLAUDE.md 以 user message 投喂，官方明说 "no guarantee of strict compliance"，措辞再狠也是引导不是强制。这个干扰项诱人在于"更用力写规则"是很多人的第一直觉。
  • B 对：permissions.deny 由客户端强制执行，"enforced by the client regardless of what Claude decides"。这是硬拦截层。
  • C 错：user-level 并不覆盖 project-level——文档明确是 concatenate 不 override；而且 ~/.claude 不进 git，队友那台机器没有这条规则。"优先级最高"本身就是被官方否认的误解。
  • D 错：/memory 只列出已加载的文件，既不触发加载也不做强制。它是诊断工具，被误当成"刷新配置"的按钮。

第 2 题

留学生求职工具 monorepo 里，.test.ts 测试文件散落在 40+ 个功能目录。团队想让"测试必须覆盖 happy path + 边界"这条约定只在编辑测试文件时加载，写 React 组件时别占 context。怎么配最对？

  • A. 在 40+ 个目录各放一份 directory-level CLAUDE.md
  • B. 写进 repo 根 CLAUDE.md，让它全局生效
  • C. 做成一个 skill，让 Claude always-on 自动调它
  • D. 在 .claude/rules/testing.md 用 paths: ["**/*.test.ts"] frontmatter

正确答案：D

  • A 错：40+ 份拷贝，改一条约定要改 40+ 处，必然 drift。看着"就近生效"很合理，实际是维护灾难。
  • B 错：root CLAUDE.md 每个 session 都全量加载，写 React 时测试规则也在烧 token，正好违背了"只在编辑测试时加载"。
  • C 错：skill 是按需任务型（调用时才加载），不是"随文件类型自动常驻的背景约定"；把它说成 always-on 本身就误解了 skill。
  • D 对：path-scoped rule 只在 Claude 读到匹配 glob 的文件时进 context，正是为"跨目录文件类型约定 + token 效率"设计的。

第 3 题

你写了个 PreToolUse hook 拦截 rm -rf：脚本检测到危险命令时往 stderr 打了原因并 exit 1。但 Claude 照样把命令跑了。为什么？

  • A. 只有 exit 2 才阻断动作；exit 1 被当成非阻断错误，动作照常继续
  • B. PreToolUse 不能拦 Bash，只能拦 Edit 类工具
  • C. hook 必须先加进 settings.json 的 allow 列表才会生效
  • D. stderr 不会回传给 Claude，必须改用 stdout

正确答案：A

  • A 对：官方警告得很死，"only exit code 2 blocks the action... treats exit code 1 as a non-blocking error and proceeds"。exit 1 是 Unix 惯用失败码，正因如此最容易顺手写错。
  • B 错：PreToolUse 对任意工具（含 Bash）都能阻断，命中就拦。
  • C 错：hook 不进 permissions.allow，两套机制不搭界。
  • D 错：恰好反了——exit 2 时 stderr 正是回传给 Claude 的错误信息通道。

第 4 题

你在一个大 repo 里让 Claude 排查 bug，需要先 grep 几十个文件、翻一堆日志才能定位，但你不想让这些中间输出塞满主对话 context。最合适的做法是？

  • A. 把相关日志都贴进 CLAUDE.md，让 Claude 直接读
  • B. 开 bypassPermissions 模式，让它跑快点少产生输出
  • C. 用一个 subagent 做定位，它在独立 context window 里跑、只回传 summary
  • D. 每读完一个文件就 /compact 一次，随时压缩

正确答案：C

  • A 错：CLAUDE.md 是放常驻指令的，不是临时日志缓冲；而且它每 session 全量加载，塞日志纯属浪费 context。
  • B 错：bypassPermissions 只是跳过权限确认，和 context 占用完全无关。这个干扰项蹭"加速"的直觉。
  • C 对：subagent "runs in its own context window... returns only the summary"，正是为隔离 verbose 探索、保持主对话干净而设计。
  • D 错：频繁 compact 有信息损耗且开销大，也不解决"探索输出污染主线程"这个根因。

第 5 题

匠人团队想让所有人 clone repo 后就能用同一个 /deploy 命令，还要接上团队共用的 Notion MCP server。哪组配置对？

  • A. /deploy 放 ~/.claude/commands/；Notion 用 claude mcp add --scope local
  • B. /deploy 放 .claude/skills/deploy/SKILL.md 并提交进 git；Notion 用 claude mcp add --transport http notion <url> --scope project（写进 .mcp.json）
  • C. /deploy 放 .claude/commands/，但 MCP server 只能每人手动 mcp add，没法团队共享
  • D. 把 /deploy 流程写进 CLAUDE.md 当一段说明；Notion 配到 ~/.claude.json

正确答案：B

  • A 错：~/.claude/ 是个人路径不进 git，队友 clone 拿不到；MCP 的 local scope 存 ~/.claude.json 同样只有你自己有。两处都不共享。
  • B 对：project skill 进 git 全队共享；MCP --scope project 写进 repo 根的 .mcp.json 随 git 分发（队友首次会看到待批准）。两者都是团队共享的正解。关键判据是"进 git 的项目级"——放 .claude/commands/deploy.md 并提交同样能共享，不取决于它算 skill 还是 command，所以这题不押"合没合并"。
  • C 错：前半对（.claude/commands/ 能共享），但"MCP 没法团队共享"是错的——project scope 就是为共享设计的。半对最诱人。
  • D 错：把任务型流程塞 CLAUDE.md 违反"任务 workflow 用 skill"的原则；~/.claude.json 是本地私有，团队看不到。
