### 0.1 为什么拆（v0.4 → v1.0）

v0.3/v0.4 的双结构版在做 deck 时暴露了三个结构性问题：

1. **两侧无法对称。** Team 侧天然比 Subagent 侧多一层（charter、成员通信、对抗设计、外部验收），deck 做出来 Team 侧 6 页 vs Subagent 侧 4 页——**视觉上暗示 Team 更重要，而本节的核心判断恰恰相反**（Team 的门槛应该更高）。
2. **120 分钟装不下两次实验 + 两套开课门槛。** Lab A 13 分钟、Lab B 18 分钟已经占掉四分之一，Agent Team 还要额外的能力预检（实验开关、显示模式、权限预批）。挤压的结果是过度分派红灯从动手实验降级成 5 分钟纸面判断——**而那正好是本节最需要的痛感**。
3. **判断线被迫前置。** 双结构版必须在两个 Lab 之前就把「两问决策树」讲完，尺子先于撞墙——跟 L4/L5/L6 一贯的「先撞墙，再给尺子」反过来了。

拆开之后三个问题同时消失：本节只有一条线，红灯回到动手，判断线回到两次实验之后。

## 1. 课程定位

第六节结束时，你已经是一个能驾驭单个 Agent 的人了：会写任务交付单、会盯打断信号、知道它说「完成了」不算完成。

但有一类任务，无论你交得多好，**一个 Agent 天生跑不好**：

> 「这个 bug 到底是哪个模块引起的？」——它得翻 50 个文件、试七八个假设，才能下一个结论。
>
> 等它翻到第 40 个文件的时候，你的 context 里已经堆满了 39 份「看过了不是这里」的垃圾。而那 39 份垃圾，会一路影响它后面每一轮的判断——这正是 L6 讲的 context 稀释和错误累积。

问题不在你交得不好，在**结构**：你把「到处翻」和「下结论」塞进了同一个 context。

第七节换结构：**让别人去翻，你只收结论。**

```text
L6：一个 Agent，一个 context
    所有脏活（读 50 个文件、试错、走弯路）
    全都堆在同一个 context 里 → 稀释 / 累积 / 被压缩
                  ↓
L7：一个主 Agent + 若干子 Agent
    每个子 Agent 有自己独立的 context
    脏活在它那边发生，回来的只有结论
                  ↓
    主 Agent 的 context 保持干净
    你的活也变了：从「自己干」→「分派 + 汇总」
                  ↓
    但天下没有白拿的：每一次分派都是一次冷启动
    所以核心不是「多派」，是「该派什么、不该派什么」
```

一句话定位：

> 第六节教你把一个 Agent 用好；第七节教你**不再把所有事塞进一个 Agent 的 context 里**。

系列主线在这里走第三步：

```text
L1–L5：往 context 里放对的东西
L6：  看懂 context 怎么被消耗、怎么坏
L7：  给 context 分家
L8：  让分出去的 context 互相通信（下一节）
```

## 2. Subagent 是什么

一张图讲完：

```text
【Hub-and-spoke（主从式）】

                    ┌→ 子 Agent A ─┐
你 ↔ 主 Agent / Hub ├→ 子 Agent B ─┼→ 只回结论 → Hub 汇总
                    └→ 子 Agent C ─┘

子 Agent 之间没有连线。
分工、补 context、冲突处理，全部经过 Hub。
```

**「子 Agent 之间没有连线」这一句要讲透**，因为它同时定义了 Subagent 的能力和边界：

- 能力：每个子 Agent 的噪音留在自己那边，主 context 不被污染
- 边界：A 的发现不会自动传给 B。要传，只能经过你或主 Agent

学员会问「那要是它们需要互相说话呢」——标准答复：**那是下节课的结构，今天先把这一种用透。**

## 3. 学员起点

学员上课前应有：

- **L6 的体感，尤其那五条跑偏机制**——本节的立论建立在「你已经亲眼见过 context 被拖垮」之上。没有这个体感，学员会觉得子 Agent 只是「多几个人干活」，抓不到重点。
- L6 的**任务交付单**（本节的分派 brief 就是它的变形：目标 / 边界 / 验证点）。
- L5 的 **Skill 心智**——角色化在延伸部分回收，不作为过关前提。
- 本机可运行一种支持委派的编码 Agent。
- 能打开老师提供的**统一兜底仓库**。课堂实验以统一仓库为主，个人项目放作业，避免项目体量和环境差异吞掉课堂时间。

### 3.1 课前能力预检（老师完成，学员不现场折腾配置）

上课当天用实际工具填一张卡，并在 P07 明示结果：

| 能力 | 当天实测结果 | 课堂影响 |
|---|---|---|
| 新 Agent 是否继承主对话历史 | 无 / 摘要 / fork / 其他 | brief 里要补多少 context |
| 是否自动读取项目规则文件 | 是 / 否 / 部分角色例外 | 哪些规则必须重写进 brief |
| 多个 Agent 使用同一工作副本还是隔离副本 | 同目录 / 独立副本 / 云端 | 能否安全并行写 |
| 子任务能否继续补充信息或恢复 | 能 / 不能 / 有条件 | 「一次交清」的严格程度 |
| 工具与权限是否继承 | 全部 / 部分 / 独立配置 | 任务能否真正执行与验证 |
| 是否允许嵌套委派 | 是 / 否 / 有层级限制 | 本节 demo 的最大深度 |
| 子 Agent 默认用哪一档模型 | 跟随主对话 / 固定 / 其他 | §6.9 的选档判断能不能落地 |

这张卡的作用不是教设置，而是建立一条职业习惯：**不要假设委派能力，先做 capability check。** 具体到当天工具怎么查，见 **§18**。

## 4. 学习目标

课程结束后，学员能够：

1. 说清**子 Agent 是什么**：不是「多一个人手」，是**多一个独立的 context**——这是全节最重要的一句话。
2. 说清最大的收益是 **context 隔离**：脏活在它的 context 里发生，主 context 只收结论，于是不会被稀释和污染（直接治 L6 诊断出的病）。
3. 说清**分派的三项代价**：冷启动、报告开销、以及**它看不见你和主 Agent 说过的话**。
4. 用一条**判断线**决定该不该派——并且这条判断线是自己在课上两次实验里测出来的，不是听来的。
5. 认出**过度分派**的样子：一个两三步就能做完的活被派出去，结果更慢、更贵、还绕远路。
6. 为子 Agent 写一份**能一次执行的六格 brief**，并说清每一格在治什么。
7. 知道**实际要打什么字**：三档调用方式的强制力差别，以及一句好指令为什么这样组词。
8. 守住三条铁律：**不假设继承 · 不重叠所有权 · 不拿自述验收**。
9. 把多路结果汇总成**覆盖 / 冲突 / 缺口矩阵**，并说清「汇总是你的活，不能一起外包」。
10. 说清**独立 context 的 verifier** 为什么比让 Agent 自我复查更可靠，以及「设计一个验证角色」和「随手派个人复查一下」的区别。
11. 按**判断密度**给不同角色选**模型档位和思考力度**两个旋钮，而不是按「这个角色重不重要」。

### 4.1 过关证据

不是「成功启动了三个 Agent」，而是学员离场前能提交：

- 一份 Lab A 的**分派包**：三路 brief + 三份完成回执 + 一张汇总矩阵。
- 一份红灯实验的**翻车记录**：派了什么小活、多花了多少时间、绕了什么远路。
- 一条**自己写的判断线**（该派 / 不该派各三条以上，从自己的两次实验里来）。
- 一句话说明：**我这次派对了 / 派错了，判据是什么。**

## 5. 非目标

本节明确不做：

- **不讲 Agent Team / 成员之间的通信 / 共享任务板**——那是 **L8** 的全部内容。今天所有子 Agent 都只跟中心说话。
- 不教 SDK / API，也不搭多 Agent 编排框架。
- 不教具体工具的配置项、模型参数或层级上限。**唯一例外**：如果某个能力在当天工具上是「默认关闭、不开就不存在」的，那个开关必须讲——它是这节课跑不跑得起来的前提，讲法只有一句「先确认它开着」，参数细节留 §18。
- 不把「同时启动很多 Agent」当学习成果；课堂并行上限固定为 **3 路**。
- 不让学员在课堂里并行改同一份真实代码；两次实验都以只读为主，写冲突由老师演示。
- 不把角色化 Agent 当本节主线。它与 L5 Skill 的关系放延伸，时间不够直接砍。
- 不声称所有工具都采用相同的 context 继承、文件共享或嵌套委派机制。

## 6. 核心教学决策

### 6.1 全节只回答一个问题

> **这件事值得开一个新的 context 吗？**

```text
值得分派，当：
隔离大量噪音 + 并行分支 + 独立证据视角
                  >
冷启动 + 报告开销 + 合并/冲突风险
```

任何内容如果不能帮助学员完成这次判断、写出分派 brief 或验收结果，就移出主课。

> v0.3 的「第二问：成员之间需不需要持续通信」整体移交 L8。本节的决策卡只有一问。

### 6.2 全节的立论就一句话：子 Agent = 多一个独立的 context

如果学员只带走一句话，必须是这句。它一旦立住，后面所有内容都是推论：

- 收益是推论（脏活不污染主 context）
- 代价是推论（独立 context 意味着要从零建，也意味着它看不见你的对话）
- 铁律是推论（一次交清 = 少几次冷启动；要它知道的必须写进去 = 它读不到你的对话）
- 冲突是推论（context 隔离了，**文件系统没隔离**）

所以这一页要占足时间，不能一句话带过。**讲不透这一句，后面全是零散技巧。**

### 6.3 两层门

第一层是**至少命中一项强收益**：

- **隔离收益**：会产生大量搜索结果、日志、失败尝试，而主线只需要结论。
- **并行收益**：有两个以上互不依赖的调查分支，可以同时推进。
- **独立视角**：需要一个没参与实现的 Agent 按明确判据找证据或反例。

第二层是**四个就绪条件全部通过**：

- [ ] 子任务边界能一句话说清。
- [ ] 必要 context 可以在开工前交齐或指向稳定文件。
- [ ] 产出有明确格式和验收判据。
- [ ] 它与其他任务没有未处理的写入重叠或前后依赖。

只有强收益、没有就绪条件，先拆任务；两层都过，也只代表**有资格进入成本比较**，不代表自动该派。

> 三项强收益里，**「独立视角」是唯一一个 1 个子 Agent 就能拿满的**——隔离和并行都要量。这条直接推出 §6.7 的最小配置。

### 6.4 两次实验：先撞墙，再给尺子

- **动手 A（正收益）**：宽调查任务，并行派三路。这是子 Agent 最经典的正收益场景——要读很多地方、彼此独立、只要结论。学员能亲眼看到它**更快而且主 context 干净**。
- **动手 B（负收益 · 本节红灯实验）**：故意派一个**两三步就能做完的小活**。学员会看到：冷启动 + 重新摸索 + 写报告 + 你再读报告，加起来比自己顺手做完慢得多。

**判断线放在两次实验之后讲**，从学员自己的数据里长出来——对标 L4 的 CI 红灯、L5 的 description 翻车、L6 的裸交跑偏。这个系列一贯的做法是**先撞墙，再给尺子**。

> **红灯必须是动手的，不能降级成纸面估算。** 估算出来的成本没有痛感，而本节最需要防的偏差恰恰是「学完什么都派」。v0.3 因为要塞两种结构把它压成了 5 分钟判断题，v1.0 恢复为 12 分钟实测。

过关标准不是「我成功派出去了」，是**你亲手测到了派错的代价，从此默认不派**。

### 6.5 课堂并行默认只读，写入并行只做演示

只读调查最能展示 context 隔离和并行，又不把课堂变成 Git 救火课。并行写代码必须同时满足：

- 所有权不重叠。
- 工作副本隔离或文件边界明确。
- 集成顺序与最终验收人明确。

老师用预录事故展示同文件覆盖，再用独立工作副本展示解法；不要求全班现场配置。

### 6.6 三条铁律

1. **不假设继承**：聊天里说过，不等于新 Agent 知道；工具自动加载，也不等于每种角色都加载。关键事实写进 brief 或落盘。
2. **不重叠所有权**：可以并行读同一个文件，不能让两个 Agent 同时拥有同一处写入或同一个最终决策。
3. **不拿自述验收**：不重做它的探索过程，但要用它之外的判据验收证据与成品。

「一次交清」和「派了别重做」保留为操作建议，但不讲成绝对规则：发现新证据时可以补充、改派或取消；目标是减少可预防的往返，不是为了守口号而让错误继续跑。

### 6.7 verifier 是最小、也是最值的那一个

「再找一个 Agent 看看」不是 verifier。合格 verifier 只拿到成品、需求和验收规则，输出红 / 绿 / 无法判断及证据；优先只读，不替实现者顺手改代码。

**最小配置阶梯：**

```text
1 个 → verifier              ← 最小，单位成本收益最高
2 个 → 调查员 + verifier      ← 最小的「有分工」结构
3 个 → 三路并行分支           ← 只有真有 ≥2 条互不依赖分支时才需要
```

为什么最小那个是 verifier 而不是调查员：三项强收益里**「独立视角」是唯一一个 1 个成员就能拿满的**，而且它不需要并行、不需要协调、不需要汇总矩阵——冷启动是唯一成本。

确定性测试仍优先于模型判断；高风险内容仍需要人类验收。独立 Agent 的价值是**补充不同视角，不是制造第二份自信**。

### 6.8 汇总是你的活，不能一起外包

学员最危险的终局是「我派了一堆 Agent，它们说都好了」。子 Agent 的报告是**它的视角**，而且你看不到它的过程。所以要教三件事：报告里该有什么、你审什么、以及「它没说的」往往才是关键（它跳过了什么、它假设了什么、它有没有真跑验证）。

汇总必须用矩阵，**不允许把多份报告直接拼起来**——拼接不会暴露冲突和缺口，矩阵才会。矩阵至少回答四个问题：

1. 多路任务覆盖了原问题的全部范围吗？
2. 两条结论是否互相矛盾？
3. 每条关键结论是否能追溯到文件、行号、命令输出或测试？
4. 哪些地方没有检查、无法验证或只是假设？

一句话收口：

> **分派改变的是信息怎样流动，不会转移最终验收责任。**

### 6.9 模型档与力度：按判断密度，不按重要性

同一个问题的两个问法差别很大：

- ❌「这个角色重不重要？」→ 重要的都给最强档 → 花冤枉钱
- ✅「这个角色是在**做判断**，还是在**做检索**？」

| 角色 | 干什么 | 密度 | 模型档 | 力度 |
|---|---|---|---|---|
| Verifier | 按判据找反例、给红绿 | **判断密集** | 最强档，不能省 | 高 |
| 实现型 | 改文件、跑验证 | **判断密集** | 最强档 | 偏高 |
| 调查员 | 读文件、搜日志、归纳复述 | 执行密集 | 中间档 | 低 |
| 格式转换 / 清单核对 | 机械劳动 | 执行密集 | 最快档 | 最低 |

**两个旋钮，同一条判断线。** 力度控制的是「它愿意花多少步」，不是它有多聪明——调低的实际表现是更少、更合并的工具调用。

两条配套判断：

- **先调「思考力度」，后调模型档。** 同一档降力度，成本降得快；反过来（先降档）容易把「档不够」和「力度不够」搞混。
- **最便宜的档往往 context 最小**，而子 Agent 最典型的用途恰恰是吞大量文件——**最便宜的档正好不适合最典型的用途**。这条要当场点破。

> deck 上只讲「最强档 / 中间档 / 最快档」和判断线，不出现模型名、价格、版本号——那些当天口播，细节见 §18。

### 6.10 异构：可以混，但只在这一种结构里

学员会问「能不能让别家的 Agent 当子 Agent」。可以，但要讲清机制和边界：

- 成员本身只能是同一家的会话；想混只有两条路：**把它包成一个工具**，或者**开一个只给 Bash 的包装层**去调别家的 CLI。
- **异构只能进 Subagent 结构。** 下节课的 Agent Team 做不到——成员资格靠共享任务板和信箱，外部进程收不到消息、不出现在任务板。这条先埋一句，L8 回收。
- **真该混的场景只有 verifier**：同一个模型的两个 context 共享同样的偏好和盲区；换个模型家族，独立性硬得多。这是「验证的价值来自独立」的最强版本。

## 7. 课堂最终产物

每位完成者应有：

- 一张**能力预检卡**（老师当天实测版）。
- 一张**分派判断卡**：该派 / 不该派 + 理由（§10）。
- 一份 Lab A 的**分派包**：三路 brief、三份完成回执、一张汇总矩阵。
- 一份红灯实验的**翻车记录**：计时对比 + 绕了什么远路。
- 一条**自己写的判断线**，从两次实验的数据里长出来。
- 一份可复用的 **brief 模板 + 完成回执模板 + verifier 模板**。

> ① 两次实验必须相邻（中间只隔休息），对比的冲击力全靠这个紧邻。

## 9. 各阶段教学细节

### 9.1 开场：把病摆出来

投一段 L6 的长任务记录：主 Agent 为找根因读了几十个文件、跑了多次失败命令，最后主 context 里充满「不是这里」。然后只问两句：

1. 哪些信息是下最终结论真正需要的？
2. 哪些信息只在探索当时有用，却永久占着主 context？

### 9.2 立论页（慢讲）

一句话：**它不是多一个人手，是多一个独立的 context。**

配一张对比图：

```text
【L6：一个 context】
你 → 主 Agent ──读 50 个文件──→ context 里堆了 39 份「不是这里」
                                  ↓ 这些垃圾持续影响它后面每一轮
                              结论质量下滑

【L7：分家】
你 → 主 Agent ──派──→ 子 Agent A（自己的 context：翻模块 1）→ 只回结论
                ├──→ 子 Agent B（自己的 context：翻模块 2）→ 只回结论
                └──→ 子 Agent C（自己的 context：翻模块 3）→ 只回结论
                     主 context 只多了三条结论，没多 39 份垃圾
```

### 9.3 快速分类：先暴露直觉，再给判断尺

给 6 张任务卡，让学员先投「直接做 / 派出去」：

1. 查一个函数定义在哪。
2. 从 20,000 行日志里找首次异常并给证据。
3. 分别排查前端、API、数据库三种登录失败假设。
4. 修改一个已知文件中的常量并运行已有测试。
5. 对已经完成的权限改动按 5 条安全判据做只读审查。
6. 把一份 200 行的 CSV 转成另一种格式。

讲完两层门之后再投一次。重点不在标准答案，而在学员能否说出**为什么需要一个新 context**。

### 9.4 六格 brief 必须在开工前回答

```markdown
## 1. 目标
一句话说清要回答或交付什么。

## 2. 范围与所有权
- 只读 / 可写：______
- 明确不要碰：______
- 你独占的文件或决策：______

## 3. 必要 context
- 项目规则：______
- 已知事实与已排除方向：______
- 必读文件：______

## 4. 产出合同
- 用 ______ 格式返回。
- 每条结论必须附 ______ 证据。
- 若未完成，返回 partial / blocked，不得装作 complete。

## 5. 完成判据
- ______（命令、测试、清单或红绿规则）

## 6. 停止与升级条件
- 遇到 ______ 就停止并报告，不要扩大范围。
```

讲法不是逐格念，而是拿一个坏 brief 现场补齐：

```text
坏：去看看登录为什么有时失败。

好：只读排查 src/api/auth/，判断 refresh token 轮换是否可能造成偶发 401。
返回：最多 3 条结论；每条附文件:行号和触发路径；列出未检查范围。
不要改文件，不要排查前端或数据库。若证据不足，返回「无法判断 + 缺什么证据」。
```

### 9.5 怎么派：三档调用 + 为什么这样组词

**三档，强制力递增：**

```text
① 自然语言点名   → 工具自己决定派不派。会漏。
② 明确指名调用   → 保证这个角色跑。课堂演示用这档。
③ 整个会话跑成它 → 主线程直接接管这个角色。
```

①和②的差别本身就是教学点：**「我说了」不等于「它照做了」。**

**逐句拆解好指令**（这一层比 prompt 本身值钱）：

| 这一句 | 治什么 |
|---|---|
| `只读排查 src/api/auth/` | 边界必须落在字面上——它读不到你和主 Agent 的对话 |
| `不要改文件，不要排查前端或数据库` | **否定句**显式收窄。Agent 默认倾向顺手多做 |
| `每条附 文件:行号 和触发路径` | 证据格式**前置**。不前置只能拿到自然语言总结，没法验收 |
| `列出未检查范围` | 逼出 not_checked。没这句你不知道它跳过了什么 |
| `若证据不足，返回「无法判断 + 缺什么证据」` | 给「不知道」一个**出口**。不给出口，它就编 |

最后一条最容易漏：**不给出口，等于逼它猜。**

### 9.6 动手 A：宽调查并行分派

统一问题示例：

> 「如果我们修改当前登录态的来源，哪些代码路径、配置和测试会连带受影响？」

三路只读边界：

- A：`src/api/` 与服务端鉴权路径。
- B：`src/components/`、路由守卫与客户端状态。
- C：配置、脚本、测试与文档中的隐式依赖。

统一返回格式：

```markdown
status: complete | partial | blocked

## findings
- 结论：______
  evidence: `path/to/file:line` + 一句解释
  impact: ______

## checked
- ______

## not_checked
- ______

## assumptions_or_risks
- ______
```

**计时终点**：不是最后一个 Agent 说「完成」，而是主 Agent 产出一张**证据可追溯、缺口已标记**的汇总表。

同时填一张观察卡：

```markdown
任务：______
启动 Agent 数：______
拿到可验收结果的时间：______
额外往返次数：______
证据覆盖：找到标准证据点 ____ / ____
主 context 是否被污染：是 / 否
主要协调成本：______
```

### 9.7 汇总矩阵

不允许把三份报告直接拼起来：

| 范围 | 关键结论 | 证据 | 冲突 / 缺口 | 主 Agent 决定 |
|---|---|---|---|---|
| API |  |  |  |  |
| Client |  |  |  |  |
| Config / Test |  |  |  |  |

最后一列是**你的活**：矩阵填满不等于收口，要有人对冲突和缺口做决定。

### 9.8 动手 B：红灯实验（12 分钟，真的跑）

给一个明确的微任务，例如：**定位 `MAX_RETRY` 这个常量定义在哪个文件。**

要求学员**真的派出去一次**，并用同一张观察卡计时。同时自己顺手做一遍作为对照。

预期结果：

| | 单 Agent | 派出去 |
|---|---|---|
| 动作 | 搜一次 → 看结果 | 写 brief → 冷启动 → 它重新摸项目 → 写回执 → 你读回执 |
| 时间 | 十几秒 | 数分钟 |

过关答案不是「派出去也能做」，而是：**它没有强收益（噪音量不够、没有并行分支、不需要独立视角），所以不该派。**

一句收口：**能派出去完成，不代表应该派出去。**

### 9.9 判断线（从两次数据里长出来）

让学员对着自己两张观察卡，各写三条：

```markdown
## 我会派，当：
1. ______
2. ______
3. ______

## 我不会派，当：
1. ______
2. ______
3. ______
```

然后补一条**工具默认倾向校准**：

- 有的工具**偏保守**——该派的时候不派，非要你推一把。
- 有的**过度热情**——一点小事也开一堆子 Agent。

教法不是「多派」或「少派」，而是：**掌握判断线，然后观察你手上这个工具偏哪边，往反方向校准。** 这个教法不会过期：工具换了、模型升级了，判断线还成立，学员只需重新观察一次默认倾向。老师上课当天按实际表现口头补充「今天这个工具偏哪边」。

### 9.10 Context 隔离不等于 workspace 隔离

用一张矩阵取代绝对说法：

| 层 | 应有的默认假设 | 开工前要确认什么 |
|---|---|---|
| 对话历史 | **不假设继承** | 是新 context、摘要注入还是 fork？ |
| 项目规则 | **不假设所有角色都加载** | 哪些规则文件会自动读？ |
| 工作副本 | **不假设共享，也不假设隔离** | 同目录、独立副本还是云端？ |
| 工具与权限 | **不假设一致** | 能读、能写、能跑哪些验证？ |

并行安全口诀：

1. **读可重叠，写要独占。**
2. **有依赖就排顺序，无依赖才并行。**
3. **谁合并谁验收，开工前指定。**

最坏的一种翻车：**context 隔离了，workspace 却在打架。**

### 9.11 完成回执

```markdown
status: complete | partial | blocked

## outcome
- 最终结论或交付物：______

## evidence
- 结论 → 文件 / 行号 / 命令输出 / 测试：______

## changes
- 修改过的文件：______（只读任务填 none）

## validation
- 实际运行：______
- 结果：pass / fail / not_run（原因）

## assumptions_and_gaps
- 假设：______
- 未检查：______
- 已知风险：______

## handoff
- 主 Agent 下一步需要决定或执行：______
```

课堂审一份反例：结论写得很顺，但没有出处、没有 `not_checked`、把未运行的测试写成「应该通过」。让学员把它退回到「可验收」为止。

### 9.12 不重做探索，但要独立验收

| 动作 | 是否应该 | 原因 |
|---|---|---|
| 主 Agent 再完整搜索一遍 | 通常不应该 | 等于付两次探索成本 |
| 主 Agent 打开关键证据、抽查路径 | 应该 | 验证结论可追溯 |
| 执行 brief 里的测试或验收命令 | 必须 | 判据来自 Agent 自述之外 |

Verifier 模板：

```markdown
你是只读 verifier。不要修改成品，也不要根据实现过程替作者辩护。

输入：成品 / diff / 需求 / 验收规则。

逐条输出：
- criterion: ______
- verdict: pass | fail | cannot_determine
- evidence: ______
- required_fix_or_missing_evidence: ______

只有所有必选 criterion 都 pass 才能给总体 green。
```

## 14. Exit ticket 与作业

### 14.1 Exit ticket（5 分钟，四题）

1. 用一句话说清子 Agent 是什么。（标准答案只有一个：多一个独立的 context）
2. 三项强收益里，哪一项 1 个子 Agent 就能拿满？为什么？
3. 你刚才那个红灯任务，为什么不该派？
4. 它说「完成了」，你还要做什么才算验收？

过关标准：四题至少三题正确，且第 1 题必须答对。

### 14.2 作业

1. 在自己的真实项目中找一个值得分派的任务，先填**分派判断卡**；不能先开 Agent 后补理由。
2. 提交每一路 brief、完成回执和汇总矩阵。
3. 至少执行一个来自 Agent 自述之外的**验收动作**，并附输出。
4. 再找一个**不值得**分派的微任务，实测一次并记录时间差。
5. 选做：把一个重复出现三次以上、职责稳定的任务角色化，并说明它和 L5 Skill 的差别。

提交包：分派判断卡 + 运行材料 + 验收证据 + 150 字复盘。

## 15. 延伸模块（不占 120 分钟主课）

### 15.1 角色化：接回 L5

| | Skill（L5） | Agent 角色（L7） |
|---|---|---|
| 沉淀的是 | 可复用的做事流程、知识与规范 | 特定职责、上下文边界、工具与权限 |
| 适合场景 | 同类工作反复需要同一套方法 | 同类任务反复需要独立执行或隔离 context |
| 判断线 | 重复、稳定、值得维护 | 重复、职责稳定、产出合同稳定 |

不是重复三次就一定要建 Agent；如果任务需要主对话里的完整 context，Skill 可能更合适。

### 15.2 并行写入进阶

另开 20–30 分钟加餐：任务分区 → 独立工作副本 → 各自验证 → 指定集成人 → 合并 → 全量验收。它是 Git / 工作区隔离训练，不应挤占本节「该不该派」的核心判断。

### 15.3 国内环境

**本节的判断框架是工具无关的，而且 Subagent 这一档国内工具普遍都有**——独立 context 的委派是主流 AI 编程工具的基础能力，叫法不同而已。学员真正会缺的是：

| 本节能力 | 国内工具普遍情况 | 拿不到时怎么办 |
|---|---|---|
| 独立 context 的委派 | **基本都有** | 正常做，只是 brief 要写得更满 |
| 各自独立工作副本 | 多数没有 | 退回人工分目录；课堂本来就只读 |
| 角色定义文件化复用 | 部分有 | 退回每次手写 brief |

> 相比之下 L8 的 Agent Team 国内基本拿不到——那一节的降级方案见 L8 蓝图。

## 16. 官方依据与数据纪律

### 16.1 稳定原理

- 独立 context 适合隔离大量搜索、日志和文件读取，只把摘要或结构化结果带回主线。
- Subagent 是集中协调结构：成员聚焦执行，结果回中心，由中心处理覆盖、冲突与汇总。
- Agent 数量增加会增加总 token / 计算成本、协调成本与结果合并风险；墙钟变快不等于总成本变低。
- 对话 context 与工作区隔离是两个维度，不能从「独立 context」推导出「文件一定隔离」或「文件一定共享」。
- 验证的价值来自**独立**，不来自「多一个人看过」。

### 16.2 产品事实只做「当天映射」

截至 2026-08-02，Claude Code 官方文档说明：subagent 在独立 context 中执行聚焦任务并回报主会话；非 fork subagent 通常不继承主对话历史，但会加载哪些项目规则、权限或 git 信息取决于角色与配置；worktree 是文件写入隔离手段。参考：

- [Create custom subagents](https://code.claude.com/docs/en/sub-agents)
- [Run agents in parallel](https://code.claude.com/docs/en/agents)

这些页面用来验证「为什么要做能力预检」，不用于在 deck 上背产品参数。若课堂改用其他工具，老师必须换成该工具的官方文档并重新实测。

### 16.3 数据纪律

- Deck 只保留跨工具成立的判断框架；具体按钮、模型倾向、并发上限、上下文继承方式放老师备注。
- **唯一例外是 P12**（怎么落盘）：给角色文件的存放路径和三档调用语法。理由是不知道文件放哪、不知道怎么触发，学员回去就落不了地——判断线再对也没用。路径和调用语法是稳定的结构事实；会变的（版本行为、参数细节、`/agents` 之类命令的语义变更）仍然只口播，不上 slide。该页底部必须标明「这是全课唯一一页出现具体路径和命令」。
- **模型选型只讲档位（最强 / 中间 / 最快）和判断线，不出现模型名、价格、版本号**——那些讲完就过期。
- 两次实验用来观察信息流和成本，不包装成模型跑分或普遍性能结论。
- 任何「更快」「更省」「更可靠」的结论都必须说明比较对象和指标。

## 18. 附录 A：Subagent 的设置与生成方法

> **这一节不上 deck。** 它是老师备课和学员课后自查用的操作材料，写在这里是为了让 §3.1 的能力预检卡、§12.1 的课前准备有确定答案可填。
>
> **口径与复核**：以下按 Claude Code 官方文档整理（2026-08-02 核对）。带版本号的条目说明该行为在哪个版本变过——**它们会继续变**。老师上课当天必须用手上那个版本重跑一遍，不要凭这份附录开课。换别的工具则整节作废。

### 18.1 四种生成方式

| 方式 | 存在哪 | 作用范围 | 什么时候用 |
|---|---|---|---|
| 让 Claude 写（推荐） | 你指定的目录 | 同下 | 日常。描述要什么 + 存哪里 |
| 手写文件 · 项目级 | `.claude/agents/` | 当前项目 | 要 commit 进仓库、全班共享同一份角色 |
| 手写文件 · 用户级 | `~/.claude/agents/` | 你所有项目 | 个人常驻角色（verifier 这类） |
| CLI 传 JSON | 不落盘 | 仅本次 session | **课堂统一发放**：一条命令全班拿到相同角色 |

同名优先级：组织托管设置 > CLI 传入 > 项目级 > 用户级 > 插件。两个目录都递归扫描；身份只由 frontmatter 的 `name` 决定，路径不影响调用。

⚠️ `/agents` 命令**从 v2.1.198 起不再是创建向导**，跑它只会提示去问 Claude 或直接编辑目录。网上不少教程还在教向导，那个已经没了。

### 18.2 文件格式

YAML frontmatter + Markdown 正文（正文就是这个角色的 system prompt）。只有 `name` 和 `description` 必填：

```markdown
---
name: readonly-verifier
description: 只读验收员。拿到成品和验收判据，逐条给红绿。实现完成后使用。
tools: Read, Grep, Glob
model: sonnet
---

你是只读 verifier。不要修改成品，也不要根据实现过程替作者辩护。
逐条输出 criterion / verdict / evidence / required_fix_or_missing_evidence。
只有所有必选 criterion 都 pass 才能给总体 green。
```

这份正文就是 §9.12 的 verifier 模板落盘后的样子——**§9.12 讲判断，这里讲它怎么变成一个可复用的文件**。§15.1「角色化接回 L5」要落地，落的就是这个文件。

教学要用到的字段：

| 字段 | 对应课上哪个概念 |
|---|---|
| `tools` / `disallowedTools` | brief 六格的「范围与所有权」——把只读约束变成工具层强制，而不是靠嘱咐 |
| `isolation` | 给它一份临时的独立工作副本，没产生改动会自动清理。§6.5 并行写的正解 |
| `permissionMode` | 它能不能真的执行和验证 |
| `model` | 默认 `inherit`（跟随主对话）—— 见 §18.5 |
| `maxTurns` | 兜底止损，对应「停止与升级条件」 |
| `skills` | 把某个 skill 全文预加载进它的 context |

热加载：改了定义文件几秒内生效，不用重启。**唯一例外**：`~/.claude/agents/` 这个目录如果在 session 启动前压根不存在，新建之后要重启一次才认。

### 18.3 三档调用

```text
① 自然语言点名："用 readonly-verifier 这个 subagent 看一下这次改动"
   → Claude 自己决定派不派。会漏。
② @ 提及：@agent-readonly-verifier
   → 保证这个角色跑。课堂演示用这档。
③ 整个 session 跑成它：命令行 --agent 参数，或项目设置里指定
   → 主线程直接接管这个角色的 system prompt / 工具限制 / 模型。
```

### 18.4 它启动时 context 里有什么

（§3.1 预检卡第一行的标准答案）

- **有**：自己的 system prompt + 环境信息、Claude 写的委派消息、**完整的 CLAUDE.md 层级**、git 状态快照、`skills` 字段预加载的内容。
- **没有**：你的对话历史、你已经调用过的 skill、Claude 已经读过的文件。
- **例外**：fork 形态的 subagent 继承完整对话——这就是预检卡「无 / 摘要 / fork / 其他」里 fork 那一项的实际含义。

所以铁律一「不假设继承」要讲得更准：**项目规则会自动到位，对话历史不会。** 你在聊天里排除掉的那三个方向，它一个都不知道——这正是六格 brief 第 3 格「已知事实与已排除方向」存在的理由。

### 18.5 它到底怎么跑（以及「会不会起两个」）

**执行链路：**

```text
主 Agent 决定派
   ↓
Claude 自己写一条委派消息        ← 不是你的原话，是它转述的
   ↓
新实例启动，context 是空的
   ↓
它跑自己的循环，工具调用全部写进它自己的 transcript
   ↓
只有最终那段文字回主对话
```

**transcript 独立落盘**，这是「独立 context」最硬的物证，也是课堂上最好的教具（可以当场 `ls` 给学员看）：

```text
~/.claude/projects/{项目}/{会话}/subagents/agent-{id}.jsonl
                                            └─ 一个子 Agent 一个文件
```

由此推出三条：

- **主对话被压缩，动不了它**——压根不在同一个文件里。
- **子 Agent 自己也会 auto-compact**，同一套逻辑，transcript 里能看到 `compact_boundary` 事件。
- **它的 context window 大小由它自己的模型决定**，不是父的。这就是 §18.5「最便宜的档 context 最小」为什么危险。

不传递的还有：主对话的输出风格、主对话的长期记忆。

#### 会不会起两个？会，而且比你想的容易

**① 每次 Agent 调用都是新实例——这是默认行为，不是 bug。**

官方原文：*Each subagent invocation creates a new instance with fresh context.*

你说「继续那个 code-reviewer 的活」，如果走的是一次新的 Agent 调用，**那就是第二个全新实例，前面的事一件都不知道**。想真的续上，必须走 `SendMessage`（按 agent ID 或名字），resume 会保留完整历史，包括之前所有工具调用和推理。

**② 内置 Explore / Plan 根本不能 resume。** 它们是一次性的，不返回 agent ID。想续只能重开 = 必然是第二个。要能续就用 `general-purpose` 或自定义角色。

**③ 同名再生成会撞车。** v2.1.199 起 `SendMessage` 会校验名字是否还指向同一个 agent——如果新 agent 抢了这个名字（比如后台 agent 重生成时复用），Claude Code **拒绝发送**而不是发错人。这条设计本身就证明了同名两个实例并存是真实会发生的。

> **对课程的意义**：这是「不假设继承」的第三个面——**不假设它还记得**。P03 立论说「多一个独立 context」，这里说的是「而且每次都是新的一个」。适合当 P09 的老师补充，不必上 slide。

**并发**：background subagent 是真并发；想让多个真的同时跑，要在**一条消息里发多个工具调用**。并发上限 20，会话累计 200。

### 18.6 模型与力度：五个技巧

1. **别让 `model` 字段空着。** 默认 `inherit` 跟随主对话——你主线程用最强档，它就跟着用最强档去做检索。不写 = 默认按主对话的价钱付。
2. **换档不炸缓存。** 主会话中途切模型，整个 prompt cache 全废（缓存按模型分）。想让一段活跑在便宜档上，唯一不付这个代价的办法就是**开一个 subagent 用那个档，主线程一动不动**。这是 subagent 被低估的第二个价值。
3. **先调力度，后调档。** 官方对 subagent 的建议是低思考力度。而且能调的旋钮只有两个——subagent 继承主对话的 extended thinking 配置，**没有 per-subagent 的 thinking 开关**（v2.1.198 起）。
4. **给搜索型角色设天花板。** 内置的 Explore subagent 就是这么做的：继承主对话模型但在 Claude API 上封顶，理由是「让它永远不会跑在比你已选的更贵的模型上」。你的 investigator 类角色照抄，写死档位别 inherit。
5. **统一压档用环境变量。** 解析优先级：环境变量 > 每次调用传的 model > frontmatter。课堂一条变量把全班压到同一档，不用改任何角色文件。

**力度（reasoning effort）怎么按角色选：**

力度控制的是**它愿意花多少步**，不是它有多聪明。调低的实际表现是：更少、更合并的工具调用，更短的前言，更简短的确认。

| 角色 | 力度 | 为什么 |
|---|---|---|
| 调查员 / 搜索 | **低** | 官方对 subagent 的默认建议就是低档。它的活是「找到并复述」，不需要反复权衡 |
| 实现型（写代码、跑验证） | **偏高** | 编码和 agentic 场景的推荐档，也是 Claude Code 自己的默认 |
| verifier | **高** | 判断密集；而且它要能说出 `cannot_determine`，那需要真的想过 |
| 格式转换 / 清单核对 | **最低** | 机械劳动 |

跟模型选档是同一条判断线（判断密集往高、执行密集往低），所以 deck 上用一张表两列讲完（P08）。

三条容易踩的：

- **低力度会「想当然」。** 工具调用变少的直接后果就是少查一次。所以给低档调查员的 brief 里，「每条结论附 文件:行号」那句更不能省——那是逼它真的去查的唯一手段。**低力度 + 松 brief = 它会编。**
- **新一代模型的低/中档常常超过上一代的最高档。** 从旧模型迁过来时沿用原来的力度通常是浪费，值得重新扫一遍。
- **力度高 ≠ 总成本高。** 长任务给高档，它前期规划得好、回合数少；低档可能来回试。要看的是**总回合数 × 单价**，不是单次力度。

**三个坑：**

- **最便宜的档 context 最小**，而 subagent 最典型的用途是吞大量文件——最便宜的档正好不适合最典型的用途。
- **组织 allowlist 会静默降级**：指定的模型不在允许列表里，Claude Code 跳过这个值改用继承的模型，**不报错**。
- **fork 不是省钱工具**：它继承完整上下文和工具池，省的是「重新解释一遍」，档位应跟主线程齐平。

### 18.7 课堂容量

默认值（2026-08-02）：每 session 累计 200 个、同时并发 20 个、嵌套默认 3 层——三个数都远大于课堂需要的 3 路。

> 这条要在 P07 明说，因为它正好是本节价值观的证据：**限制从来不是瓶颈，判断力才是。** 学员问「最多能开几个」，标准答复是「多到你不该问这个问题——该问的是这一路值不值得开」。

### 18.8 异构：混用别家的 Agent

成员本身只能是同一家的会话——角色定义里的 `model` 字段收不了别家的名字。想混只有两条路：

- **路 A：包成一个工具**，让主 Agent 当外部工具调用（MCP 那一类）。官方给的正路。
- **路 B：一个只给 Bash 的包装层**，开一个 subagent 工具只留 Bash，让它去命令行喊别家的 CLI。

路 B 的包装层长这样——**它不推理，只转发，所以用便宜档是对的；真正的模型选择在另一侧的命令行参数里**：

```markdown
---
name: <别家 CLI>-rescue
model: <便宜档>
tools: Bash
---
你是一个转发层。把请求转给 <别家 CLI>，原样返回它的输出。
```

**结构性结论**：异构**只能进 Subagent，进不了 Agent Team**——team 成员资格靠共享任务板和信箱，那是工具内部的东西，外部进程收不到消息也不出现在任务板。这条在 L8 回收。

**真该混的场景只有 verifier**：同一个模型的两个 context 共享同样的偏好和盲区；换个模型家族，独立性硬得多。
