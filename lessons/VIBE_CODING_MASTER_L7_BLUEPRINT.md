# Vibe Coding 大师课 · 第七节蓝图（草稿）

> 状态：DRAFT 0.1
> 主题：Agent Team —— 从一个 context 到一支队伍：分派、隔离、汇总
> 课型：~132 分钟动手工作坊
> 本文只定义课程，不包含 deck 实现。
> 承接第六节：L6 把 Agent 拆开了，你知道它没有记忆只有 context，也知道长任务会被 context 稀释 / 错误累积 / 压缩丢细节拖垮。L7 给出那个病的**结构性解法**——别把所有事塞进一个 context 里。

## 1. 课程定位

第六节结束时，你已经是一个能驾驭单个 Agent 的人了：会写任务交付单、会盯打断信号、知道它说"完成了"不算完成。

但有一类任务，无论你交得多好，**一个 Agent 天生跑不好**：

> "这个 bug 到底是哪个模块引起的？"——它得翻 50 个文件、试七八个假设，才能下一个结论。
>
> 等它翻到第 40 个文件的时候，你的 context 里已经堆满了 39 份"看过了不是这里"的垃圾。而那 39 份垃圾，会一路影响它后面每一轮的判断——这正是 L6 讲的 context 稀释和错误累积。

问题不在你交得不好，在**结构**：你把"到处翻"和"下结论"塞进了同一个 context。

第七节换结构：**让别人去翻，你只收结论。**

```text
L6：一个 Agent，一个 context
    所有脏活（读 50 个文件、试错、走弯路）
    全都堆在同一个 context 里 → 稀释 / 累积 / 被压缩
                  ↓
L7：一个主 Agent + 若干子 Agent
    每个子 Agent 有自己独立的 context
    脏活在它那边发生，回来的只有结论
                  ↓
    主 Agent 的 context 保持干净
    你的活也变了：从"自己干"→「分派 + 汇总」
                  ↓
    但天下没有白拿的：每一次分派都是一次冷启动
    所以核心不是"多派"，是「该派什么、不该派什么」
```

一句话定位：

> 第六节教你把一个 Agent 用好；第七节教你**不再把所有事塞进一个 Agent 的 context 里**——从指挥一个人，到带一支队伍。

> 系列主线在这里再走一步：L1–L5 是「往 context 里放对的东西」，L6 是「看懂 context 怎么被消耗」，L7 是「**给 context 分家**」。这三步合起来才是完整的 context 治理。

## 2. 学员起点

学员上课前应有：

- **L6 的体感，尤其那五条跑偏机制**——本节的立论建立在"你已经亲眼见过 context 被拖垮"之上。没有这个体感，学员会觉得子 agent 只是"多几个人干活"，抓不到重点。
- L6 的**任务交付单**（本节的分派指令就是它的变形：给子 agent 的 brief 同样要有目标 / 边界 / 验证点）。
- L5 的 **Skill 心智**——本节后半段要把子 agent 角色化，那和写 SKILL.md 是同一件事的另一个维度。
- 本机可运行 Claude Code（或 Cursor），有一个**自己的真实项目**，最好**代码量够大**（子 agent 的收益在小项目里看不出来）。
- 一个**"需要到处翻才能下结论"的真实问题**（某个 bug 的根因、某个功能到底散落在哪些地方、某个依赖被哪些地方用了……）当练习素材。

没有足够大的项目的学员用老师提供的**兜底仓库**（刻意做得够大、含一个跨模块的真实问题）。

## 3. 学习目标

课程结束后，学员能够：

1. 说清**子 Agent 是什么**：不是"多一个人手"，是**多一个独立的 context**——这是全节最重要的一句话。
2. 说清子 agent 最大的收益是 **context 隔离**：脏活在它的 context 里发生，主 context 只收结论，于是不会被稀释和污染（直接治 L6 诊断出的病）。
3. 说清**分派的三项代价**：冷启动（它要从零重建 context）、报告开销（它写一份、你再读一遍）、以及**它看不见你和主 agent 说过的话**。
4. 用一条**判断线**决定该不该派——并且这条判断线是自己在课上两次实验里测出来的，不是听来的。
5. 认出**过度分派**的样子：一个两三步就能做完的活被派出去，结果更慢、更贵、还绕远路。
6. 守住三条铁律：**一次交清**（别派出去→等→再补 brief）、**派了就认**（不重做它的活、不自己再推导一遍它的结论）、**要它知道的必须写进指令或落盘**。
7. 说清并行时**子 agent 之间共享什么、不共享什么**：共享文件系统，不共享对话历史——以及这个差别为什么会导致互相覆盖。
8. 用**隔离手段和写边界**让多个 agent 同时干活而不打架。
9. 把反复用的子 agent **角色化**定义下来，并说清它和 Skill 是什么关系（接 L5）。
10. 说清**独立 context 的 verifier** 为什么比让 agent 自我复查更可靠，以及"设计一个验证角色"和"随手派个人复查一下"的区别。
11. 认清**汇总是你的活**：子 agent 的报告不等于结论，你要审的是它没说的那部分。

## 4. 非目标

本节明确不做：

- **不教用 SDK / API 自己实现多 agent 编排框架**（工程课，不是这节）。本节讲的是"你怎么带这支队伍"。
- **不讲 MCP / Hooks**（能力扩展层，仍留后续）。
- **不追求搭一个复杂的多 agent 流水线**。本节只做"派得准一次 + 亲眼看一次派错"。
- **不讲模型内部**，也不引与具体版本绑定的分派行为参数（见 §14 数据纪律）。
- **不做"agent 越多越强"的展示**——本节的价值观恰恰相反：**默认不派，值得才派。**
- 不讲跨机器 / 跨团队的 agent 协作平台化（§15 待定项 3）。

## 5. 核心教学决策

### 5.1 全节的立论就一句话：子 agent = 多一个独立的 context
如果学员只带走一句话，必须是这句。它一旦立住，后面所有内容都是推论：

- 收益是推论（脏活不污染主 context）
- 代价是推论（独立 context 意味着要从零建，也意味着它看不见你的对话）
- 铁律是推论（一次交清 = 少几次冷启动；要它知道的必须写进去 = 它读不到你的对话）
- 冲突是推论（context 隔离了，**文件系统没隔离**）

所以这一页要占足时间，不能一句话带过。**讲不透这一句，后面全是零散技巧。**

### 5.2 把 L6 的病当作 L7 的立论前提
L6 学员亲手体验过 context 被拖垮。L7 开场就把那个体验接上来：

> 你上节课那个跑偏，不是你交得不好，是你把"到处翻"和"下结论"塞进了同一个 context。

这让 L7 从"又一个新功能"变成"上节课那个问题的解法"。**两节课必须咬合**，否则 L7 会被当成技巧集。

### 5.3 正收益 + 负收益两次实验，判断线让学员自己长出来
- **动手 A（正收益）**：宽调查任务，并行派几个。这是子 agent 最经典的正收益场景——要读很多地方、彼此独立、只要结论。学员能亲眼看到它**更快而且主 context 干净**。
- **动手 B（负收益 · 本节红灯实验）**：故意派一个**两三步就能做完的小活**。学员会看到：冷启动 + 重新摸索 + 写报告 + 你再读报告，加起来比自己顺手做完慢得多。

**判断线放在两次实验之后讲**，从学员自己的数据里长出来——对标 L5 的"该不该做成 Skill"、L6 的"该不该打断"。这个系列一贯的做法是**先撞墙，再给尺子**。

### 5.4 本节的红灯实验是「过度分派」
对标 L4 的 CI 红灯 / CORS 红灯、L5 的 description 翻车、L6 的裸交跑偏。

过关标准不是"我成功派出去了"，是**你亲手测到了派错的代价，从此默认不派**。这是本节最需要防的偏差——学员学完最容易犯的错就是"什么都派"。

### 5.5 诚实处理一个张力：不同工具对分派的默认倾向是相反的
这是本节必须讲、又必须讲得版本无关的一点：

- 有的模型/工具**偏保守**——该派的时候不派，非要你推一把。
- 有的**过度热情**——一点小事也开一堆子 agent，成本和时间翻几倍。

所以本节教的不是"多派"或"少派"，而是：**掌握判断线，然后观察你手上这个工具的默认倾向，往反方向校准。**

这个教法的好处是**不会过期**：工具换了、模型升级了，判断线还成立，学员只需重新观察一次默认倾向。老师上课当天按实际表现口头补充"今天这个工具偏哪边"。

### 5.6 区分"设计一个验证角色"和"随手派个人复查一下"
这两件事看起来一样，实质相反，必须点破：

- ❌ **随手外包验证**："你派个 agent 帮我 double check 一下"——它不知道要查什么，回来一句"看起来没问题"，你付了成本买了个安慰。
- ✅ **设计验证角色**：一个有明确判据、独立 context、只做验证的角色。它强在**没看过你怎么做的**，所以看得见你的盲点——自我复查的 context 里全是"我刚做对了"的痕迹。

这条同时回收 L6 的铁律（它说完成不算完成）：**验证的价值来自独立，不来自"多一个人看过"。**

### 5.7 汇总是你的活，不能一起外包
学员最危险的终局是"我派了一堆 agent，它们说都好了"。子 agent 的报告是**它的视角**，而且你看不到它的过程。所以要教三件事：报告里该有什么、你审什么、以及"它没说的"往往才是关键（它跳过了什么、它假设了什么、它有没有真跑验证）。

### 5.8 延续 Vibe Coding 口径
全程不教配置项、不教参数。本节的四个动作是**派（写 brief）、隔（划边界）、盯（看它有没有歪）、收（审报告）**——全是 Agent 替不了你的判断。

## 6. 课堂最终产物

每位完成者应有：

- 一次**成功的宽调查分派记录**：派了几个、各自 brief 是什么、拿回了什么结论、比自己一路读快了多少。
- 一次**过度分派的翻车记录**（红灯实验）：派了什么小活、多花了多少时间、绕了什么远路。
- 一条**自己写的判断线**（该派 / 不该派各三条以上，从自己的两次实验里来）。
- 一份**分派 brief 模板**（目标 / 边界 / 要什么形态的产出 / 怎么算完成）——L6 任务交付单的变形。
- 至少一个**角色化的子 agent 定义**（如一个 verifier 或一个 investigator）。
- 一句话能说清：**我这次派对了/派错了，判据是什么。**

## 7. ~132 分钟流程

| 时间 | 阶段 | 课堂动作 | 阶段产物 |
|---|---|---|---|
| 0–10 min | 开场 | 回放 L6：有一类任务一个 agent 天生跑不好，问题在结构不在你 | "该分家"的共识 |
| 10–26 min | 子 agent 是什么 | **多一个独立 context**；主 agent 的活变成分派+汇总 | 一句话立论 |
| 26–38 min | 收益：context 隔离 | 脏活不污染主 context；直接治 L6 的病 | 收益机制 |
| 38–50 min | 代价三项 | 冷启动 / 报告开销 / 它看不见你的对话 | 代价机制 |
| 50–64 min | **动手 A：宽调查并行分派** | 派几个独立调查，收结论 | 一次正收益记录 |
| 64–69 min | 休息 | — | — |
| 69–81 min | **动手 B：派一个不该派的（红灯）** | 故意派个两三步的小活，计时对比 | 一次翻车记录 |
| 81–92 min | 判断线 | 从 A/B 两次数据里长出该派/不该派 + 工具默认倾向校准 | 自己的判断线 |
| 92–104 min | 三条铁律 | 一次交清 / 派了就认 / 要它知道的写进去 | 三条铁律 |
| 104–114 min | 并行与冲突 | 共享文件系统不共享对话；互相覆盖；隔离与写边界 | 并行安全 |
| 114–124 min | 角色化 + verifier | 把子 agent 定义下来（接 L5）；独立 context 为什么强 | 一个角色定义 |
| 124–132 min | 汇总是你的活 + 收尾 | 报告 ≠ 结论，审什么；作业 | 作业清单 |

> 节奏提示：**动手 A 和 B 必须相邻**（中间只隔一个休息），对比的冲击力全靠这个紧邻。B 很快（本来就是个小活），别给太多时间，10 分钟够。

## 8. 各阶段教学细节（要点）

### 子 agent 是什么（本节的立论页，慢讲）
一句话：**它不是多一个人手，是多一个独立的 context。**

配一张对比图：

```text
【L6：一个 context】
你 → 主 Agent ──读 50 个文件──→ context 里堆了 39 份"不是这里"
                                  ↓ 这些垃圾持续影响它后面每一轮
                              结论质量下滑

【L7：分家】
你 → 主 Agent ──派──→ 子 Agent A（自己的 context：翻模块 1）→ 只回结论
                ├──→ 子 Agent B（自己的 context：翻模块 2）→ 只回结论
                └──→ 子 Agent C（自己的 context：翻模块 3）→ 只回结论
                       ↓
              主 context 里只有 3 条结论，没有 39 份垃圾
```

同时点破**主 agent 的活变了**：从"自己一路干"变成"分派 + 汇总"。这也意味着**你的活变了**：你现在审的不是它写的代码，是它的分工合不合理、它收回来的结论可不可信。

### 收益：context 隔离（接 L6 的病）
把 L6 的五条机制拿出来逐条对：

| L6 的病 | context 隔离怎么治 |
|---|---|
| context 稀释（越到后面越不守规矩） | 脏活不进主 context，主 context 一直短 |
| 压缩丢细节 | 主 context 没胀到要压缩 |
| 错误累积 | 子 agent 的弯路留在它自己的 context 里，不会带回来 |

**但要诚实**：目标漂移和进度幻觉这两条，隔离**治不了**——反而更难发现，因为你连它的过程都看不到了。这条张力要讲，它直接引出 §「汇总是你的活」。

### 代价三项（每条配一句"所以"）
1. **冷启动** —— 子 agent 从零开始建 context：它不知道你们刚聊了什么，得自己重新摸索一遍项目。*所以：小活不值得派。*
2. **报告开销** —— 它写一份报告，你（或主 agent）再读一遍。*所以：结论型任务值得派，过程型任务不值得。*
3. **它看不见你和主 agent 说过的话** —— 这条学员最容易踩。子 agent 拿到的只有你派它时写的那段 brief。*所以：要它知道的，必须写进 brief 或者落盘成文件。*

第 3 条要用一个反例讲透：「你派它去改一个文件，但"我们项目不用 xxx"这个规矩是你半小时前在对话里说的——它不知道，它会用 xxx。」

### 动手 A：宽调查并行分派（投屏示意）
```text
我要查清楚 xxx 这个功能到底散落在哪些地方。
分头查，别自己一路读完：
- 一个查 src/api/ 下有哪些地方碰了它
- 一个查 src/components/ 下有哪些地方用了它
- 一个查配置和脚本里有没有引用
每个只要三样东西：文件清单、每处是怎么用的（一句话）、有没有意外发现。
都回来之后你汇总，告诉我改动它的话哪些地方会连带受影响。
```
点出这段 brief 里的四个要件：**分工边界清楚 / 要什么形态的产出说清了 / 并行发出去 / 汇总动作明确交给主 agent。**

### 动手 B：派一个不该派的（本节红灯实验）
挑一个**你自己两三个动作就能做完**的活（改一个常量、看一个函数在哪定义的、加一行日志），故意派出去。**计时**。

学员会看到：它要先摸清项目结构 → 找到文件 → 做那件小事 → 写一份报告 → 主 agent 再读报告。**比你自己做慢好几倍，而且它可能还理解错了。**

过关标准：**你能说出这次多花的时间具体花在哪几个环节上**（对应代价三项）。

### 判断线（从 A/B 长出来）
```markdown
## 该派（满足多条）
- [ ] 要读 / 要查的地方很多，而且彼此独立
- [ ] 我只要结论，不需要看过程
- [ ] 这些活可以同时干，互不依赖
- [ ] 脏活会污染主 context（大量试错、大量无用信息）
- [ ] 需要一个"没看过我怎么做的"独立视角（验证类）

## 不该派
- [ ] 我自己几步就能做完
- [ ] 需要来回对话才能定的事（每次补 brief 都是一次冷启动）
- [ ] 强依赖前一步结果的串行活
- [ ] 只是想"多一个人看看"（没有明确判据的复查）
```
**加一条元判断**：观察你手上这个工具的默认倾向——它是偏保守（该派不派）还是过度热情（什么都派）？**往反方向校准。**

### 三条铁律
1. **一次交清** —— 别"派出去 → 等 → 发现没说清 → 再补一句"。每次补 brief 都是重新冷启动。派之前把 brief 写完整。
2. **派了就认** —— 不要重做它的活，也不要自己再把它的结论推导一遍。那等于**付两倍成本拿一份结果**。不信它就别派；派了就在"审报告"这一层把关，不在"重做"那一层。
3. **要它知道的，写进指令或落盘** —— 它读不到你的对话。规矩、上下文、前面的决定，要么写进 brief，要么写成文件让它读。（这条直接回收全系列的 SoT 主线：**落盘的东西才是跨 context 存活的东西。**）

### 并行与冲突（一句话点破 + 一个事故）
**它们共享文件系统，不共享对话历史。**

- 不共享对话 → A 不知道 B 在干什么。
- 共享文件 → A 和 B 可能同时改同一个文件，后写的覆盖先写的。

事故长什么样：两个 agent 并行改同一个模块，各自都"成功了"，合起来是坏的。

三条防法：
1. **划写边界** —— 每个 agent 只许碰指定目录/文件，写在 brief 里。
2. **读可以并行，写要收拢** —— 调查类（只读）随便并行；改代码类尽量串行，或者严格分区。
3. **物理隔离** —— 让并行改代码的 agent 各自在独立的工作副本上干，最后再合。

### 角色化（接 L5）
反复要派的活，把它定义成一个角色存下来——和 L5 把反复说的话做成 Skill 是**同一个思路的另一个维度**：

| | Skill（L5） | 子 Agent 角色（L7） |
|---|---|---|
| 沉淀的是 | 一套做事的**套路** | 一个**干活的角色**（带自己的 context 和职责） |
| 解决的重复 | 我又要讲一遍怎么做 | 我又要派一个人去查这类事 |
| 共同点 | 都是一次定义、处处复用、改一处全局生效 | 同左 |

判断线同 L5：**重复 ≥3 次 + 职责固定**，才值得定义成角色。

### verifier：为什么独立 context 更强
让 agent 自己复查，它的 context 里全是"我刚这么做的、我觉得对"的痕迹——**它看不见自己的盲点**。一个没看过你怎么做的角色，只拿到"成品 + 判据"，才看得见。

但必须配判据：**"你复查一下"不是验证，"对照这三条检查并给出红/绿"才是**。（直接续 L4 红灯 + L6「能跑出红绿的才叫验证」。）

### 汇总是你的活
子 agent 的报告是**它的视角**，而且你看不到它的过程。所以：

- **报告里该有什么**：结论、依据（具体到文件/行/命令输出）、它跳过了什么、它假设了什么。
- **你审什么**：依据够不够硬（有没有具体出处）、有没有"应该 / 大概"这类猜的痕迹、验证是它跑的还是它以为的。
- **最关键**：**它没说的那部分**。L6 的进度幻觉在这里会变得更隐蔽——它说"查完了没问题"，而你连它查了哪些地方都看不见。

一句话收：**分派省的是你的 context，不是你的判断。**

## 9. 分派 brief 模板 + 报告审查速查

**分派 brief（L6 任务交付单的变形）**
```markdown
## 要它做什么
一句话说清任务。

## 边界
- 只查 / 只改 ______
- 不要碰 ______

## 它需要知道但对话里才有的事（关键！它读不到你的对话）
- ______（项目规矩 / 前面的决定 / 已经排除的方向）

## 要什么形态的产出
- ______（清单 / 结论 + 依据 / 红绿判定），每条要给出处

## 怎么算完成
- ______（可执行的判据）
```

**报告审查速查**
```markdown
- [ ] 每条结论都有具体出处（文件 / 行 / 命令输出），不是"看起来"
- [ ] 没有"应该 / 大概 / 我假设"这类猜的痕迹
- [ ] 说跑过的验证，是真跑了（有输出），不是它以为跑了
- [ ] 它跳过了什么？它假设了什么？（问它）
- [ ] 我有没有在重做它的活（如果有 → 当初就不该派）
```

## 11. 老师课前准备

- 一个**够大的兜底仓库**：小项目里子 agent 的收益看不出来，这条是硬要求。仓库里要预埋一个**真实的跨模块问题**（某功能散落在 4–5 处）。
- **A 组的示范 brief**（三路并行调查）+ **B 组的小活题目**（明确到"你自己两三步能做完"）。
- **一份预录的过度分派翻车记录**：万一课上 B 组恰好很快，要有能投屏的对照。
- **一个并行覆盖事故的复现或录屏**：两个 agent 同改一个文件、互相覆盖。这一幕现场不好复现但极有说服力。
- **上课当天先自己试一次**：确认今天这个工具/模型对分派是偏保守还是过度热情（§5.5），课上口头校准。
- 分派 brief 模板 + 报告审查速查卡（发给学员）。
- 一个做好的**角色化子 agent 示范**（如 investigator 或 verifier），现场从零定义一遍。

## 12. 高频风险与课堂降级

| 风险 | 处理 |
|---|---|
| 学员项目太小，A 组看不出收益 | 用兜底仓库；这是本节最常见的失败原因，课前要点名提醒 |
| B 组（红灯）恰好跑得很快、没翻车 | 投预录记录；并让那位学员算总账（冷启动 + 报告 + 你读报告的时间也要计入）|
| 学员学完变成"什么都派" | 这是**本节最需要防的偏差**。判断线和 B 组红灯必须保住，宁可砍角色化 |
| 并行冲突现场没复现出来 | 投预录事故；或老师现场制造（两个 agent 同改一个文件）|
| 学员在重做子 agent 的活 | 当场点出铁律②：你在付两倍成本；不信它就别派 |
| 汇总环节被跳过 | 明确：本节最后一段是"你审报告"，不是"它们说好了就好了"|
| 时间不够 | 优先级：**立论页（P02）+ 动手 A + 动手 B + 判断线 + 三条铁律**必须保；并行冲突、角色化、verifier 可以老师演示 + 课后做 |
| 有人环境不支持并行 | 结对共看；本节重点在判断与 brief，不在"我自己跑起来了"|

## 13. 作业

1. 找一个**真实的宽调查问题**（要读很多地方才能下结论的），用**分派 brief 模板**并行派出去，收结论。
2. 再故意**派一次不该派的**（一个你自己几步能做完的活），计时对比，写清多花的时间花在哪几个环节。
3. 写出**你自己的判断线**（该派 / 不该派各三条以上），必须来自上面这两次的数据。
4. 记录一次**你看不见的过程**带来的风险：子 agent 报告里有没有"应该 / 大概"、有没有它跳过但没说的东西——按报告审查速查过一遍。
5. 把一个反复要派的活**角色化定义下来**（一个 investigator 或 verifier），并用一次。
6. 观察并写下：**你手上这个工具对分派偏保守还是偏热情**，你打算往哪边校准。
7. 提交：两次分派记录 + 判断线 + 一个角色定义 + 一句话「我这次派对了/派错了，判据是什么」。

## 14. 官方依据与数据纪律

- **子 agent 的核心机制**：每个子 agent 在自己的**独立上下文**里运行，拥有自己的对话历史、系统提示和工具；**共享文件系统，不共享对话历史**——官方多 agent 文档明确写了这一点，并给出配套告诫：「不要假设共享上下文。如果需要子 agent 基于某件事行动，必须在派发消息里说清，或者写到磁盘上。」这是本节铁律③的直接依据。
- **单层分派**：官方限制"只允许一层委派"（被派出去的 agent 不能再往下派），且这是**校验层面强制**的，不是悄悄摊平。本节据此不讲多层编排。
- **分派的开销**：官方分派指南原话——「子 agent 会成倍放大成本和时间：每一个都要重新建立上下文、重新探索、汇报回来，然后你还要再读一遍它的报告。」并明确列出**不该派**的场景：几个工具调用就能做完的活、以及"用来复查/验证你自己的工作"。本节代价三项与判断线据此而来。
- **一次交清 / 派了就认**：官方原话「第一次就把子 agent 交代清楚，避免派出去、等待、再重新交代」和「如果你委派了，就认这个委派——不要重做它的工作，也不要在它汇报回来后重新推导它的结论」。这是铁律①②的原文级依据。
- **并行发出**：多个独立任务应在**同一条消息里一次发出**以并发执行，而不是一个个串行发。
- **异步优于派出去干等**：官方长任务指南指出，与编排者**异步**协作的子 agent 优于"派出去就阻塞等待"——长活的 agent 保住自己的上下文而不必每个子任务重建，编排者也不被最慢的那个卡住。这是 §8「读可以并行」和作业设计的依据。
- **独立 context 的 verifier**：官方指出**独立上下文的验证者 agent 往往优于自我批评**。同时另有指引反对"随手派 agent 做复查"。本节把这两条解释成同一条原则的两面（§5.6）：**验证的价值来自独立 + 有判据，不来自"多一个人看过"**——这是本节的教学再表述，不是官方原文的直接引语，deck 上不会声称是官方原话。
- **分派倾向随版本反转（重要）**：官方迁移文档记录了**相邻两代模型对子 agent 的默认倾向是相反的**——一代需要额外提示才肯委派，下一代反而需要显式设上限。这正是 §5.5 那条元判断的依据，也是本节**坚决不讲具体版本参数**的理由：写死"要多派"或"要少派"，下个版本就错。
- **数据纪律（延续 L6 §14）**：deck 上只讲**机制类别与判断线**，不引任何与具体模型版本绑定的行为描述、参数名、上限数字或跑分。判据是：**换个模型、换个工具也成立**的才留。工具当天的实际倾向由老师口头校准（§11）。
- **学员自己的 A/B 数据是本节主教材**：判断线的说服力来自学员当场测出的时间差，官方文档只用来给机制命名和背书。

## 15. 待确认项

进入 PRD / deck 开发前需要最终决定：

1. 时长定 132 min 还是放宽到 140+（同 L4–L6 倾向可延长）。
2. **L7 是不是系列收尾？** 这直接决定 P23 是"下节预告"还是"整个系列的收束"。如果是收尾，建议 P23 之外再加一页把 L1–L7 的主线串一遍（人 / 产品 / 视觉 / 交付 / 能力 → 看懂 context → 给 context 分家）。**需要 Rick 定。**
3. 讲不讲**跨机器 / 团队共享 agent 定义**（把角色定义提交进仓库让全组共用）？目前按 L5 的处理方式只在角色化那一页点一句，不展开——要不要提升为一个独立段落？
4. **并行改代码**讲到多深：只给"划写边界 / 读并行写收拢 / 物理隔离"三条原则，还是现场演示一次独立工作副本的完整流程？（后者更实用但要吃掉 10+ 分钟。）
5. B 组红灯题目**统一还是各选各的**？建议统一（保证一定翻车、便于全班对比时间数据）。
6. 并行覆盖事故：靠预录，还是设计一个**必然触发**的课堂小实验？（同 L6 的进度幻觉，需课前实测能不能稳定复现。）
7. 是否点一句子 agent 与后续 MCP / Hooks 的分界（各是什么、别混），像 L5 对 Skill、L6 对 context 手段那样做边界声明。
