## 怎么用这份讲义

这份材料里的每一条 prompt，右边都有一列 **「为什么这么写」**。

> ## 考试不考 prompt，考右边那一列。

因为你回去用的不会是 star-mansions，可能也不是今天这个工具。
**prompt 抄过去就废了，理由抄过去还成立。**

自测标准很简单：

> **遮住左边，你能不能照着右边把左边重写一遍？**

能，这节课你就带走了。

## §0 七条通用规律

L5–L7 一路攒下来的，今天全部要用。**先记这七条，后面所有 prompt 都是它们的实例。**

| # | 规律 | 为什么 |
|---|---|---|
| 1 | **边界写在字面上，别指望它猜** | 它读不到你和别人的对话，也读不到你脑子里的分工 |
| 2 | **否定句比肯定句强制力高一档** | `不要读 backend/` > `请专注 frontend/`。Agent 默认倾向顺手多做 |
| 3 | **证据格式前置** | 不前置只能拿到自然语言总结，没法验收，更没法给别人当证据 |
| 4 | **逼出 not_checked** | 不问，你永远不知道它跳过了什么——**而缺口正是今天要找的东西** |
| 5 | **给「不知道」一个出口** | 不给出口就是逼它编。这条最容易漏 |
| 6 | **范围靠 `tools` 物理限制，不靠正文请求** | 正文是请求，`tools` 是保证 |
| 7 | 🆕 **传证据，不传结论** | 你把证据总结过再给对方，掺进去的是你的判断——那不叫证伪，叫说服 |

**第 7 条是今天新加的，也是今天操作层最重要的一条。**

## §1 拍 1 · 你的第一个 agent

### 1.1 完整文件：`.claude/agents/sm-investigator-frontend.md`

```markdown
---
name: sm-investigator-frontend
description: 只读调查 star-mansions 的前端代码，回答关于登录、会话与接口调用的具体问题。需要确认前端实际行为时使用。
tools: Read, Grep, Glob
model: <中间档>
---

你是 star-mansions 项目的前端只读调查员。

## 范围
- 只读 `frontend/` 目录。
- **不要读 `backend/`，不要读部署与配置文件。** 那两块由别人负责。
- 不修改任何文件。

## 产出合同
status: complete | partial | blocked

## findings
- 结论：______
  evidence: `文件:行号` + 一句解释

## checked
- ______

## not_checked
- ______

## 硬规则
- 每条结论必须带 `文件:行号`。没有行号的结论不要写。
- 只描述你**读到的代码行为**，不要推测其它模块怎么实现。
- 证据不足时返回「无法判断 + 缺什么证据」，不要猜。
```

### 1.2 逐格：这一格在治什么

| 这一格 | 它在治什么 |
|---|---|
| `name` | 点名调用时用。**必须和文件名一致**，不一致点不到 |
| `description` | **给主 Agent 看的**，它靠这句决定要不要派你。写含糊了，主 Agent 根本不会派它 |
| **`tools`** | ⭐ **不写这一行，它就能改文件。** 正文里写一百遍「只读」都不如这一行。**这是六格 brief 里唯一能从「请求」变成「保证」的一格** |
| `model` | 按**判断密度**选，不按重要性。调查员是执行密集，中间档够用；唱反调是判断密集，要最强档 |
| 范围（否定句） | 规律 2。而且这里是**双保险**——`tools` 挡写，正文挡读的范围 |
| 产出合同 | 三路格式不统一就没法比对。**而今天要比对的正是三路之间的缝** |
| `not_checked` | 规律 4。**三路的 not_checked 拼起来，就是那道信息墙的形状** |
| 出口 | 规律 5，不给出口它会编 |

### 1.3 调用句

```text
用 sm-investigator-frontend 调查：星宿记录的历史列表有时看不到之前保存的内容。
前端这一侧，从填邮箱登录到调用 /api/history，做了哪些对邮箱字符串的处理？
每一步都要给出 文件:行号。
```

| 这一句 | 它在治什么 |
|---|---|
| `用 sm-investigator-frontend 调查` | **指名调用**（L7 三档里的第②档）。不指名，主 Agent 可能自己干了 |
| `历史列表有时看不到之前保存的内容` | 只给**用户视角的症状**。给方向就等于替它推理 |
| `从填邮箱登录到调用 /api/history` | 划一条**路径**而不是一个目录。路径比目录更能约束它别乱翻 |
| `做了哪些对邮箱字符串的处理` | 具体到能被证据回答，但**不包含答案**——注意这里没提「大小写」 |
| `每一步都要给出 文件:行号` | 规律 3。**而且这些行号就是你等一下要粘贴的原文** |

### ✍️ 你的记录

```text
我的 tools 那一行写的是：_______________________________

仓库自带的 .claude/agents/ 里，谁的 tools 划得比我更死？_______________
```

## §2 拍 2 · 浅题：三路并跑

### 2.1 题面

```text
【浅题】

用户报告：用同一个邮箱登录，之前保存的星宿记录有时候看不到了。
不是报错，就是列表空的。重新登录一次有时又出来了。

三路只读调查，各自回答：你这一侧，有没有任何东西会影响
「这条记录属于谁」这个判断？

规则：
1. 全程只读，谁都不许改文件。
2. 三路各自独立，不要把 A 的结果喂给 B。
3. 三路都用同一个产出格式，不然没法比对。
```

| 这一句 | 它在治什么 |
|---|---|
| `不是报错，就是列表空的` | 排除「查错误日志」这条捷径，逼它读代码 |
| `重新登录一次有时又出来了` | 「有时」= **暗示状态相关，但不说是什么状态** |
| `有没有任何东西会影响「这条记录属于谁」` | 三路问同一个问题，而**这个问题跨越了三路的边界** |
| `不要把 A 的结果喂给 B` | ⭐ **这是今天的实验变量。** 先忠实执行，才有对照 |

### 2.2 三路只改三处

| 角色 | 只读范围 |
|---|---|
| `sm-investigator-frontend` | `frontend/src/` |
| `sm-investigator-backend` | `backend/src/`、`backend/api/` |
| `sm-investigator-config` | `backend/.env.example`、`backend/vercel.json`、`.github/workflows/`、`backend/db/schema.sql` |

> **三个队友的差别只有几行。角色不是人格，是边界。**

### ✍️ 你的三条结论

```text
frontend：__________________________________________
backend： __________________________________________
config：  __________________________________________

这三份里有错的吗？  □ 有  □ 没有
```

## §3 🔥 拍 3 · 那一次粘贴

**今天最重要的一个动作。**

### 3.1 你要打的字

```text
frontend 那一路的原文：

> authAdapter.login 只对邮箱做了 trim()，不做大小写归一。
> 证据：frontend/src/lib/authAdapter.ts:31

这会影响你刚才的结论吗？
```

### 3.2 逐句：**本讲义最值钱的一页**

| 这一句 | 为什么这么写 | 写错会怎样 |
|---|---|---|
| `frontend 那一路的原文：` | **标明来源。** 让它知道这不是你的判断，是另一个调查者的观测 | 不标来源，它会当成你在提要求，倾向于**顺从**而不是**核对** |
| 用引用块贴**原文** | 规律 7。**证据可以被独立核对，结论不行** | 你一总结，它翻转的是「同意你」，不是「发现矛盾」 |
| 保留 `文件:行号` | 它可以自己去读那一行验证 | 没有行号，它只能选择信或不信——**那是社交，不是证伪** |
| `这会影响你刚才的结论吗？` | **开放问句。** 不给方向，让翻转由它自己完成 | 写成「是不是大小写导致 id 不一致？」= 你替它推理完了 |
| `你刚才的结论` | 锚定到**它自己说过的话**，逼它做前后对比 | 不锚定，它会当成新问题重新答一遍，不产生「我错了」这一步 |
| 全程不提「大小写」 | 那是它要自己接的那一环 | 提了，这一拍就从**发现**降级成**确认** |

### 3.3 它没翻转？用这句

```text
那如果同一个用户先后填了 Rick@x.com 和 rick@x.com，
emailToId 会派生出几个 id？
```

| 这一句 | 为什么 |
|---|---|
| 给两个**具体字面值** | 从抽象规则降到具体输入。**抽象它能糊弄，具体它必须算** |
| `会派生出几个 id` | 问一个**有唯一数字答案**的问题。答「2」它就自己把结论推翻了 |

> ⚠️ 用了这句要意识到：**提示越具体，说明这条信息越难自己跨过去。** 那道墙是真的。

### ✍️ 记录

```text
我贴进去的那句原文：____________________________________
它翻转后说的第一句话：__________________________________
```

## §4 拍 4 · 反向传递 + 三类消息

### 4.1 贴回 A

```text
backend 那一路的原文：

> emailToId() 用邮箱原文派生 user.id，
> Rick@x.com 和 rick@x.com 会得到两个不同的 id。
> 证据：backend/src/handlers/auth.ts:12

你那一侧，有没有可能让同一个人先后提交两种大小写？
```

| 这一句 | 为什么 |
|---|---|
| 同样是**原文 + 来源 + 行号** | 规律 7，双向都要守 |
| `你那一侧，有没有可能……` | 把问题**限定在它的边界内**。不问「所以根因是什么」——**根因的裁决是你的活** |
| 问**触发路径**不是结论 | 这一步要的是「怎么发生的」，闭合证据链 |

> 注意：你没有让任何一个成员宣布根因。**根因是你根据两边证据自己裁决的。这就是 Lead 的活。**

### 4.2 关键消息卡（🖨 纸质，人手一份）

```markdown
[DISCOVERY] 我传了哪一句原文，从谁到谁：
            ______________________________________________

[CONFLICT]  它和对方原来的哪条结论矛盾？双方证据各是什么：
            ______________________________________________

[DECISION]  最后怎么裁的？谁去确认的？
            ______________________________________________
```

**为什么只留这三类：只有这三类会改变后续行动。**
「收到」「同意」「我这边继续」——不改变任何事，是噪音。

## §5 拍 5 · Team charter（课堂只填两项）

### 5.1 空白版

```markdown
## 2. 成员与初始所有权
- Lead（你自己）：拆分、盯覆盖、处理冲突、最终验收
- 成员 A：______        只读范围：______
- 成员 B：______        只读范围：______
- 成员 C（**唱反调**）：______   它的任务是：______

## 4. 通信规则
- 什么样的证据必须立即转给别人：______
- 转给谁（点名，不能写「相关的人」）：______
- 冲突怎么处理：附双方证据，**不投票**，由 ______ 裁决
- 转发时：贴 ______（原文 / 我的总结）
```

### 5.2 填好的样例

```markdown
## 2. 成员与初始所有权
- Lead（我）：裁决、外部验收
- A · frontend investigator   只读范围：frontend/
- B · backend investigator    只读范围：backend/src/、backend/api/
- C · 唱反调                  它的任务是：给 A 和 B 的每条结论找一个反例

## 4. 通信规则
- 必须立即转的证据：任何「某个值在我这一侧被改变 / 未被改变」的观测
- 转给谁：A ↔ B 双向互转，C 全收
- 冲突：附双方 文件:行号，不投票，由 Lead 裁决
- 转发时：贴原文，不贴我的总结
```

### 5.3 四个填写要求（**考点**）

| 这一格 | 为什么这么填 |
|---|---|
| C 的任务写成「**给每条结论找一个反例**」 | 不能写「批判性思考」「保持怀疑」——那是**态度**，不是任务。**任务必须是可执行的动作** |
| 「必须立即转」按**形状**定义，不按重要性 | 「重要」由谁判断？**恰恰是最没资格判断的那个人**——他不知道别人在查什么 |
| 转给谁要**点名** | **没有广播。** 想让所有人知道，得发多条 |
| `不投票` | 三个 Agent 很容易达成一致，**而一致不等于对** |
| `贴原文，不贴总结` | 规律 7。写进 charter 才守得住 |

## §6 拍 6 · 深题

### 6.1 题面

```text
【深题】

线上现象：用户保存了星宿记录，过一阵子回来看，历史是空的。
但有时候又能看到。见附页《线上现象报告》。

找出根因，并给出可验收的证据。

规则：
1. 全程只读。
2. 这一次，你可以在三个会话之间传递证据 ——
   但每一次传递你都要记在任务板上。
3. 计时终点不是「找到根因」，是第一次 CONFLICT 被裁决。
```

| 这一句 | 为什么 |
|---|---|
| `但有时候又能看到` | 和浅题同一个手法：「有时」= 状态相关，但不说是什么状态 |
| `见附页《线上现象报告》` | 诱饵全在那一页。**题面本身不能有任何倾向** |
| `你可以在三个会话之间传递证据` | 明确宣布**实验变量变了**。你要意识到「现在允许了」，才会去做 |
| `每一次传递都要记在任务板上` | 不记，讲评时没有素材 |
| `终点是第一次 CONFLICT 被裁决` | 终点定在**过程**而不是**答案**上。定在答案上，快的组松懈、慢的组崩溃 |

### 6.2 三路 brief（复用同样三个角色文件，只换问题）

```text
用 sm-investigator-backend 调查：

每条路径给出 文件:行号，并说明它在什么条件下会被走到。
```

| 这一句 | 为什么 |
|---|---|
| `经过哪些存储路径` | **复数。** 问「哪些」而不是「怎么存的」，逼它把分支都列出来 |
| `在什么条件下会被走到` | ⭐ 深题的关键提问。**它的回答后来会和配置那一路撞车** |
| 仍然要 `文件:行号` | 拍 8 的外部验收要用 |

## §7 🔥 拍 7 · 唱反调 prompt

**今天第二重要的 prompt，也是最容易写错的一个。**

### 7.1 正确版

```text
你的任务不是找根因，是找反例。

现在有一个结论：「部署 / 实例回收导致记录丢失」，
证据是每次记录消失前 30 秒内都有一次部署，时间戳吻合。

去《线上现象报告》里找：有没有「没有部署，但记录也丢了」的时候？
或者「有部署，但记录没丢」的时候？

找到就给出具体时间戳。找不到就明确说找不到，不要替这个结论辩护。
```

| 这一句 | 为什么这么写 |
|---|---|
| `你的任务不是找根因，是找反例` | **第一句就把角色定死。** 不说这句，它会顺手也去找根因，然后被同一批证据说服 |
| 把要攻击的结论**完整复述** | 它必须知道打的是什么。「挑战一下大家的结论」= 没有靶子 |
| 把对方的**证据也复述** | 让它针对证据本身找漏，而不是针对结论抬杠 |
| `有没有「没有 X，但 Y 也发生了」的时候` | ⭐⭐ **把证伪变成一个可检索的动作。** 这是整条 prompt 的技术核心 |
| 双向都问 | 因果链两端都要打。只打一端，可能漏掉更容易找的那个方向 |
| `找不到就明确说找不到` | 规律 5 的变体。**不给出口，它会硬编一个反例出来**——那比虚假共识更糟 |
| `不要替这个结论辩护` | 它的默认倾向是帮你把事情说圆，要显式禁掉 |

### 7.2 ❌ 四种常见错法（**这张表是考点**）

| ❌ 这样写 | 为什么不行 |
|---|---|
| 「批判性地看一下大家的结论」 | **态度不是任务。** 它会回一段「确实需要更多证据」的正确废话 |
| 「你觉得这个结论对吗？」 | 是非题。它大概率答「基本合理，但建议进一步验证」 |
| 「找出这个结论的三个问题」 | 逼它凑数。**没问题的时候它会编三个出来** |
| 「假设这个结论是错的，那根因是什么？」 | 跳过证伪直接换答案，等于换一个没有证据的猜测 |

> ### 「唱反调」不是一种性格，是一个有具体检索目标的任务。
> 你给不出检索目标，就得不到反调。

## §8 拍 8 · 外部验收 prompt

```text
不要重做调查。

现在的结论是：生产环境未生效的 Supabase 配置导致
history 走了进程内存回落，实例之间不共享。

只做两件事：
1. 把这条结论追溯到 文件:行号 —— 那条内存回落分支具体在哪一行？
2. 指出一条这个结论无法解释的现象（如果有）。

只回答这两条，不要给修复建议。
```

| 这一句 | 为什么 |
|---|---|
| `不要重做调查` | L7 的老规矩：**verifier 不重做探索**，重做就是又一次同样的偏差 |
| 把结论**完整给出** | 验收的对象必须明确 |
| `追溯到 文件:行号` | 外部判据第一条。**「说得通」不是证据，行号才是** |
| `指出一条这个结论无法解释的现象` | ⭐ 更狠的一条——**逼它找结论的边界**，而不是确认结论 |
| `不要给修复建议` | 今天不修。一给建议你就想动手，后面全乱 |

## §9 拍 9 · 自动 Team 的 spawn prompt

```text
用 agent team 开三个 teammate，分别用
sm-investigator-frontend、sm-investigator-backend、sm-investigator-config
这三个 agent 定义。

任务：找出线上记录丢失的根因（现象报告已在 docs/ 下）。

让它们互相对话、试图推翻彼此的理论，像一场科学辩论。
发现会改变别人方向的证据时，直接发给相关成员并抄送我。
最后把裁决过程和结论写进任务板。
```

| 这一句 | 为什么 |
|---|---|
| `用 agent team` | **不明说，工具会用 subagent 冒充**——而两者在面板上长得一样 |
| `分别用 ...这三个 agent 定义` | ⭐ **同一份文件，换个结构再跑一次。** 就是你一小时前写的那三份 |
| `让它们互相对话、试图推翻彼此的理论` | ⭐ **去掉这半句，拿到的就是三份互不相干的报告**——那是 Subagent，只是更贵 |
| `发给相关成员并抄送我` | charter 第 4 项的翻译。**没有广播**，所以要写「抄送我」 |
| `把裁决过程写进任务板` | 只写结论的话，看不到消息流动——而那正是要看的东西 |

**开完立刻做两个验证动作：**

1. 看成员名单：**多于一个成员 = team 成型；只有你自己 = 三个 subagent。**
2. 让两个成员互发一条消息，在 Lead 侧看到。

> **「你怎么知道你现在跑的是 Team 不是三个 Subagent？」**
> 答不上来 = 你在假设协作能力。

## §10 带走的三件东西

### 10.1 一句立论

> **交界处的 bug，互不通信的调查者在结构上不可能发现。不是漏了，是算不出来。**

### 10.2 通信治的两种病

| | 病 A · 交界 bug | 病 B · 虚假共识 |
|---|---|---|
| 性质 | **结构问题**——不通信就发现不了 | **概率问题**——不通信会一起错 |
| 通信的作用 | **交换证据** | **对抗证伪** |
| 多派几路能不能解决 | **不能**，派再多也是同一个和 | 有可能碰上，但不可靠 |
| 需要什么 | 两个能互相发消息的成员 | **一个专职找反例的成员** |

### 10.3 课后自查清单

- [ ] 有没有人在找反例？

## 收口
- [ ] 冲突是靠证据裁决的，还是靠投票 / 默认一致？
- [ ] 排除项有**反证**，还是只写了「没查到」？

## §12 进阶 · 如何和 Agent 对话生成专家 Agent

> **这一节不在课堂 120 分钟里讲**（拍 11 只用 3 分钟预告），但它是本节最值得带回去的方法。
>
> 拍 1 你手写了一个四格角色文件——那是**一次性调查 agent** 的正确做法。
> 但当你要造一个**给别人用、长期复用、碰得到权限**的专家 Agent 时，手写四格远远不够。

### 12.0 先看一个反面例子

❌ 不要直接对 Agent 说：

```text
帮我创建一个安全专家 Agent。
```

你会拿到一段「你是一名资深安全专家，拥有十年经验……」的人设提示词。

**它缺的是全部要紧的东西**：真实职责、能碰哪些系统、用什么工具、按什么流程走、拿什么判据定级、什么时候必须交给人。

回收 L7 那条：**人设不是边界，权限才是。**「你是世界顶级安全专家」写在正文里是一句请求；`tools:` 那一行才是保证。一段纯人设 prompt = 一个没有 `tools` 字段的角色文件。

✅ 正确做法：**让 Agent 先当 Agent 架构师，通过访谈把规格问出来，最后才写 Prompt。**

### 12.1 判断线：什么时候值得走这套？

⚠️ **这套五阶段访谈很贵**（认真做要半小时对话）。别因为方法更高级就都用它 —— 这跟本节「Team 门槛必须比 Subagent 高」是同一种判断。

| 情况 | 怎么做 |
|---|---|
| 一次性调查 / 只有你自己用 / 只读无权限 | **手写四格**（拍 1 那套），5 分钟，够了 |
| 要交给别人用 | 走五阶段 —— 别人不知道你脑子里的边界 |
| 要长期复用、会被反复调用 | 走五阶段 —— 规格是它的合同 |
| **碰得到权限 / 能改东西 / 能花钱** | **必须走五阶段** —— 权限出事没有回头路 |
| 要和其他 Agent 交接 | 走五阶段 —— 交接靠的是 Input / Output Contract |

一句话：**只读、一次性、自己用 → 手写；能改东西、给别人用 → 走规格。**

### 12.2 五阶段访谈流程

#### 第一阶段 · 定义任务（先别让它写 Prompt）

```text
我要创建一个负责 HCP/GPU 平台安全的专家 Agent。

它需要审查代码、架构、IAM、客户数据隔离和部署配置，但不能自行修改生产环境。
请先不要生成最终提示词，先通过提问帮助我明确它的职责。
每次只问一个最重要的问题。
```

| 这一句 | 它在治什么 |
|---|---|
| `请先不要生成最终提示词` | ⭐ **最关键的一句。** 不写这句，它第一轮就会甩给你一段人设 prompt，访谈根本不会发生 |
| `先通过提问帮助我明确它的职责` | 把它的角色从「答题者」换成「访谈者」 |
| **`每次只问一个最重要的问题`** | 不写这句，它会一口气问 15 个问题，你会敷衍地一次答完 —— **访谈的价值在于它根据你上一个回答调整下一个问题** |
| `但不能自行修改生产环境` | 一开始就给一条硬边界，后面所有权限设计都会围着它长 |

它应该反过来问你这些：

```text
它负责哪些系统？          最常处理什么任务？
什么问题属于它？          什么问题必须转交给其他 Agent？
它能读取和修改什么？      最终输出给谁？
```

#### 第二阶段 · 给真实案例（不要只描述抽象职责）

```text
这个 Agent 以后可能会处理以下任务：

1. 检查不同客户的 GPU workload 是否可能读取其他客户的数据。
2. 检查 ECS 服务是否只能通过 ALB 访问。
3. 检查应用是否错误信任 X-Forwarded-For。
4. 检查 S3、IAM Role 和 AssumeRole 设计。
5. 审查 PR 中的鉴权、租户隔离和敏感信息处理。
6. 对发现的问题给出 Critical、High、Medium、Low 等级。
```

**为什么必须给真实案例**：抽象职责（「负责安全」）推不出任何具体设计；真实任务能让它反推出——

```text
专业边界  ·  检查清单  ·  风险等级  ·  所需工具  ·  输出格式
```

> 至少给三个。**一个案例它会过拟合，三个才能看出共性。**

#### 第三阶段 · 让它反推专家能力

```text
根据这些任务，请反推这个专家 Agent 必须具备：

1. 哪些专业知识
2. 哪些工具
3. 哪些数据访问权限
4. 哪些固定工作流程
5. 哪些判断规则
6. 哪些升级和人工审批机制

请指出目前还缺少的信息，不要自行假设关键业务规则。
```

| 这一句 | 它在治什么 |
|---|---|
| `反推` | 顺序反过来 —— 从**它要干的活**推**它要有的能力**，而不是先想「一个安全专家应该会什么」 |
| `请指出目前还缺少的信息` | 逼它交出缺口清单。**这一步等于 L7 的 `not_checked`** |
| **`不要自行假设关键业务规则`** | ⭐ AI 会很乐意替你填 Severity 定义和升级门槛 —— **而那些恰恰是只有你知道的**。不写这句，你会得到一份看起来很完整、但业务规则全是它编的规格 |

> ⚠️ 收到规格后，**把「AI 填的」和「你填的」分开标一遍**。凡是它替你决定的业务规则，都要你自己确认过才算数。

#### 第四阶段 · 先生成规格，**还不要 Prompt**

```text
现在请生成这个专家 Agent 的完整规格，包含：

- Agent 名称        - Mission              - Responsibilities
- Out of Scope      - Knowledge Sources    - Available Tools
- Permissions       - Standard Workflow    - Decision Rules
- Severity Definitions                     - Escalation Rules
- Input Contract    - Output Contract      - Memory Rules
- Failure Handling  - Evaluation Criteria

暂时不要生成系统提示词。
```

**为什么规格要先于 Prompt**：

> 规格是**可以逐条审的**，Prompt 是一大段散文，你审不动。
>
> 这跟本节拍 5 是同一条纪律：**charter 必须在开跑前写死**。
> 写 Prompt 相当于开跑，规格相当于 charter。

#### 第五阶段 · 规格确认后，才生成 System Prompt

```text
根据已经确认的 Agent 规格，生成可直接使用的 System Prompt。

要求：
1. 不使用空泛的专家人设描述。
2. 明确职责边界和禁止事项。
3. 明确每次任务的执行步骤。
4. 要求结论必须有证据。
5. 信息不足时不得猜测。
6. 输出必须符合结构化格式。
7. 高风险操作必须要求人工批准。
8. 包含与其他 Agent 的交接规则。
```

八条里有四条你今天已经练过了：

| 这一条 | 今天在哪练的 |
|---|---|
| `结论必须有证据` | 三路 brief 的 `文件:行号`（拍 2） |
| `信息不足时不得猜测` | 角色文件里那个「不知道」的出口（拍 1 · 规律 5） |
| `输出必须符合结构化格式` | 三路统一产出合同（拍 2） |
| `包含与其他 Agent 的交接规则` | charter 第 4 项通信规则（拍 5） |

### 12.3 可直接复制的完整提示词

> 把下面整段发给 Agent，把【】里换成你的领域。

```text
你现在是一名 Expert Agent Architect。你的任务不是直接回答领域问题，
而是通过结构化访谈，帮助我设计一个真正可执行、可验证、可评估的专家 Agent。

我要创建的专家 Agent 初步用途是：

【在这里填写领域，例如：负责 HCP/GPU 平台的安全审查、客户数据隔离、IAM、网络边界和代码安全】

请按照以下流程工作。

## 工作规则
- 不要一开始就生成最终 System Prompt。
- 先理解专家 Agent 实际需要完成的任务。
- 每次只问一个最重要的问题。
- 优先询问具体案例、真实输入、期望结果和操作限制。
- 不要只询问抽象的「风格」或「角色定位」。
- 对缺失的关键业务规则必须询问，不得自行假设。
- 如果我的设计存在职责重叠、权限过大或无法验证的问题，要明确指出。

## 第一阶段：任务发现
通过提问确认：
- 这个 Agent 服务于什么系统或业务
- 它最常处理哪些任务
- 它接收什么输入
- 它应该交付什么结果
- 谁会使用它的结果
- 哪些问题属于它 / 哪些不属于它
- 哪些情况必须交给其他 Agent 或人工

请要求我至少提供三个真实任务案例。

## 第二阶段：能力反推
根据真实任务，推导这个 Agent 所需要的：
专业知识 / 内部知识来源 / 外部权威资料 / 工具和 API /
代码库或数据访问 / 执行权限 / 验证方法 / 固定检查清单 /
决策规则 / 风险等级 / 升级机制

区分三类：必须具备 · 推荐具备 · 暂时不需要。

## 第三阶段：风险检查
检查设计中是否存在：
- 职责范围过大
- 与其他 Agent 职责重叠
- 缺少真实数据来源
- 只有建议能力但没有验证能力
- 权限超出职责
- 可以直接修改生产环境
- 缺少人工审批
- 输出无法被其他 Agent 或系统消费
- 无法衡量 Agent 是否正确
- Agent 可能在证据不足时猜测

对每个问题给出修改建议。

## 第四阶段：生成 Agent Specification
信息充分后，生成完整规格：

1. Identity：Agent Name / Domain / Mission
2. Scope：Responsibilities / Out of Scope / Ownership Boundaries
3. Knowledge：Required Domain Knowledge / Internal Sources /
   External Authoritative Sources / Knowledge Freshness Rules
4. Tools：Read / Analysis / Execution / Verification / Prohibited
5. Permissions：Allowed / Requiring Approval / Forbidden / Least-Privilege
6. Workflow：理解请求 → 确认范围 → 收集证据 → 执行分析 → 工具验证 →
   评估影响 → 形成结论 → 修复建议 → 判断升级 → 输出结构化结果
7. Decision Rules：严重程度定义 / 阻塞条件 / 可接受风险 /
   置信度规则 / 信息不足处理方式
8. Collaboration：可调用哪些 Subagent / 向谁请求帮助 /
   何时交接 / 如何避免同时修改相同资源
9. Input Contract：标准输入字段
10. Output Contract：Summary / Status / Findings / Evidence / Severity /
    Impact / Recommendation / Verification Performed / Confidence /
    Assumptions / Missing Information / Escalation Required
11. Memory：长期记住什么 / 不保存什么 / 过期信息怎么处理 /
    历史决策和已接受风险怎么记
12. Evaluation：准确率 / 漏报率 / 误报率 / 证据完整性 /
    建议可执行性 / 工具验证率 / 人工覆盖率 / 任务完成率

## 第五阶段：生成最终 System Prompt
只有在我确认 Agent Specification 后，才生成。必须：
可直接复制使用 · 明确角色和任务目标 · 明确职责边界 · 明确禁止行为 ·
明确工具使用顺序 · 明确验证要求 · 明确信息不足时不得猜测 ·
明确人工审批条件 · 明确与其他 Agent 的交接规则 · 明确输出 Schema ·
避免空泛描述 · 不使用「你是一名世界顶级专家」之类没有执行意义的语句。

## 第六阶段：测试专家 Agent
生成至少五个测试场景：
正常任务 / 信息不足 / 超出职责范围 / 高风险操作 /
多 Agent 职责冲突 / 工具执行失败 / 结论证据不足

每个测试场景必须包含：
测试输入 · 期望行为 · 不允许的行为 · 合格标准
```

### 12.4 生成完之后：找个 Agent 当审计员

```text
你是审计员。下面是一份专家 Agent 的规格和 System Prompt。

不要评价它写得好不好。只找四类具体问题，每类至少给一个可复现的场景：

1. 职责过宽：给出一个它会越界处理、但本该转交的具体请求。
2. 权限过大：给出一个它能执行、但按职责不该有权限的具体动作。
3. 缺少验证：给出一个它会只凭推理下结论、没有工具验证的具体场景。
4. 输出不稳定：给出一个会让它的输出无法被下游 Agent 解析的输入。

找不到就明确说找不到，不要替这份设计辩护。
```

| 这一句 | 为什么 |
|---|---|
| `不要评价它写得好不好` | 挡掉「整体设计合理，建议进一步完善」这种正确废话 |
| `只找四类具体问题` | 给它**有限且具体的检索目标** |
| `每类至少给一个可复现的场景` | ⭐ **场景才是证据。** 「权限可能过大」是意见，「它能对生产库执行 DELETE」是事实 |
| `找不到就明确说找不到` | 不给出口，它会硬编问题 —— 和拍 7 的唱反调 prompt 同一条 |

> 这就是拍 7 那个唱反调成员，换了个对象：**从审查一个结论，变成审查一个 Agent 设计。**
>
> 同一条纪律再说一遍：**「审计一下」是态度，「找一个它会越权的具体动作」才是任务。**

### 12.5 这套方法和今天这节课的四个接口

| 访谈法里的 | 就是今天的 |
|---|---|
| **规格先于 Prompt** | **charter 先于开跑**（拍 5）—— 临场判断的人恰恰最没资格判断 |
| **第三阶段风险检查那 10 条** | **全是交界问题**（拍 3 立论）：职责重叠、权限超职责、输出没人消费 —— 每条单看都合理，合起来才出事。`「A 没问题」+「B 没问题」≠ 真相` |
| **让另一个 Agent 当审计员** | **拍 7 的唱反调成员** —— 而且必须给检索目标，不能只说「批判性地看看」 |
| **「不要只询问抽象的风格或角色定位」** | **L7 的 `tools` 那一行** —— 人设不是边界，权限才是 |

**所以这一节不是新东西，是把今天学的四条判断用到「设计 Agent」这件事上。** 你今天查了一个 bug，用的是同一套结构。
