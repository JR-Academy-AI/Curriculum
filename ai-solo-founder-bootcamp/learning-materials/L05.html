让第一位 AI 员工安全上岗，并交出一次可检查的工作

这一节不比谁安装的 Agent 多，也不把“配置了五条 Schedule”当成完成。你的目标是：根据真实任务选一条可行路线，给一个 Agent 写清工作说明书，只授予完成任务所需的最小权限，先让一到两条排程真实运行，再通过人工检查、失败测试、审计和撤权决定它能否安全重复。

Agent 和普通聊天的区别不是回答更长，而是它可以读取输入、调用工具、在指定时间运行并把结果送到某处。能力增加的同时，误发邮件、读取过多数据、超额消耗、时区错误和无人审查的风险也一起增加。因此，本节的顺序固定为：任务 → 路线 → 权限 → JD → 手动运行 → 失败测试 → 排程 → 审查 → 决定是否重复。

本节学习路径

  1. 先定任务：从 Business SoT 取一个与客户研究相关、低风险、可重复的小任务。
  2. 再选路线：比较运行位置、所需工具、数据边界、排程机制和维护能力，不按热度选。
  3. 限制权限：默认不给；每增加一项权限，都写明用途、范围、期限、审计和撤销方法。
  4. 写 Agent JD：明确使命、输入、允许工具、禁区、交付物、review owner、触发条件、成本上限和停止条件。
  5. 先手动运行：用脱敏数据跑一次，检查原始来源、格式、边界和错误。
  6. 故意让它失败：测试来源不可用、输入为空、达到成本上限或遇到越权要求时是否会停。
  7. 只开一到两条 Schedule：确认本机或云端运行条件、睡眠状态和澳洲时区。
  8. 留审计并撤权演练：能回答它何时运行、读了什么、写了什么、花了多少、怎样暂停和撤销。

四、排程不是一句“每天七点”：先弄清谁负责把它叫醒

每条 Schedule 都有两个不同问题：何时应运行，以及到点时哪个进程仍然活着。本机排程依赖电脑、电源、网络、应用、daemon 或会话状态；云端排程依赖账户资格、托管环境、连接器、用量和服务可用性。把两者混在一起，就会出现“表达式没错，但电脑睡着所以没跑”。

运行形态睡眠／关机后的预期本节必须验证
本机应用或当前会话通常依赖设备和应用／会话存活；以当前官方说明为准合盖或睡眠测试、重启后状态、网络断开后的表现
本机 Gateway／daemon设备关机不会运行；睡眠是否运行取决于系统和配置服务状态、开机自启、日志、重启恢复、重复执行保护
托管云端 routine／automation不依赖个人笔记本，但依赖托管账户与环境仓库和连接器范围、时区、用量上限、失败记录、暂停入口
外部云调度器由外部服务运行凭证存储、费用、重试、审计和供应商退出方案

时区与夏令时

澳洲多个城市存在不同时区，部分地区有夏令时。不要只写“UTC+10”，也不要假设悉尼、布里斯班和珀斯永远同一时间。优先使用平台支持的 IANA 时区，例如 Australia/Sydney、Australia/Brisbane 或 Australia/Perth；然后在界面或日志中确认下一次运行的完整日期、时间和时区。若平台只接受 UTC，保存换算依据，并在夏令时切换前设置复查提醒。

五、课堂模拟：从危险自动化缩成安全的第一项任务

以下为课堂模拟／合成场景，不代表真实公司、客户、访谈或商业成绩。

模拟案例 A：一上来就自动触达客户

创始人要求 Agent 每天搜索潜在客户、猜测邮箱、写个性化信息并自动发送五十封。这个任务同时包含身份冒用、关系虚构、隐私、反垃圾邮件、发送错误和声誉风险，且无法在无人审查时安全回滚。本节应拒绝自动发送，把任务缩成：根据创始人亲自确认的五位真实对象，为每人生成一封透明访谈邀请草稿；创始人检查关系描述、对象身份和内容后，自己决定是否发送。

即使缩小后，这仍不是最适合作为第一条无人值守 Schedule 的任务，因为外部触达需要逐条判断。它应保持手动触发。

模拟案例 B：客户研究证据助理

一位创始人的 Business SoT 假设，小型物业管理机构会为减少维修报修的来回追问而行动。Agent 的第一项任务不是扮演五位物业经理，而是每周检查三到五个公开、预先批准的替代方案页面，记录功能、定位或价格页面是否出现变化，并把原文与推断分开。

输入Business SoT 非敏感摘要、固定公开 URL 列表、上次快照
输出变化／未变化／页面不可访问；每条附原始 URL、访问日期、原文依据、推断和 unknown
权限公开网页读取 + 指定本地目录写入；不接邮箱、客户库或支付
人工检查创始人打开至少一个原始链接，确认 Agent 没把营销文案写成客户效果
停止条件来源要求登录、出现个人信息、页面结构改变导致提取异常、成本触顶或连续两次失败
对客户研究的价值帮助访谈时询问客户现有替代，不构成客户痛点或购买意愿证据

这项任务低风险、可重复、可回查，并直接为真人访谈提供更具体的问题。它仍不能证明需求。Agent 发现竞品新增一个功能，只说明页面发生变化；客户是否使用、为何使用、是否付费，必须向真人核实。

六、第一条任务的完整验收协议

步骤 1：先手动触发

不要创建完 Schedule 就等待明天。用与未来排程相同的 prompt、输入、权限和输出路径点击“Run now”或执行当前官方文档提供的手动运行命令。记录开始时间、结束时间、运行环境和实际费用；费用看不到就写 unavailable。

步骤 2：逐项检查交付物

  • 是否只读取了白名单输入？
  • 是否按 JD 的字段和长度输出？
  • 每条事实能否点回原始来源？
  • 事实、Agent 推断和 unknown 是否分开？
  • 是否越过“不发送、不购买、不承诺、不处理敏感数据”的禁区？
  • 输出是否写到预定位置，而不是散落到未知频道？

步骤 3：至少做一次失败测试

成功运行只能证明 happy path。选择一个无破坏性的失败条件：把其中一个测试 URL 换成不存在的页面、提供一个空输入文件、暂时移除测试目录写权限，或设置一个极小的测试长度上限。合格行为是停止、标记失败并通知人；不合格行为是编造内容、静默跳过、改写别处或无限重试。

步骤 4：检查审计

你应能回答：任务由谁创建；什么时候触发；使用了哪个版本的 JD；读取和写入了哪些资源；运行结果是 completed、failed 还是 unknown；花费是否可见；谁检查并批准重复。只有输出截图而没有运行记录、输入引用和人工 review，不足以支持可重复运行。

步骤 5：暂停、撤权、再恢复

先暂停 Schedule，确认下一次运行不再排队；撤销一个测试连接器或目录权限，确认 Agent 无法继续访问；再按权限登记表恢复最小范围。撤权不是“以后出事再学”的动作，而是上线前必须演练的退出机制。

七、只启用一到两条真正可验的 Schedule

第一条建议使用上述“客户研究证据助理”。第二条只有在第一条已通过手动运行、失败测试和审查后才启用，可选择一份只读取 Founder Workspace 指定文件的周总结。SEO、财务、Git 日报等任务应等到你真正拥有对应数据和审批流程时再开，不为了凑数提前接入。

候选任务现在是否适合原因
公开替代方案变化记录适合低权限、可回查、直接支持真人访谈准备
Founder Workspace 周总结条件适合只读指定目录，不对外发送；需要已有一周真实记录
SEO 周报通常稍后没有网站和 Search Console 数据时，配置只是空壳
财务月报稍后涉及支付和会计数据，需要专门权限、审计和人工复核
Git 日报按需只有存在真实 repo 和稳定开发节奏时才有输入
自动发送客户邀约本节禁止外部承诺与声誉风险，应由本人审查并发送

一条 Schedule 的完成定义：配置已保存；手动运行成功；至少一个失败场景被测试；自动触发真实发生；交付物被人检查；日志可查；撤权已演练；创始人明确批准是否继续。仅有 cron 表达式、设置页面或“已创建”的截图，仍然只是草稿。

十、证据状态：自动化存在不等于工作完成

  • drafted：路线决策、Agent JD、权限表或 Schedule 已创建，但尚未发生真实运行。
  • executed：至少一项低风险真实任务已用脱敏数据运行，并在 AUTOMATION-LOG.md 留下输入、输出和检查记录。
  • verified：学生检查了输出，纠正至少一处错误或明确记录“未发现错误”的检查范围；失败测试、自动触发、审计和撤权可查，并由规定 reviewer 接受安全重复计划。

设置页面截图、AI 生成的成功截图、私有本地草稿、同学说“很酷”或学生声称“省了很多时间”都不是 verified 证据。可接受的材料包括带日期的运行日志、脱敏输入引用、可检查输出、原始来源、人工纠错记录、暂停／撤权记录和讲师 review。保存证据引用，不保存不必要的客户姓名、联系方式、付款标识、税号、身份文件、合同或健康信息。

十一、本节完成标准

  1. Business SoT 已存在，第一位 Agent 的任务明确支持其中一个待验证决策。
  2. 路线选择记录了运行环境、官方核实日期、未知能力、成本上限和降级方案；没有使用过时价格硬断言。
  3. AGENT-TEAM.md 不超过三个角色，当前只启用一个真正有任务的角色。
  4. Agent JD 包含使命、输入、允许工具、禁止动作、输出、review owner、trigger、cost ceiling 和 stop condition。
  5. 权限登记表写明用途、资源范围、动作、期限、审计和撤销；未授予无关邮箱、客户、财务或身份数据权限。
  6. 至少一项与客户研究相关的低风险真实任务已手动运行，所有输入都公开或脱敏。
  7. 本人检查至少一个原始来源，并保留 AI 原错误、修正指令和重跑结果；若未发现错误，记录检查范围。
  8. 至少一次无破坏性的失败测试通过；Agent 没有编造结果、静默越权或无限重试。
  9. 启用一到两条真正需要的 Schedule；每条都确认运行位置、IANA 时区、睡眠条件和下一次运行时间。
  10. 至少一条 Schedule 已发生一次真实自动触发，不只是手动触发或配置截图。
  11. 审计记录能回答何时运行、读写什么、结果状态、成本可见性和谁批准重复。
  12. 暂停和撤权演练已完成；恢复后仍保持最小权限。
  13. AUTOMATION-LOG.md 已更新，并明确决定 pause、revise 或 repeat。
  14. 列出五位真实可接触对象和本人要执行的访谈邀请动作；Agent 没有模拟访谈、客户承诺或购买意愿。
