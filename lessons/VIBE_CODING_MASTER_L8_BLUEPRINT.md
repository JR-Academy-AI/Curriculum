# Vibe Coding 大师课 · 第八节蓝图

> 状态：DRAFT 1.0（2026-08-09 · 从零重写）
> 主题：**Agent Team —— 从“多开 context”到“共同完成任务”**
> 课型：**120 分钟先讲后做工作坊**
> 课堂硬产物：每位学员或每两人一组，亲手创建并验证一个真正的 Agent Team。
> 本文只定义课程。Deck、`RUNSHEET.md` 与 `HANDOUT.md` 必须以本文为唯一事实源重新生成，旧版拍次、旧版双实验与旧版角色编号全部作废。

## 0. 重写决定

旧蓝图采用“先撞墙、再解释”和浅题/深题双线。它造成了四个问题：

1. 学员还没建立 Agent Team 心智，就被要求同时管理角色文件、三个会话、任务板、消息协议和两条根因线。
2. `C` 在 config 与唱反调之间换身份，角色、任务板和讲稿无法保持一致。
3. 课堂把“发现某个预设答案”当成成功，反而弱化了真正应学会的结构和设置。
4. 大量概念靠课后解释，学员做的时候不知道自己在观察什么。

新蓝图完全放弃旧顺序，采用两幕结构：

```text
第一幕 · 先讲（0–50 分钟）
定义 → 判断 → 最小单位 → 必要设置 → 角色与任务 → 通信 → Lead 验收

过渡（50–60 分钟）
老师 smoke test → 休息

第二幕 · 后做（60–113 分钟）
环境预检 → 建最小 Team → 验证 Team → 扩成标准组合 → 跑完整案例 → Lead 收口

结尾（113–120 分钟）
组合选择 → Exit ticket → 作业
```

本节不靠“隐藏答案”制造戏剧性。先把尺子讲清楚，再要求学员用尺子做出一个可验收的 Team。

## 1. 课程定位

### 1.1 承接 L7

L7 已经回答第一问：

> **这件事值得开一个新的 context 吗？**

L8 回答第二问：

> **这些 context 在完成前，需要互相改变对方的下一步吗？**

这句话是本节的判断核心。

```text
只需分头做，最后回给中心
→ Subagent

成员的中途发现会改变另一名成员的搜索、假设、实现或验收
→ Agent Team
```

Agent Team 不是 Subagent 的升级版，也不是 Agent 越多越强。它只是把“成员之间的持续协调”变成一等能力。

### 1.2 全节立论

> **Agent Team 的价值，不是多开几个 Agent；是让一名成员的新证据，在任务结束前改变另一名成员的下一步。**

如果禁止成员直接通信，任务仍能以同样顺序、同样质量完成，就不该开 Team。

### 1.3 一条必须讲清的诚实边界

Agent Team 并不会让某个结论“在结构上只有 Team 才能发现”。一个优秀的 Lead 也可以手动收集并转发证据。

Team 真正提供的是：

- 成员拥有独立 context；
- 成员能直接互发消息；
- 全队共享任务状态；
- 发现、阻塞与任务重分配可以在工作过程中发生；
- Lead 不必充当每一条信息的人工中转站。

因此选择 Team 是收益与协调成本的比较，不是能力等级判断。

### 1.4 老师必须抓住的十个要点

1. **先判断任务，再选择结构。** 人多、文件多、任务大，都不自动等于需要 Team。
2. **唯一关键判断是中途依赖。** 一名成员的新证据必须在任务结束前改变另一名成员的下一步。
3. **本课的最小可用单位是 Lead + 2 teammates。** Lead + 1 无法证明成员间协作。
4. **最低产品设置很少。** 启用实验能力、账号可用、项目可读、权限明确、`in-process` 可运行即可起步。
5. **成员名单和共享任务不是充分证据。** 必须出现一次 teammate → teammate 的直接消息。
6. **消息必须带证据和影响。** 不只说“我发现了 X”，还要说证据在哪里、希望谁改变什么。
7. **角色按责任边界设计，创建后不换身份。** 新需要出现时新增或结束角色，不把原角色改名换岗。
8. **Lead 管结果，不抢成员工作。** Lead 负责拆分、看依赖、裁决冲突和独立验收。
9. **先只读，再讨论多人写入。** 一旦允许写代码，必须增加文件所有权、集成顺序和回滚方式。
10. **Team 是一种有成本的拓扑。** 没有真实互相影响时，降级为单 Agent 或 Subagents 才是正确答案。

### 1.5 最容易出错的六类地方

| 类型 | 容易错在哪里 | 当场纠正 |
|---|---|---|
| 结构判断 | 把“可以并行”误当“需要 Team”；Lead + 1 也算过关 | 删除成员间消息再问：质量会不会下降？不会就降级 |
| 产品设置 | 忘开实验能力；把 `tools` 当目录沙箱；以为分屏、MCP、Hooks 是必需 | 先跑四步 smoke test；把必要项和体验增强分开 |
| 协作过程 | 成员各做各的；角色漂移；消息无证据；Lead 抢活 | 固定 owner，写通信触发器，用消息模板，Lead 只补缺口 |
| 验收 | 把全员同意、任务 `completed` 或找到根因当作完成 | Lead 用独立命令、输入或文件证据做外部验收 |
| 写入安全 | 多名成员改同一文件，最后才发现冲突 | 默认只读；写入前先划文件所有权和集成顺序 |
| 教学节奏 | 学员还没理解结构就开做；投屏自动揭晓答案 | 0–55 分钟先讲和演示；实践页只显示动作与完成判据 |

## 2. 学员起点与课堂门槛

### 2.1 学员应已具备

- 完成 L7，知道 Subagent 是独立 context。
- 会写最基本的任务 brief：目标、范围、产出、证据和停止条件。
- 知道 Agent 自述“完成”不等于外部验收完成。
- 已 clone 老师锁定 commit 的课堂仓库。
- 会在项目目录启动编码 Agent，并能打开项目设置文件。

### 2.2 本节的真实门槛

本节过关要求是“亲手做出真正的 Team”，所以以下能力必须在课前确认：

| 必须项 | 课前判断 | 不满足时怎么处理 |
|---|---|---|
| 当前工具支持 Agent Team | 能创建 Lead 与 teammate | 进入课前补环境，不在正课现场安装 |
| 当前账号可用该能力 | 实际创建一次 smoke-test team | 改用老师提供的共享实验环境 |
| 协作能力已启用 | 能看到成员名单与共享任务 | 课前按 §6.1 完成设置 |
| 项目可读取 | teammate 能读锁定仓库 | 修复路径、权限或 clone 问题 |
| 至少能使用 in-process 模式 | 单终端能切换成员并发消息 | 不要求 tmux 或分屏 |
| 课堂网络与登录可用 | 预检通过 | 准备已登录的备用实验机 |

**手动开三个聊天窗口不算完成本节。** 手动模拟只用于解释通信拓扑或救教学节奏，不能替代最终过关证据。

### 2.3 分组方式

默认每人独立完成。机器、账号或 token 条件不足时，两人一组：

- 一人操作；
- 一人按验收卡记录成员、任务、消息与决定；
- 10 分钟后交换操作权。

两人一组仍必须由学员亲手输入创建指令、发送成员消息并完成 Lead 验收。

## 3. 学习目标

课程结束后，学员能够：

1. 用一句话区分 Subagent 与 Agent Team。
2. 用三问判断一个任务是否值得开 Team。
3. 配好 Agent Team 的最低必要设置，并知道哪些设置只是体验增强。
4. 创建一个最小可用 Team，而不是把多个 Subagent 误认成 Team。
5. 证明成员名单、共享任务和成员间直接消息都真实存在。
6. 写一份最小 Team charter：目标、角色、所有权、通信触发器、完成判据。
7. 设计稳定、不漂移的成员角色。
8. 使用 `DISCOVERY / CONFLICT / DECISION` 三类关键消息。
9. 区分成员共识与外部验收。
10. 根据任务形状选择 Lead + 2、Lead + 3 或不用 Team。
11. 知道可以扩展哪些能力，以及何时不要扩展。

### 3.1 过关证据

学员离场前必须提交：

- 一张成员名单截图或等价记录：至少 1 Lead + 2 teammates。
- 一张共享任务列表截图或等价记录：至少一个任务经历 `pending → in progress → completed`。
- 一次 teammate A → teammate B 的直接消息，以及 B 因此改变下一步的证据。
- 一份 Team charter。
- 一条 `[CONFLICT]` 或明确说明本次为什么没有冲突。
- 一条 `[DECISION]`，包含决定、证据和下一责任人。
- 一次 Lead 外部验收记录。
- 一张结构选择卡：为什么这题值得或不值得使用 Team。

缺少成员间直接消息，视为没有证明 Team；只有 Lead 与成员往返，按 Subagent 处理。

## 4. 非目标

本节明确不做：

- 不重讲 L7 的完整 Subagent brief。
- 不同时讲两套故障案例。
- 不让角色在课中换身份。
- 不把模型数量、token 消耗或“全员最强模型”当学习成果。
- 不教 SDK 或自建编排框架。
- 不让多个成员并行修改同一个文件。
- 不以 `--dangerously-skip-permissions` 作为课堂捷径。
- 不要求所有人安装 tmux、iTerm2 分屏或额外 MCP。
- 不把手动多会话模拟包装成真正的 Agent Team。
- 不要求学员在课堂修复仓库 bug；课堂目标是建立 Team、协作调查和验收结论。

## 5. 选择 Team 的三问

### 第一问：值得开多个 context 吗？

这是 L7 的门：

- 搜索或调查会产生大量中间噪音；
- 有两个以上可独立推进的工作流；
- 需要独立证据视角。

如果第一问为否，直接用单 Agent。

### 第二问：成员的中途信息会改变别人的下一步吗？

命中以下任一情况，才进入 Team 候选：

- A 的证据会让 B 改搜索方向；
- A 与 B 的接口或计划需要多轮协商；
- 两个假设竞争，需要成员互相寻找反证；
- 任务有依赖，前序结果会改变后序任务定义；
- 需要持续同步阻塞、风险或所有权变化。

如果所有成员只需各自完成、最后统一回报，用 Subagent。

### 第三问：协调收益大于协调成本吗？

Team 会增加：

- 每个 teammate 的独立 context 成本；
- 任务拆分与状态维护；
- 消息阅读与转发；
- 冲突处理；
- Lead 验收时间；
- 共享 workspace 下的写入风险。

标准判断句：

> **如果我删掉成员间消息，任务会在哪一步变慢、变差或失去可验证性？**

答不出来，不开 Team。

## 6. 必须设置、可选设置与验证动作

### 6.1 当前课堂实现的最低必要设置

本蓝图以 Claude Code Agent Teams 为当前映射。该能力目前是实验性能力，默认关闭。课前在用户或项目设置中启用：

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

最低要求只有：

1. 功能已启用并对当前账号可用；
2. 项目目录可读；
3. 至少使用默认或 `in-process` 显示模式；
4. Lead 与 teammates 使用安全、明确的权限模式；
5. 课堂任务默认只读。

`teammateMode`、tmux、分屏、角色文件、skills、MCP、Hooks、不同模型都不是创建第一个 Team 的必要条件。

### 6.2 第一个 Team 的验证动作

创建后不要立刻跑正式任务，先做四步 smoke test：

1. **看成员名单**：Lead 之外至少有两名 teammate，名字与指令一致。
2. **看共享任务**：创建一条任务，由某名 teammate 认领并改变状态。
3. **发直接消息**：A 发给 B，B 的会话明确收到并回复。
4. **看 Lead 视角**：Lead 能看到任务状态，并收到需要抄送给 Lead 的结论。

只有 1、2、3 都通过，才进入正式 Lab。

### 6.3 权限设置

课堂默认只读：

- 成员可以读取、搜索和列文件；
- 不允许修改业务代码；
- 唯一可写产物是课堂记录或老师指定的交付文件；
- 不通过跳过权限检查解决弹窗问题。

需要写代码的课后扩展必须增加：

- 文件所有权；
- 写入不重叠规则；
- 集成顺序；
- 回滚方式；
- 独立测试与最终验收人。

### 6.4 关于角色文件的准确边界

角色文件是可选扩展，不是建 Team 的前提。

- `tools` 是工具 allowlist，可以限制成员能否写文件；它不是目录级沙箱。
- `Read, Grep, Glob` 能做出只读成员，但“只读 `frontend/`”仍是角色指令，不是物理路径限制。
- 为课堂一致性，文件名与 `name` 采用相同命名；这是课程约定，不是产品强制要求。
- 角色定义作为 teammate 使用时，`tools` 与 `model` 会生效，角色正文作为附加指令加入。
- 角色定义里的 `skills` 与 `mcpServers` 字段不会按 subagent 方式套用到 teammate；teammate 从项目与用户设置加载这些能力。
- 团队消息与任务管理能力由 Team 提供，即使角色的 `tools` 很窄也应可用。

### 6.5 可选体验设置

| 设置 | 什么时候加 | 什么时候不加 |
|---|---|---|
| `in-process` | 默认课堂路径，所有终端都能用 | — |
| tmux / iTerm2 分屏 | 老师投屏、需要同时观察多个成员 | 学员首次创建时 |
| 自定义角色文件 | 角色会复用、边界稳定 | 一次性 smoke test |
| 不同模型档位 | 角色判断密度明显不同 | 为了“看起来高级” |
| plan approval | 高风险实现、架构改动 | 只读调查 |
| Hooks 质量门 | 团队流程重复运行、需要强制验收 | 第一个 Team |
| MCP | 任务确实依赖外部系统 | 为了展示功能而连接 |
| Skill | 团队需要稳定领域流程 | 临时事实可以直接写入任务 |

## 7. 最小可用单位与组合阶梯

### 7.1 最小可用 Team

本课定义的最小可用单位：

```text
1 Lead
+ 2 teammates
+ 1 个共享任务
+ 1 次 teammate → teammate 直接消息
+ 1 次 Lead 决定与外部验收
```

为什么不是 Lead + 1：

- 只有一名 teammate，没有成员间通信；
- 协调仍是 Hub-and-spoke；
- 这更像一个长期一点的 Subagent，不足以证明 Team 的独特价值。

产品可能允许更小的形态，但“最小能学到协作结构的单位”必须有两名 teammates。

### 7.2 标准课堂单位

```text
Lead + 3 teammates

A · 边界一调查员
B · 边界二调查员
C · verifier / challenger
```

这是本节正式 Lab 的组合。A 与 B 交换跨边界证据；C 负责找反例和验收候选结论；Lead 负责拆分、决定和最终验收。

### 7.3 组合选择表

| 任务形状 | 推荐组合 | 原因 |
|---|---|---|
| 查一个定义、改一个常量 | 单 Agent | 没有多 context 强收益 |
| 两条独立调查，最后统一汇总 | Lead + 2 Subagents | 不需要成员中途互通 |
| 两个模块的证据必须互相解释 | Lead + 2 teammates | 最小跨边界 Team |
| 两个调查角色容易形成同一偏见 | Lead + 2 investigators + 1 challenger | 加入反证责任 |
| 设计方案有明显取舍 | Lead + 2 proposal owners + 1 critic | 竞争方案与证伪 |
| 前后端持续协商接口并分别实现 | Lead + frontend + backend + tester | 持续依赖与验收 |
| 三个 README 独立更新 | Subagents | 只是并行分工 |
| 多人会改同一文件 | 先重划所有权或不用 Team | 共享 workspace 风险过高 |
| 5 名以上成员 | 默认不用；先拆成两个阶段 | 协调成本和信息噪音迅速上升 |

### 7.4 可以扩展什么

从最小 Team 向上扩展时，固定按以下顺序：

```text
最小 Team
→ 稳定角色
→ 明确依赖与任务状态
→ challenger / verifier
→ 写入所有权
→ 模型与思考档位
→ plan approval
→ Hooks / MCP / Skills
```

不得倒着扩展。没有角色、消息与验收协议时，先加 MCP、模型和 Hooks 只会让错误更复杂。

## 8. Team 的操作协议

### 8.1 Team charter：开跑前必须写的五项

```markdown
# Team charter

## 1. Outcome
最终要回答或交付什么？

## 2. Members and ownership
- Lead：拆任务、处理冲突、最终验收
- A：范围 / 所有权 / 明确不碰什么
- B：范围 / 所有权 / 明确不碰什么
- C：反证或验收责任

## 3. Shared evidence contract
- 每条关键结论必须带：文件:行号 / 命令输出 / 可复现输入
- 证据不足时返回：无法判断 + 缺什么

## 4. Communication triggers
- 发现会改变别人方向的证据，立即点名发送
- 与别人结论冲突，发 [CONFLICT]
- 任务被阻塞，更新任务状态并说明需要谁提供什么

## 5. Done
- 哪些任务完成
- 哪些冲突已决定
- 哪个外部验收已执行
- 哪些范围未检查
```

### 8.2 角色设计原则

角色不是人格，是责任与边界。

一个合格角色必须回答：

1. 它拥有哪一块证据或决策？
2. 它明确不碰什么？
3. 什么发现必须发给谁？
4. 它用什么格式交证据？
5. 什么时候应该停止并报告阻塞？

禁止使用只有态度、没有动作的角色：

```text
坏：你是一个批判性思维专家。
好：针对候选根因，寻找至少一条“原因不存在但现象仍发生”的记录；找不到就明确返回找不到。
```

### 8.3 共享任务

任务必须小到能被一人认领，大到值得独立 context：

```text
坏：调查并解决所有历史记录问题。

好：
T1 追踪前端从邮箱输入到请求发出的字符串变化。
T2 追踪后端从登录邮箱到 user.id、token 和 history scope 的派生。
T3 对候选根因设计一组能证伪的具体输入，并核对证据链。
```

任务状态至少使用：

```text
pending → in progress → completed
                     ↘ blocked（缺什么、等谁）
```

### 8.4 三类关键消息

#### `[DISCOVERY]`

```text
[DISCOVERY] frontend → backend
observed: login 只做 trim，没有大小写归一
evidence: frontend/src/lib/authAdapter.ts:__
why_you_need_it: 你正在检查 email 如何派生 user.id
```

#### `[CONFLICT]`

```text
[CONFLICT]
claim_A: 同一个人的历史应落到同一个 user_id
claim_B: 大小写不同的邮箱会派生不同 user_id
evidence_A: ______
evidence_B: ______
decider_needed: 用两个具体输入计算结果
```

#### `[DECISION]`

```text
[DECISION]
decision: ______
deciding_evidence: ______
owner_next: ______
verification: ______
```

`blocked` 是任务状态，不另造一套消息分类。阻塞时必须写清“缺什么、等谁”。

### 8.5 传证据，不只传结论

消息最少应包含：

- 观察到什么；
- 原始证据在哪；
- 为什么收件人需要知道；
- 是否要求对方改变任务或回答一个问题。

成员可以给出解释，但不能只发“我觉得根因是……”。对方必须能独立核对原始证据。

### 8.6 Lead 的四项责任

Lead 不是第四个调查员。Lead 的工作是：

1. **结构**：任务与所有权是否清楚；
2. **流动**：该互通的证据是否真的互通；
3. **决定**：冲突用什么判据裁决；
4. **验收**：结论是否有成员自述之外的证据。

Lead 只有在以下情况才下场调查：

- 两个成员的范围之间出现无人拥有的缺口；
- 某个冲突需要独立第三证据；
- 成员全部阻塞且任务无法重新分配。

### 8.7 什么时候给 Prompt 模板

Prompt 模板只放在五个容易因表达不完整而失败的动作上：

1. 创建最小 Team；
2. 增加 verifier；
3. 把工作拆成共享任务；
4. 成员发送 `DISCOVERY / CONFLICT`；
5. Lead 收敛为 `DECISION` 并执行外部验收。

三问判断、组合选择和失败模式不用 Prompt 模板。那些地方要学的是判断，不是复制指令。

所有模板遵循同一骨架：

```text
目标：最终回答或交付什么
角色：谁拥有什么，明确不碰什么
任务：可认领的工作与依赖
通信：何时必须直接发给谁
证据：文件:行号 / 命令输出 / 具体输入
停止：做到哪一步先停，等待谁验收
```

## 9. 正式 Lab：亲手做出并扩展一个 Team

### 9.1 Lab 目标

学员先创建最小 Team，再把它扩成标准 Team，完成一个跨前后端的只读调查。

课堂仓库：`star-mansions`，必须锁定 commit，不允许依赖课前一天的 `main`。

用户症状：

> 同一个人使用“看起来相同”的邮箱登录，有时历史记录为空；重新登录后有时又出现。没有报错。

最终问题：

> 从邮箱输入到 history 查询，哪一段字符串或身份派生会使同一个人落入不同的数据作用域？

### 9.2 第一步：创建最小 Team

先只创建两名 teammates：

```text
A · frontend-trace
B · backend-identity
```

给 Lead 的创建 Prompt：

```text
为“邮箱身份与 history scope 的只读调查”创建一个 Agent Team。

成员：
- frontend-trace：只读追踪 frontend 中邮箱从输入、登录到请求发出的字符串变化。
- backend-identity：只读追踪 backend 中邮箱如何派生 user.id、token，以及 history 如何按身份过滤。

创建一条共享任务：确认 Team 通信可用。
让 frontend-trace 认领任务，但先不要开始正式调查。
成员必须使用以上固定名字，不得修改业务代码。

创建完成后停止，只报告：
1. 成员名单；
2. 共享任务及 owner；
3. 当前权限模式。
```

创建后立刻完成 §6.2 smoke test。

### 9.3 第二步：扩成标准 Team

最小 Team 验证通过后，增加第三名：

```text
C · verifier
```

它的任务固定为：

> 不重复完整调查。接收 A、B 的候选证据；用具体输入找反例；检查结论是否能解释症状；输出可复现步骤和未检查范围。

给 Lead 的扩展 Prompt：

```text
最小 Team 的成员、共享任务和 A→B 消息已经通过 smoke test。

现在新增 teammate：verifier。
它只负责接收 frontend-trace 与 backend-identity 的候选证据，
用具体输入寻找反例，检查候选结论能否解释用户症状。
它不得重复两人的完整搜索，也不得修改代码。

创建后先不要调查。把 verifier 写入 Team charter，并报告新的成员名单。
```

角色从创建到结束不更名、不换身份：

| 成员 | 固定所有权 | 必须发出的消息 |
|---|---|---|
| A · frontend-trace | 前端字符串变化 | 任何“被改变 / 未被改变”的观测发给 B，并抄送 Lead |
| B · backend-identity | 身份派生与 history scope | 任何会产生不同 user_id 的条件发给 A、C，并抄送 Lead |
| C · verifier | 反例、复现与证据链 | 发现证据缺口或无法解释的现象，发 `[CONFLICT]` 给相关成员与 Lead |
| Lead | 任务、冲突、决定、验收 | 不替成员先给根因 |

### 9.4 第三步：分配共享任务

```text
T1 · A · 追踪邮箱从输入到请求发出，列出每一步字符串处理和证据。
T2 · B · 追踪邮箱到 user.id / token / history scope，列出每一步和证据。
T3 · C · 等待 A、B 的候选证据；设计具体输入验证“同一个人是否可能得到不同作用域”。
T4 · Lead · 收集 conflict，做最终决定与外部验收。
```

依赖关系：

```text
T1 ─┐
    ├→ T3 → T4
T2 ─┘
```

C 不应在没有 A、B 证据时自行猜根因。它可以准备验证方法，但必须基于实际证据执行。

给 Lead 的任务拆分 Prompt：

```text
按 T1–T4 创建共享任务，并设置 T3 依赖 T1、T2，T4 依赖 T3。
每个任务只能有一个 owner。
每项完成时必须附文件:行号、命令输出或具体输入；没有证据不得标 completed。
分配完成后停止，先展示任务、owner、依赖和当前状态。
```

### 9.5 第四步：触发一次真实的成员间改变

预期的关键协作事件：

1. A 发现前端只做某种字符串处理，未做另一种归一；
2. A 把原始证据发送给 B；
3. B 因为这条消息，使用两个具体输入重新检查身份派生；
4. B 把差异发送给 C；
5. C 形成复现步骤或寻找反例；
6. Lead 根据完整证据链决定并验收。

课堂验收关注的是第 2–5 步是否真实发生，不是要求 Agent 使用某句固定措辞。

如果 B 在收到 A 消息前已独立找到完整答案，Lead 仍要让 A 发送证据，并要求 B 明确回答：

> 这条证据是否改变、缩短或加强了你原来的调查？如果没有，为什么？

允许答案是“没有改变”。真实协作记录比强行制造翻转更重要。

在 `frontend-trace` 会话中使用的消息 Prompt：

```text
把你最关键的一条前端观测直接发给 backend-identity，不经 Lead 转述。
使用 [DISCOVERY] 模板，必须包含 observed、evidence、why_you_need_it，
并明确请对方说明这条证据是否改变、缩短或加强了下一步。
同时抄送 Lead，但不要替 backend-identity 得出结论。
```

### 9.6 第五步：Lead 验收

Lead 必须执行：

1. 核对 A、B 给出的文件与行号；
2. 使用两个只在大小写或空白上不同的具体输入，检查身份派生结果；
3. 检查候选根因是否能解释“无报错但列表为空”；
4. 记录无法解释的现象；
5. 输出 `[DECISION]`。

给 Lead 的收敛与验收 Prompt：

```text
不要采用多数意见，也不要把 completed 当作验收。

先列出 A、B、C 的关键 claim 与原始证据；
再指出冲突或证据缺口；
使用两个只在大小写或空白上不同的具体输入做独立核对；
最后输出：

[DECISION]
decision: ...
deciding_evidence: ...
owner_next: ...
verification: ...
unchecked_scope: ...

如果现有证据不足，决定必须是“无法判断”，并写明缺什么。
```

课堂不修代码。修复建议可以记录，但不进入完成判据。

### 9.7 Lab 完成判据

必须同时满足：

- [ ] Team 成员名单真实存在；
- [ ] 至少两名 teammates；
- [ ] 共享任务状态发生过变化；
- [ ] 至少一次 teammate → teammate 直接消息；
- [ ] 至少一名成员因消息改变、缩短或加强了下一步，或明确证明没有改变；
- [ ] 结论含可核对证据；
- [ ] Lead 执行外部验收；
- [ ] 标出未检查范围。

只找到根因但没有协作证据，Lab 不完整；有漂亮消息但没有外部验收，也不完整。

## 10. 120 分钟流程

| 时间 | 阶段 | 教学方式 | 产物 |
|---|---|---|---|
| 0–5 | 开场与课程合同 | 讲 | 知道今天必须亲手建 Team |
| 5–15 | L7 → L8：两种拓扑 | 讲 | 一句话区分 Subagent / Team |
| 15–25 | 选择 Team 的三问 | 讲 + 快速判断 | 结构选择卡 |
| 25–34 | 必须设置与最小单位 | 讲 + 老师投屏 | 设置清单 + MVP 图 |
| 34–42 | Charter、角色与共享任务 | 讲 | Charter 模板 |
| 42–50 | 消息协议、Lead 与失败模式 | 讲 | 三类消息 + Lead 四责 |
| 50–55 | 老师演示 smoke test | 看 | 看到真正 Team 的证明 |
| 55–60 | 休息 | — | — |
| 60–70 | 学员创建最小 Team | 做 | Lead + A + B |
| 70–76 | Smoke test | 做 | 名单、任务、A→B 消息 |
| 76–84 | 扩成标准 Team + 写 Charter | 做 | 增加 C verifier |
| 84–99 | 三成员调查 | 做 | T1/T2/T3 证据 |
| 99–107 | Conflict 与验证 | 做 | CONFLICT + 具体输入 |
| 107–113 | Lead 决定与外部验收 | 做 | DECISION + 验收记录 |
| 113–117 | 组合重构 | 讲评 + 判断 | 何时 Lead+2 / Lead+3 / 不用 Team |
| 117–120 | Exit ticket + 作业 | 写 | 过关结果 |

### 10.1 节奏铁律

1. 0–55 分钟不让学员创建 Team；先把结构、设置和验收讲完。
2. 60 分钟后不再插入新的大概念；老师只按已讲框架纠偏。
3. 最小 Team 验证不过，不进入正式 Lab。
4. 不以“找到根因”替代“证明 Team 真实协作”。
5. 时间不足时，砍组合重构与部分讲评，不砍最小 Team、直接消息和 Lead 验收。

## 11. 各阶段教学细节

### 11.1 开场：今天不是看老师开 Team

老师第一句话：

> 今天的完成标准不是“看过 Agent Team”，是你自己创建一支、让两个成员互发一条会改变工作的消息，并由 Lead 验收结果。

投屏过关证据，不展示最终案例答案。

### 11.2 拓扑讲解

```text
Subagent
                 ┌→ A → 回报 ┐
Lead / Hub ──────├→ B → 回报 ├→ Lead 汇总
                 └→ C → 回报 ┘
成员之间不需要直接连线

Agent Team
                 A ↔ B
                  ↘ ↙
                   C
                   ↕
                  Lead
          + shared task list
```

不要说“Team 更高级”。只强调：Team 多了成员间通信和共享协调，因此门槛更高。

### 11.3 三问判断练习

先讲三问，再给 6 张任务卡判断：

1. 查一个常量定义在哪个文件。
2. 三个模块分别更新 README。
3. 前后端持续协商接口并分别实现。
4. 两名调查员验证两个互斥根因，并交换反证。
5. 一个 Agent 写方案，另一个按固定清单验收最终文档。
6. 三名成员都会修改同一个核心文件。

学员必须给结构和理由：单 Agent / Subagent / Team / 先重拆。

### 11.4 最小单位讲法

从 Lead + 1 开始问：

> 只有一名 teammate，谁和谁直接协作？

答案：没有。于是推出课堂最小单位是 Lead + 2。

### 11.5 Smoke test 演示

老师创建一个一次性演示 Team，不读正式案例文件：

```text
创建两个 teammates：alpha 和 beta。
创建共享任务“确认团队通信可用”。
让 alpha 认领任务并给 beta 发消息：PING alpha-to-beta。
让 beta 收到后回复：PONG beta-to-alpha，并把任务标为 completed。
先不要做其他工作。
```

老师只展示四个证据：成员、任务、PING、PONG。演示结束立即清理，不让它污染正式 Lab。

### 11.6 学员操作时老师只检查四件事

- 成员名对不对；
- 任务是否真的共享；
- 消息是否真从 A 到 B；
- Lead 有没有提前下场抢调查。

老师不替学生给根因方向。

### 11.7 组合重构

完成 Lab 后，要求学员做三次删减：

1. 删掉 C，什么时候仍然成立？
2. 把 A、B 换成 Subagents，什么能力消失？
3. 把任务缩成一个函数查找，为什么整个 Team 都应该删掉？

让结构选择从刚完成的 Team 反向长出来。

## 12. Slide 蓝图（20 页）

### 12.1 Deck 性质

Deck 用于投屏与节奏控制，不是讲义。

- 每页只承担一个教学任务。
- 完整配置、Charter、prompt 和消息模板放 `HANDOUT.md`；deck 只显示必要片段。
- 讲授页可以完整呈现结论，因为本节明确先讲后做。
- 实践页只显示“现在做什么、完成判据、硬停时间”，不自动揭示案例答案。
- 禁止按时间自动出现答案；需要分步时使用讲师控制的点击阶段或拆页。
- 1600×900 画布下：主正文不小于 26px，代码与证据不小于 22px，辅助脚注不小于 16px。
- 不在一页同时放完整代码、解释表、prompt 和警告。

### 12.2 逐页表

| 页 | 标题 | 页面任务 | 阶段 |

## 13. 老师课前准备

### 13.1 硬要求

- [ ] 在课堂同版本工具上真实创建一次 Lead + 2 Team。
- [ ] 验证 feature flag、账号权限和计划可用性。
- [ ] 验证 in-process 模式，无 tmux 也能完成全部 Lab。
- [ ] 验证成员名单、共享任务和 A→B 消息的具体 UI 位置。
- [ ] 验证锁定 commit 的三个 Lab 角色都能在 15 分钟内获得足够证据。
- [ ] 把仓库 commit 写入投屏、讲义和群通知。
- [ ] 准备至少两台已登录备用实验机或远程实验环境。
- [ ] 准备 smoke-test 录屏，但录屏不能代替学员过关。
- [ ] 准备标准 Charter、标准消息记录和标准 Lead 验收记录。

### 13.2 仓库验收

不要只检查 `main`。对锁定 commit 执行：

- [ ] 前端存在可追踪的邮箱输入与登录调用链；
- [ ] 后端存在邮箱到身份与 history scope 的派生链；
- [ ] A 的证据可以被 B 消费；
- [ ] B 的结果可以被 C 用具体输入验证；
- [ ] 整题只读可完成；
- [ ] 标准答案含文件与行号；
- [ ] 即使 Agent 提前发现结论，仍有可观察的通信与验收动作。

如果代码发生变化，更新 fixture 或换 commit，不允许老师凭旧行号上课。

### 13.3 学员课前预检

课前 24 小时发一条 smoke-test 作业：

1. 启用 Agent Teams；
2. 创建 `alpha` 与 `beta`；
3. 截图成员名单；
4. 不要求完成正式任务。

未通过者参加 15 分钟课前补环境。正课不处理安装与账号问题。

## 14. 不同环境与降级路径

| 情况 | 课堂路径 | 是否算过关 |
|---|---|---|
| 功能可用，能分屏 | 现场 Team + 分屏观察 | 是 |
| 功能可用，不能分屏 | `in-process` 模式 | 是 |
| 功能可用，但学生机器性能不足 | 两人一组或备用实验机 | 是 |
| 账号/计划不支持 | 老师提供共享实验环境，学生本人操作 | 是 |
| 临时网络故障 | 先用讲义写 Charter；网络恢复后补真实 Team | 补完后才算 |
| 工具完全不支持 Team | 手动模拟理解协议；课后到可用环境补做 | 当堂不算 |
| 成员创建了但不能互发消息 | 按 Subagent 处理，修复设置后重建 | 否 |
| 只有 Lead + 1 teammate | 作为最小 Subagent 对照，不算最小 Team | 否 |

这张表必须在课前对助教公开，避免现场为了“让所有人过”而降低过关定义。

## 15. 高频失败模式

| 失败 | 识别信号 | 纠正动作 |
|---|---|---|
| 用 Subagent 冒充 Team | 只有 Lead↔成员，没有成员间消息 | 要求 A→B smoke test |
| 退化成分工 | 三人各做各的，最后一次性回报 | 在 Charter 写通信触发器 |
| 角色漂移 | frontend-trace 中途变 verifier | 新增成员，不修改原身份 |
| Lead 抢活 | Lead 自己搜完代码再告诉成员答案 | Lead 只处理缺口、冲突、验收 |
| 消息只有结论 | “根因是 X”，无原始证据 | 使用 DISCOVERY 模板 |
| 虚假共识 | 都同意，但无人找反例 | 增加 verifier/challenger |
| 任务过大 | 一个任务包含调查、实现、测试、部署 | 拆成可认领任务与依赖 |
| 任务过小 | 每个成员只查一行 | 降级为单 Agent |
| 所有人改同一文件 | 冲突、覆盖、无法集成 | 先重划所有权或不用 Team |
| 全员最强模型 | 成本高但判断工作很少 | 按角色判断密度选档 |
| completed 当验收 | 无外部命令、行号或复现 | Lead 执行独立验收 |

## 16. 评分与 Exit ticket

### 16.1 课堂评分（10 分）

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| Team 真实性 | 无 Team | 有成员但无 A→B 消息 | 名单、任务、A→B 全通过 |
| Charter | 无 | 有目标和角色 | 五项齐全且触发器明确 |
| 证据通信 | 只有结论 | 有证据但无消费者 | 证据改变/加强了别人下一步 |
| Lead 决定 | 默认采用共识 | 有决定无判据 | 有 deciding evidence 与 owner_next |
| 外部验收 | 无 | 只看成员自述 | Lead 独立核对并标缺口 |

过关线：8/10，且“Team 真实性”和“外部验收”不得为 0。

### 16.2 Exit ticket

1. 为什么 Lead + 1 不是本课的最小可用 Team？
2. 哪一项设置是当前工具创建 Agent Team 的必要项？
3. 什么时候 Lead + 2 足够，什么时候要加 verifier？
4. 如果删掉成员间消息，任务完全不受影响，应该换成什么结构？
5. Team 全部任务 completed，Lead 还缺哪一步？

五题至少四题正确；第 1、4、5 题必须正确。

## 20. 产品事实与数据纪律

### 20.1 当前官方事实

截至 2026-08-09，课堂需按当天版本再次验证：

- Agent Teams 是实验性能力，默认关闭。
- Team 由 Lead、独立 teammate sessions 与共享任务列表构成。
- teammates 可直接互发消息；广播需要逐个发送。
- teammate 不继承 Lead 的对话历史，但会加载项目环境与 spawn prompt。
- 可复用 subagent definition 创建 teammate；`tools`、`model` 与角色正文的应用方式见 §6.4。
- Team 共享工作副本，不自动提供工作树隔离。
- Agent Teams 消耗显著高于单会话，成员数增加会放大成本。

### 20.2 课堂数据纪律

- Deck 不出现具体模型名、价格或并发上限。
- feature flag 作为必要设置保留，因为不开就无法完成课堂目标。
- 产品 UI、快捷键和计划可用性写进 RUNSHEET 的“当天映射”，不写成永久原理。
- 角色文件与权限行为必须引用当天官方文档并真实测试。
- 仓库必须锁 commit，所有行号以锁定版本为准。
