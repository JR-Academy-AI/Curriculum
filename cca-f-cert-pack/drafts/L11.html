场景题机制：一段情境，一组判断

CCA-F 不考"背定义"，考的是"给你一个真实系统设计现场，你选哪个做法"。这类题叫场景题：题干先铺一段情境——某个 agent 系统在什么规模下、卡在什么问题上、有什么业务约束，然后让你在几个候选做法里挑。它和"单选事实题"的区别是：正确答案不止一个字面正确的，而是最贴合这段情境约束的那个（或那几个）。

关于形式，社区流传一个说法叫"6 抽 4"：社区口径，以官方公布为准——把它读成一道场景题给 6 个候选做法、要你选出其中 4 个正确项（多选）。这个数字 Anthropic 官方页面查不到出处，别拿它当计分硬规则去抠"少选一个扣几分"。你真正要练的能力是：面对一堆看着都沾边的选项，能稳定地分出"对且贴合" vs "对但不贴合" vs "根本错"。

为什么多选比单选难：单选题里错项往往有明显破绽，场景多选里的干扰项个个都写得"技术上说得通"。比如题干是高峰期延迟高，选项里"上多智能体编排"听起来更专业、更稳——但多 agent 约比单纯对话多用 15 倍 token（Anthropic 多 agent research 系统实测），在延迟/成本吃紧的场景里恰恰是反面答案。选项对不对，脱离约束根本判不了。所以场景题必须有一套固定流程，不能凭手感——闭卷、有监考、不许用 AI 辅助（Pearson VUE 承办、OnVUE 远程监考或线下考场），考场上没有查文档的机会，只能靠脑子里这套流程稳定复现。下面这套四步框架就是干这个的。

四步定位法：抓约束 → 判域 → 排雷 → 选最贴

下面这套流程叫四步定位法，四步的名字和动作后面 L12（六类场景实战）、L13（干扰项拆解）会直接引用，先把每一步的判断动作记死。

第一步「抓约束」——先圈出题干的硬约束

读题干时不看选项，先用笔圈出四类信号：规模（并发量、高峰、数据体量）、延迟（要不要实时、用户等得起几秒）、成本（token 预算、调用频次）、合规（涉钱/涉法/涉隐私/需人工背书）。约束决定一切——同一个技术方案，在"内部低频工具"里是对的，在"黑五高峰实时客服"里就是错的。抓不到约束，后面三步全废。经验：题干里每一个具体数字和形容词（"高峰""偶尔""绝对不能"）都是约束线索，不是废话。举个对照：题干写"给内部 10 人团队做份周报汇总"（低频、无实时、无风险）和写"给上万并发用户做实时下单助手"（高规模、低延迟、涉钱），哪怕问的是同一个 agent 结构，答案会朝相反方向走。所以约束是先于选项存在的尺子，别等看完选项再回头找。

第二步「判域」——把题归到五个域里的哪一个

判断这道题主要考哪个 domain，你就知道该调用哪套判据。五个域及其相对权重（社区口径，非官方，百分比不可引用；域名与排序可信度较高）：Agentic Architecture 约 27%、Claude Code Configuration 约 20%、Prompt Engineering 约 20%、Tool Design & MCP 约 18%、Context Management 约 15%。判域看题干关键词：出现"单/多 agent、coordinator、loop、升级人工"→ Agentic Architecture；"退款/转账必须 100% 不发生、hook、验证前置"→ 落到可靠性（属 Agentic Architecture 域）；"工具选哪个、MCP、参数 schema"→ Tool Design；"上下文塞不下、成本、裁剪历史"→ Context Management。判错域，你会拿错误的判据去套，直接选偏。一道题可能横跨两个域（比如多 agent 编排里夹一个退款可靠性问题），这时判"主域"是哪个——题干最终问你解决什么，就以那个域的判据为主、另一个为辅。别在次域的细节上纠结，那往往是出题人埋的烟雾。

第三步「排雷」——先删掉明显错误项

不要一上来找最优，先做减法，删掉三类雷：事实错误（"Claude 不支持多 agent"这种硬伤）、方向反了（用 PostToolUse 去"阻止"一笔转账——触发时钱已出，方向就错）、反模式（拿 content[0].type=="text" 判断任务完成、把 tool_choice 长期设 "any"、用迭代上限当正常终止信号）。这些在 L06/L07 都点过名，是干扰项的常客。除了这三类，还有一类"张冠李戴"的雷：拿别的域的正确做法来答这道题——比如题干考的是 Context Management（历史塞不下），却给你一个"改进 prompt 措辞"的 Prompt Engineering 选项，字面没错但答非所问，第二步判对域就能识破。排雷通常能砍掉一半选项，剩下的才值得细比。

第四步「选最贴」——在剩下的里选最贴合约束的

排完雷剩下的往往都"技术上正确"，这时唯一的裁判是第一步抓到的约束。逐个把候选项拿去对约束：这个方案在题干那个规模/延迟/成本/合规下，是不是最优解？多选题就选出所有"对且贴合"的。判不下来时问一句官方最爱的原则——"先用最简单能解决的方案，只有简单方案顶不住才加复杂度"（Anthropic《Building Effective Agents》原话：只在复杂度"能明确改善结果"时才加）。这句话是场景题的万能裁决器：两个方案都对，选更简单的那个，通常就是答案。

SCENARIO 带练：双语电商客服的多智能体改造

用四步定位法完整过一道 6 抽 4。

题干：你给墨尔本一家中英双语电商平台维护客服 agent，接的活有订单查询、库存问询、退款、投诉升级。当前是单 agent 版本，团队反馈两个问题：(1) 黑五高峰期延迟明显变高；(2) agent 偶尔把该转人工的激烈投诉自己回了，还编了套听着专业的说辞。下面 6 个改造项，选出应当采纳的 4 个。

  • A. 用 PreToolUse hook 匹配 process_refund 和 escalate_complaint 工具，退款超阈值或投诉命中升级条件时返回 permissionDecision: "deny"/"ask" 转人工
  • B. 订单查询、库存问询这类只读操作，保持单 agent 单轮处理，不拆多 agent
  • C. loop 用 stop_reason 驱动（tool_use 继续、end_turn 结束），另设一个迭代上限当防失控的 safety net
  • D. 退款前的身份验证做成 hook 层的前置 gate，而不是只在 system prompt 里写一句"记得先验证"
  • E. 把订单/库存/退款/投诉四条线全拆成 orchestrator-worker 多 agent 编排，"显得更稳更专业"
  • F. 在 system prompt 里加一句"遇到情绪激烈的投诉务必转人工"，就能解决 agent 乱回投诉的问题

第一步 抓约束

圈出来：延迟（黑五高峰，成本/延迟都吃紧）、合规/风险（退款涉钱、激烈投诉转人工是硬要求，"偶尔漏转"是当前 bug）、规模（高峰并发）。核心矛盾两条：高峰扛延迟成本 + 高风险动作必须 100% 走对。

第二步 判域

关键词"单/多 agent、升级人工、hook、loop 终止"——主域是 Agentic Architecture（含可靠性设计）。那就调用这套判据：由简入繁、高风险动作要确定性 gate、loop 靠 stop_reason。

第三步 排雷

删两个雷：

  • E 排除——高峰期约束下，把只读小任务也堆成多 agent 是反向操作。多 agent 约多用 15 倍 token，延迟和成本只会更糟；官方原则是简单方案够用就别加复杂度。"显得更专业"不是技术理由。
  • F 排除——这正是当前 bug 的根因。system prompt 是概率性的，能把遵守率推高但压不到 0 失败，"偶尔漏转"就是概率漏下来的那部分。对"必须转人工"这种硬要求，prompt 不合格。

第四步 选最贴

剩下 A、B、C、D，逐个对约束：

  • A ✅ 直击"漏转人工"——PreToolUse 在工具执行前触发，deny/ask 是代码级确定性 gate，模型绕不过，把"偶尔"压成"绝不"。
  • B ✅ 直击延迟/成本约束——只读操作单 agent 单轮最省，符合由简入繁。
  • C ✅ loop 正确终止靠 stop_reason，迭代上限只做防高峰失控的安全网，不喧宾夺主。
  • D ✅ 和 A 同源：身份验证是高风险前置，必须落到 hook 的确定性层，不能只靠 prompt。

答案：A、B、C、D。注意 F 和 D 讲的是同一件事（验证/转人工），但一个用 prompt 一个用 hook——场景题最爱这种"看似都对、实则一个概率一个确定"的成对干扰项，第三步排雷时靠"这是不是 100% 硬要求"一刀切开。这也是 L13 会重点拆的干扰项套路。

回看整套流程：真正定生死的是第一步抓到的约束（高峰 + 高风险）。约束一旦圈准，E（加复杂度）和 F（用概率手段扛硬要求）自己就露馅了。这就是四步定位法的价值——把"凭感觉选"换成"拿约束当尺子量"。
