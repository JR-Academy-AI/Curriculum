# 第二节课 Runsheet — ADLC + 产品思维 + PRD 工作坊：先看闭环，再定义需求

> **形态：动手工作坊（不是讲座）。** 先讲 **ADLC：今天怎么把产品做出来**，再把 **PRD 最终形态** 提前给学生看，让他们知道自己要产出什么；然后讲 **产品分析：怎么分析一个产品、Business Model 是什么、Business Logic 是什么**；最后学生写自己的 PRD，把整份 PRD 交给 agent 端到端开发。
> 每个学员拿第一节课作业里定的那个 AI 产品，**从自己的角度**：先理解 ADLC 闭环 → 看清 PRD 要长什么样 → 用产品分析把需求磨利 → 写自己产品的 PRD → 整份 PRD 交给一个 agent 端到端开发 → 跑起来 → 部署 → 看 feedback → 迭代。老师巡场带，每人做自己的。
> **为什么 ADLC 先讲**：先让学生知道「我们不是写一堆功能，而是要转完一圈产品开发闭环」。有了闭环，再回头讲需求定义，学生会更清楚 Product Thinking 为什么重要。
> **L1→L2 闭环**：L1 作业「想清楚你要做什么 AI 产品」→ L2「把它做出来」。
> **PRD 正式教学放本节**（在「写 PRD」那一步深讲，对齐 L1 的「PRD 留到下节」承诺）。
> **slide 少、引导多**：framework slide 见 §7，主体是下面的阶段引导 + 老师检查点。

---

## 0. 课前确认（开课前 5 分钟过一遍）

每个学员必须带着两样来，否则今天做不动：
1. **L1 作业**：一句话说清你要做的 AI 产品（解决你/你公司一个真问题的小东西）。没想好的 → 开场给 5 分钟现想（用 L1 的三问：哪件事最烦 / AI 替你干什么 / 一句话描述）。
2. **工具链装好**（L1 Quest 装的 Claude Code + Cursor + Codex）。没装的 → 配一个装好的同学结对，或老师课前 10 分钟兜底。

> ⚠️ 控范围红线：今天目标是**跑出一个能动、能访问的最小版本**，不是做完整产品。开场就把这句话钉死。

---

## 1. 开场 + ADLC 全景（~20min）

**回顾（念）**：「上节课你想清楚了要做什么 AI 产品。今晚我们不再讲概念，直接把它做出来。怎么做？走一套流程，叫 ADLC —— Agent Development Lifecycle。」

**讲清 ADLC 闭环**（配 §7 的闭环图）：
> 需求 → 写 PRD → 开发 → 部署 → 分析 feedback → 回到需求（持续迭代）。

**点破和传统的本质区别**（最重要一句）：
> 传统开发：把 PRD 拆成一个个 user story，分给一堆人一个个做。
> **ADLC：把整份 PRD 直接交给一个 agent，端到端跑完开发→测试→部署。你不拆活、不分活，你给方向 + 把关。**

**今天你的角色**：你是这个产品的 PO + 架构师，agent 是你的开发。你做的是「把需求说清楚 + 审 agent 的产出」。

**先讲 ADLC 的目的**：
- 让学生知道今天不是写一份文档就结束，而是要走完一圈：需求 → PRD → 开发 → 部署 → feedback。
- 让学生知道 PRD 不是作业格式，而是给 agent 的开发输入。
- 让学生知道 Product Thinking 的作用：不是讲商业理论，而是决定 ADLC 第一环「需求」到底对不对。

**整份 PRD 交给 Agent，而不是拆 user story**：
> 传统开发要把 PRD 拆成 ticket 分给多人；ADLC 里，你把整份 PRD 交给一个 agent，让它端到端跑完第一版。你不负责替它写代码，你负责给方向、审计划、验收结果。

## 2. 先看 PRD：最终要产出什么（~12min）

**为什么把 PRD 提前讲**：
- 学生先看到目标形态，后面讲 Product Thinking / Business Model / Business Logic 才知道是在为哪份文档收集信息。
- PRD 不是文档作业，而是 agent 的开发输入。
- 这节课的真正产出不是“听懂产品思维”，而是每个人写出一份 agent 能执行的 `PRD.md`。

**PRD 五块（投屏 + 讲）**：
1. **目标**：这个产品要解决什么、给谁、做到什么算成功
2. **输入**：agent 开发时能依赖的真实事实 / 数据 / 已有素材
3. **输出**：要做出什么 —— 用户看到什么、有哪些功能
4. **模块拆解**：把产品拆成几块（给 agent 看的结构，不是分给人的 user story）
5. **红线 / 验收**：绝对不能做的 + 怎么算「做对了」

**合格 PRD 的 6 个硬指标**：
1. 用户 + 场景
2. 真痛 + 成功标准
3. 输入事实
4. 输出形态
5. 范围边界
6. 验收方式

**PRD 之后：第二步是 Rules（投屏 + 讲）**：
- PRD 只回答「做什么」。Rules 回答「怎么写才算好、哪些写法不能接受」。
- 先把规则 prompt in：`Follow SOLID, DRY, KISS, and readability rules above.`
- 再 audit output：每次 agent 输出 / PR 都按 readability checklist 查一遍。
- 最后 refine：如果 LLM 违反规则，不是骂它，而是把规则写得更具体，或者加一条小 inline comment 后重跑。

**Rules List 标准原则**：
1. **SOLID Principles**：职责清楚，模块边界清楚，不把 UI、数据、业务规则塞进一个函数。
2. **DRY Principle**：Don't Repeat Yourself。同一份知识只能有一个权威表达，重复逻辑抽成函数 / 常量 / 配置。
3. **KISS Principle**：Keep It Simple。先要最简单能跑的设计，避免炫技 one-liner、不必要模式、过早优化。
4. **Readability**：今天的读者通常是未来的你，或者下一个 LLM；变量名、函数名、文件边界都要一眼能懂。

**Rules 文件结构（投屏 + 讲）**：
- `README.md`：总体概述和指引，所有 agent 先读。
- `architecture.md`：系统架构规范。
- `frontend/`：`component.md`、`styling.md`、`state.md`。
- `backend/`：`api-design.md`、`database.md`、`platform-adapter.md`。
- `workflow/`：`git.md`、`ci-cd.md`。
- `code-quality/`：`naming.md`、`testing.md`、`performance.md`。

**PRD 文件夹结构（投屏 + 讲）**：
- `docs/prd/README.md`：说明 PRD 命名、状态、评审方式。
- `docs/prd/templates/`：`prd-template.md`、`review-checklist.md`。
- `docs/prd/features/{feature-slug}/PRD.md`：按功能维护长期 PRD，例如 `features/chat-summary/PRD.md`。
- 状态写在 PRD header 里：`Status: Draft / Ready / In Progress / Review / Done / Dropped`。
- 不用 `active/`、`done/`、`dropped/` 文件夹搬文件；PRD 是长期做的，搬目录会让引用、历史和 agent 上下文变乱。

**Repo Strategy：Monorepo vs Polyrepo（投屏 + 讲）**：
- **Monorepo**：所有模块代码在一个 repo 下，通常以 `/frontend`、`/backend`、`/models`、`/infra` 子目录划分。
  - 优点：全局统一依赖、AI 易于理解全局语义、便于一次性部署。
  - 缺点：repo 过大、管理复杂、权限不易控制。
- **Polyrepo with submodules**：多个独立 repo，通过 submodule 或工作区组合。
  - 优点：各模块独立维护、利于团队分工、权限清晰、AI 可模块化理解。
  - 缺点：跨模块重构不方便、依赖更新需手动管理、AI 理解需要递归处理多个 repo。
- 课堂建议：个人小项目先用 Monorepo；公司级项目 / 多团队协作再考虑 Polyrepo + submodules。

## 3. 产品分析：自己发现需求（~45min · 为 PRD 收集判断依据）

> 刚才已经知道 ADLC 怎么跑。现在回到第一环：**需求从哪里来？** 会写 PRD 不难，难的是自己看见一个值得做的需求。这部分专练「从『等需求的人』变成『定义需求的人』」，然后用它把你 L1 作业那个产品想法磨利。

**讲（~8min）· 为什么这是天花板**：
- 工程师只会「实现」是天花板。AI 把「实现」打到地板价，于是值钱的整体上移一层：**从「你能不能写出来」变成「你能不能定义出对的东西让它写」**。
- 会写 prompt 不算本事 —— 需求本身错 / 模糊，AI 执行越快你错得越彻底。**Garbage in, garbage out 在 AI 时代是你的职业天花板。**
- 金句（可上 slide）：**过去工程师的价值是「把需求写成代码」；AI 时代是「把问题定义成需求」—— 代码 AI 替你写，但要解决什么问题，只能你自己看见。**

**第一刀（~5min）· 想法不是需求，功能也不是需求**：
- 想法：我想做一个 AI dashboard。
- 功能：要登录、列表、图表、聊天框。
- 需求：某类用户在某个场景下有一个真痛，解决后有可判断的成功标准。
- MVP：今晚只跑通一条核心流程，不做完整产品。

**Product Thinking Canvas（~10min）· 6 格把想法磨成需求**：
1. **用户**：到底是谁？学生 / 老师 / 运营 / 自己。
2. **触发场景**：什么时候会用？每天、课前、投递前、客服后。
3. **真痛**：现在哪里费劲？慢、容易错、记不住、没标准。
4. **现有 workaround**：现在怎么凑合？Excel、群聊、手抄、靠记忆。
5. **成功标准**：什么变好了？少 20 分钟、少漏 1 单、多 1 次复习。
6. **边界**：这版不做什么？不登录、不接支付、不做后台。

**MVP 砍刀（~5min）· 把三个月产品砍成今晚能跑**：
- Must：1 个用户、1 条主流程、1 个可见结果、1 个验收动作。
- Later：登录、历史记录、漂亮 dashboard、多角色权限。
- Not this version：支付、复杂后台、自动发邮件、接真实生产数据。
- 现场验收句式：打开页面 → 输入一个真实例子 → 点击一个按钮 → 看到一个有用结果。

**产品不是功能集合，是用户行为改变（~5min）**：
- 功能视角：做一个 AI 简历优化工具。
- 产品视角：让投 entry-level IT 岗的学生，15 分钟内把泛泛简历改成匹配某个 JD 的版本，并敢拿去投递。
- 讲师追问：这个产品让用户从什么旧行为，变成什么新行为？

**Business Model 四问（~5min）**：
1. 谁会用？
2. 谁会付钱？
3. 为什么现在付？
4. 从哪里来？

例：AI Assignment Debug 助手 = CS 一年级学生用；学生/家长付；due 前 48 小时最急；从课程群、学校论坛、小红书“作业 debug”获客。

**产品验证路径（~5min）**：
- **Idea**：灵感与问题定义。
- **PoC**：验证技术 / AI 逻辑能跑通。
- **MVP**：做出一个用户可真实体验的版本。
- **PMF**：验证市场愿意买、愿意用、愿意付费。
- **Scale**：验证能规模化复制。

今晚只要求走到 **PoC → MVP**：先验证 AI / 技术逻辑能跑通，再让一个真实用户完成一条主流程。不要一上来追 PMF / Scale。

**Business Logic（~5min）· 业务规则才是产品骨架**：
- 允许什么 / 不允许什么
- 状态怎么变
- 异常怎么处理
- 数据能不能覆盖、能不能编、什么时候提示用户

例：AI 简历匹配器规则：
- 如果 JD 为空，不允许生成分析
- 如果简历为空，提示先上传
- 如果匹配度低于 60%，输出 3 个最优先修改项
- 如果用户点击“生成版本”，必须保留原简历，不覆盖
- 如果 AI 没有证据，不允许编造项目经历

**为什么工程师现在要懂 Product Thinking / Business Model / Business Logic（~5min）**：
- 过去：PM / BA 给你 ticket，你负责实现。
- 现在：你要把模糊问题分析清楚，写成 Agent 能执行的 PRD。
- Product Thinking 回答：这个产品在改变谁的什么行为？
- Business Model 回答：这个东西为什么值得存在？谁用、谁付钱、为什么现在、从哪里来？
- Business Logic 回答：产品运行时必须遵守什么规则？允许什么、不允许什么、状态怎么变、异常怎么处理？
- 三者最后都要落到 PRD：目标、输入事实、优先级、模块拆解、红线和验收。

**教 + 动手（~12min）· 需求 X 光机·五问**（每人对着自己 L1 作业的产品过一遍，投屏模板照填）：
1. **谁是真正的用户**？牵扯几类人、利益冲不冲突（很可能就是你自己 / 你同事）
2. **真痛是什么**（不是嘴上要的功能）？连问三次「为什么」挖到真痛 —— 别停在「我想要个功能」
3. **不做会怎样**？代价小的需求，最好的实现是**不做**（先砍掉伪需求）
4. **怎么算成功**？哪个动作 / 数字变好了才算成？没有指标的需求是耍流氓
5. **边界在哪**？这版**明确不做什么** —— 把三个月的想法砍成今晚能做完的 MVP

> 一句对比：没产品思维 = 从「我想做什么」往外列（**供给驱动**）；有产品思维 = 从「真正要解决什么」往回倒推（**需求驱动**）。

**老师检查点**：每人用一句话说清「为【谁】在【什么场景】解决【什么真痛】，做到【什么】算成功，这版不做【什么】」—— 说不清就别往下走（需求没磨利，后面 agent 做得越快错得越远）。
**常见卡点**：① 需求是假的（「想学一下 / 想试试」不是痛）→ 换一个他真的每天烦的事；② 范围太大 → 砍到「今晚能跑通的一个核心动作」；③ 把方案当需求（「我要一个 dashboard」）→ 追问「你要这个 dashboard，是想解决什么问题」。

## 4. 写 PRD（正式教学 + 动手，~30min）

**这是本节的教学核心。前面已经看过 PRD 结构，现在每人把自己的产品分析写进 `PRD.md`。**

**现场口令**：把 PRD 读完，agent 不需要追问就能开工；你也知道怎么验收。做不到这两点，PRD 还没写完。

**Lab · 每人自己写 PRD（15min）**：照五块写自己产品的 PRD（Markdown 文件，因为 agent 读 md 最顺 —— 呼应 L1）。这不是老师代写，也不是全班共用一个例子；每个学员必须拿自己的 L1 作业产品写一份。

**投屏 worksheet（让学生照填，不要写长文）**：
```markdown
## Lab: 我的 PRD

我为【谁】解决【什么真痛】。

今晚 MVP 只做【一个核心动作】。

用户输入【什么】。
系统输出【什么】。

需要依赖的真实资料 / SoT:
- 【文件 / 链接 / 数据来源】

这版明确不做:
- 【砍掉的功能】

验收方式:
打开【页面】 -> 点击【按钮】 -> 看到【结果】。
```

**同桌互审（2min）**：交换读对方 PRD，只问一个问题：读完以后，agent 还需要追问什么？如果还要追问，现场补一句。

**老师检查点**：PRD 里 ① 有明确用户场景 ② 有真实输入 SoT ③ 有明确 MVP 边界 ④ 验收标准具体（能判断成没成）⑤ agent 读完不用再追问就能开干。
**常见卡点**：① 写成功能流水账没优先级 → 让他标「这一版只做这 1-2 个核心」；② 输出写得含糊（「做个好用的工具」）→ 逼他写「用户点 X，看到 Y」。

## 5. ADLC ③ 整份 PRD 交给 Agent 开发（~40min · 主战场）

**核心动作**：把刚写的**整份 PRD 一次性喂给 Claude Code**，让 agent 端到端搭 —— 不要自己一段段写代码，让 agent 照 PRD 干。

**老师带的要点**：
- **怎么喂**：`读这份 PRD，按它端到端把这个产品搭出来，先搭 MVP 那几块，遇到不确定的先问我再做`。
- **怎么盯**：看 agent 的计划对不对、改的文件对不对，**审产出而不是替它写**。
- **🔥 agent 卡住 / 改不动死循环怎么破**（这是工作坊最高频卡点，重点带）：
  1. 别在烂状态上继续叠 prompt → **回滚到上一个能跑的状态，重新描述**
  2. **让 agent 先讲根因再改**，禁止它瞎改
  3. **缩小范围**：把问题隔离成最小复现再喂
  4. 修好后**把教训写进 `CLAUDE.md` / rules**，让它别再犯（接 L1 的记忆系统）
- **判断 agent 在瞎编**：让它写个测试 / 解释为什么这么改有效，别盲信。

**老师检查点**：每人跑出**第一个能动的版本**（哪怕丑、哪怕只有一个核心功能能用）。
**分流**：快的 → 让 agent 加第二个功能 / 接真实数据；卡的 → 砍到更小的 MVP，老师结对破局。

**如何管理多个 PRD（讲师收口，~8min）**：
- 产品做起来以后，不是只有一份 PRD，而是一堆需求文档排队等你判断。
- **建 PRD Backlog**：所有想做的东西先进入需求池，包含一句话需求、用户、价值、状态、负责人。
- **排优先级**：每次只选 1 个最值得做的 PRD，按用户痛、商业价值、实现成本、风险排序。
- **管状态**：Draft → Ready → In Progress → Review → Done / Dropped。
- **管版本**：PRD v1 做 MVP，v2 改反馈，v3 再加范围；不要在同一份 PRD 里无限改目标。
- **给 agent 的原则**：一次只喂一个 Ready PRD；做完验收，再决定下一个。

**管理口令**：想到的需求先进 Backlog；Ready 的 PRD 才能交给 agent。

## 6. ADLC ④ 部署上线（~20min）

让 agent 帮你把 MVP 部署到云端，**拿到一个别人能打开的 URL**（Cloudflare Workers / Serverless / 任意托管）。

**怎么带**：`帮我把这个项目部署到 [Cloudflare Workers/Vercel]，给我一个能访问的地址，需要配什么 key 一步步告诉我`。
**老师检查点**：用**手机**打开那个 URL（不是本机 localhost）能看到东西 = 过关。
**常见卡点**：环境变量 / key 配置、build 报错 → 让 agent 读报错自己修（呼应 L1 debug 思路）。

> 时间紧时本步可降级为「本地能跑 + 截图」，部署留作业，但**至少演示一次真部署**让大家看到「能上线」。

## 7. ADLC ⑤ 分析 feedback + 迭代（~15min）

**自己用一遍刚做出来的东西**，找出 1-2 个最别扭的点 → 写成新需求 → 回到 PRD 改一行 → 让 agent 改。

**点破闭环（念）**：「你看，你刚走完了一整圈：需求 → PRD → 开发 → 部署 → 用起来发现问题 → 又变成新需求。**ADLC 是个循环，不是一条直线。**真实产品就是这样一圈圈转出来的 —— 你今晚转了第一圈。」

**老师检查点**：每人能说出「我用下来发现的下一个要改的点是什么」。

## 8. 收尾 + 作业 + L3 预告（~10min）

- **每人 30 秒展示**：你做出来的是什么 + URL/截图（不评好坏，只看「从想法到能跑」这一步走通没）。
- **作业**：继续迭代你的产品，至少再转一圈 ADLC；把过程中 agent 踩的坑写进你的 `CLAUDE.md`。
- **L3 预告（念）**：「今晚你是**从零**做自己的产品。下节课更难也更真实 —— 怎么把这套 ADLC + AI OS，用到一个**已经存在、有历史包袱的真实项目**上：看不懂的老代码、没文档、不敢乱改。那才是你工作里天天面对的。」

## 老师巡场总表（一页速查）

| 阶段 | 学员产出 | 检查点（过关标准） | 高频卡点 → 怎么救 |
|------|---------|------------------|------------------|
| ① 需求收敛 | 4 要素一句话 | 说清「为谁/什么痛/成功标准/不做什么」 | 范围太大 → 砍到一个核心动作 |
| ② 写 PRD | 一份 md PRD | 有 MVP 边界 + 具体验收 + agent 不用追问 | 功能流水账 → 标优先级；输出含糊 → 写「点X看Y」 |
| ③ Agent 开发 | 第一个能跑版本 | 有个核心功能真的能用 | 改不动死循环 → 回滚+讲根因+缩范围+写rules |
| ④ 部署 | 可访问 URL | 手机能打开 | key/build 报错 → 让 agent 读报错自修 |
| ⑤ feedback | 下一个要改的点 | 能说出迭代点 | 没想法 → 让他自己用一遍 |

**全程红线**：不承诺包就业 / 金钱结果；学员产品里的真实数据 / PII 不外发；只看「流程走通没」不评学员产品好坏。
