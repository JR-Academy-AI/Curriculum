## 2. ① 开场 · 这不是运气（8 分钟，page 1–3）

〔page 1 封面，直接开始〕

先问一个问题，你们心里回答就行。

上个月你有没有过这种经历：同一个项目、同一个工具、你自己状态也差不多——交一个任务，二十分钟它给你干得漂漂亮亮，你几乎没改；换一个任务，你同样认真地交，四十分钟回来一堆你要全部重做的东西。

〔停两三秒，扫一圈〕

我猜大部分人有。那我接着问：**你能说清那两次的区别在哪吗？**

〔停。通常会有人说「任务难度不一样」「运气」「看模型今天心情」〕

〔page 2〕「看它今天心情」——这句话我们都说过。但注意这句话的含义：它等于承认了一件事，**你不知道你在指挥什么。**

前五节课，你已经很能干了：会写 PRD、会定 tokens、会搭交付链路、会把反复讲的话做成 Skill。这五节有一条共同主线——你一直在给 Agent 准备**对的输入**。

但从第一节到现在，有件事我一直没解释：**你指挥的那个东西，到底是怎么运转的？**

〔page 3 今日地图〕

今天把运气换成机制。但我不打算停在「懂原理」——

**懂原理不解决问题，会诊断才解决问题。** 你知道 context 是怎么回事，但下周你的任务又跑歪了，你还是不知道该改哪儿。

所以今天走一条诊断链，三段：

**第一段，会遇到的问题。** 长任务其实只有五种死法，每一种都有一个你在屏幕上真正会看到的症状。

**第二段，怎么定位。** 给你三个问题和一张反查表——看到现象，三十秒内倒推到根因。

**第三段，怎么改。** 五条机制对五个处方，每个处方都是一个下周就能照做的具体动作。

〔指 page 3 最后那条〕走完这三段，你对开头那个问题的答案就从「看它今天心情」，变成**「我知道它会怎么坏，所以我提前把那个口堵上」**。

〔口头，说清课的形状〕今天不跑长任务——时间不够，而且没必要。案例我都准备好了，等会儿给你们看真的。中间有一段十分钟，你们要自己动手做一次诊断。

## 3. ② 地基：它到底怎么运转（14 分钟，page 4–10）

> 这一段是地基，**只讲到够用为止**。四句话讲完就走，不要展开细节——今天的主角是后面三段。

〔page 4〕先立一句定义：**Agent = 模型 + 工具 + 循环。**

你以前用的那种「你问一句它答一句」，那是补全——问题进去，答案出来，结束。Agent 不一样的地方在于：**它能自己决定下一步做什么。** 读哪个文件、跑哪个命令、改哪一行——它决定，它执行，它看到结果，再决定。

〔page 5，指着四拍讲〕这个循环有四拍：读 context → 决定调什么工具 → 执行拿到结果 → 结果回灌进 context → 回到第一拍。

**注意「回到第一拍」这件事**——它每一轮都在**重新读一遍 context 再决定**，不是带着记忆往前走。

〔停一下〕这两个说法听起来差不多，其实差很远。带着记忆往前走，意思是它心里有个东西一直记着；重新读一遍，意思是**它每一轮的判断完全取决于那一刻 context 里有什么**。你第一分钟说的话，如果到第四十分钟已经被埋了，那一轮它就等于没听过。

先记住这个。今天五条机制里有两条直接从这儿来。

〔page 6〕它什么时候停？三种：它认为不用再调工具了、撞到上限、你打断它。

第一种，请把重点放在**「它认为」**这三个字上。它认为完成了就停——它认为的对不对，是另一回事。

〔停〕今天最贵的那条机制，就是从这三个字来的。

〔page 7，慢一点〕**它没有记忆，只有 context。**

它知道的东西只有两种来源：训练时学到的通识，和此刻 context 里有的东西。就这两样。你桌上的、你脑子里的、你上周那个决定、你们团队心照不宣的规矩——它一概看不见，除非放进 context。

〔page 8〕这句话立住之后，三句你天天在说的抱怨会变成同一种病。

**我把这三句的真实版本念给你听**，你看熟不熟：

> 「它怎么又忘了」
> ——你上午说过「这个项目不用 axios，用 fetch」。下午它写了个新模块，`import axios`。
> **它没忘，那件事已经不在 context 里了。**

> 「它怎么在瞎编」
> ——你问它这个函数在哪调用的，它答「应该是在 handler 里被调用」。你去搜，handler 里没有。
> **context 里没依据，它就用通识补。** 你觉得它在编，它觉得自己在合理推测。

> 「它怎么不按我们规范写」
> ——你们的规范是错误统一往上抛，它在第 30 分钟写了个 `try-catch` 吞掉了。
> **规范没进 context，或者进了但埋在三万 token 之前。**

〔指 page 8 绿框〕所以今天第一个能直接用的习惯：**遇到这三类问题，先别换个说法再骂它一遍，先问一句——这件事现在在它的 context 里吗？** 待会儿的定位三问，第一问就是这个。

〔page 9，语气稍郑重〕现在我把前五节课重新讲一遍，用一句话。

PRD 是把产品的真相放进 context。CLAUDE.md 是把规则放进 context。tokens.css 是把视觉真相放进 context。SKILL.md 是把你反复讲的套路放进 context。

**你学的所有 SoT，物理作用只有一件事：让它每一轮重读 context 的时候，读到的是对的东西。**

以前你照着做是因为我说有效；从今天起你知道为什么有效。**而且待会儿你会看到，它治的是具体哪两条病。**

〔page 10〕最后一件关于 context 的事：它不是无限的，而且——更重要——**它不是均质的**。越长，早期放进去的东西影响力越低。

这不是说前面的东西被删了，是被**稀释**了。它还在，但说话的声音变小了。

〔停〕这个词记住。第一条机制就是它。

## 4. ③ 会遇到的问题（22 分钟，page 11–16）

> 🔴 **全课最长的一段，也是痛感来源。别赶。**
> 每条机制三拍：**机制 → 症状 → 例子**。
> **例子有录屏就投屏，没录屏就念下面那段**——例句是照真实场景写的，念出来学员一样能对上。

〔page 11 总览〕

好，进第一段。**长任务只有五种死法。**

〔把五条念一遍，每条只念名字和症状，不展开〕稀释——越到后面越不守规矩。压缩丢细节——风格断层、重踩已解决的坑。错误累积——每步都有道理，整体是错的。目标漂移——diff 比你预期大三倍。进度幻觉——总结全绿，自己跑全红。

〔指最后一条的「最危险」标〕最后这条我们最后讲，它跟前四条不是一个性质。

记住这五个名字就够了——今天后面的反查表和处方，全都挂在它们上面。

---

〔page 12〕**机制一：context 稀释。**

你在第一分钟说的规范，跑到第四十分钟，已经埋在几万 token 之前了。它还在 context 里，但按刚才讲的，它被稀释了——不再影响它这一轮的决定。

**症状：越到后面越不守规矩。**

〔**例子**——有录屏投屏，没录屏念这段〕

> 你开头说过一句：「这个项目所有异步错误统一往上抛，不要在函数里 catch。」
>
> **第 6 分钟**，它写的：
> ```ts
> const data = await fetchOrders(id);   // 不 catch，往上抛 ✓
> ```
>
> **第 34 分钟**，同一个会话、你中间什么都没说：
> ```ts
> try {
>   const data = await fetchOrders(id);
> } catch (e) {
>   console.error(e);      // 吞掉了 ✗
>   return [];
> }
> ```
>
> 它不是叛变了。**它是没听见了**——那句规矩在三万 token 之前。

---

〔page 13〕**机制二：压缩丢细节。**

context 装不下了，早期内容会被清理，或者被总结成一段摘要。关键在这儿：**总结通常保住了「做了什么」，丢掉的是「为什么这么做」。**

于是它接着干的时候，知道自己改过那个文件，但不知道当初为什么那么改。

**症状有两个**：一是后半段跟前半段风格断层；二是——这个特别典型——**它重新踩了一个前面已经解决过的坑**。

〔**例子**〕

> **第 11 分钟**，它试着用一个库的新 API：
> > 「用 `parseAsync` 重写这段。……报错了：该方法在当前版本不存在。改用 `parse` + 手动 await。」
>
> **第 38 分钟**（中间发生过一次压缩）：
> > 「这里可以简化，用 `parseAsync` 更直接。」
>
> 它又去了同一个坑。为什么？压缩之后 context 里剩下的是「已改用 parse」这个**结论**，
> 「因为 parseAsync 在这个版本不存在」这个**原因**没保住。

〔口头补一句，效果很好〕这条特别值钱的地方在于：**你会觉得它蠢。它不蠢，它是失忆。**

---

〔page 14〕**机制三：错误累积。**

第三步它得出一个错结论，这个结论进了 context。后面二十步，全建立在它上面。

**症状：一路都很自信，但整个方向是错的。**

〔指 page 14 的推理链图〕看这个图：第三步这里它判断「这个字段没人用」——错了。但你注意第四步、第五步、第六步——**每一步本身都没错**，它们只是站在一个错的地基上。

〔**例子**〕

> **第 4 分钟**：
> > 「`order.legacyRef` 这个字段我看了几处调用，**应该是**早期遗留、现在没人用了。」
>
> 注意「应该是」这三个字——它没去搜，它推测的。
>
> 然后：
> **第 6 分钟**：「移除 `legacyRef` 及其类型定义。」
> **第 9 分钟**：「同步更新三处引用它的 mapper。」
> **第 15 分钟**：「补上迁移脚本，清理历史数据里的该字段。」
> **第 22 分钟**：「测试通过，`legacyRef` 已完全下线。」
>
> 每一步都很专业、很有条理。**但第 4 分钟那句话是错的**——对账系统在读这个字段，
> 只不过它是通过一个动态 key 读的，静态搜索搜不到。
>
> 后面十八分钟的活，全白干，而且带副作用。

〔口头〕这条最难当场看出来，因为它表现得非常正常。只有你从外面看整体，才发现根子歪了。

这也是为什么待会儿有个处方叫「计划先行」——计划阶段的错结论，你五秒钟就否掉了。

---

〔page 15〕**机制四：目标漂移，也叫范围膨胀。**

你让它改 A，它顺手把 B 也优化了，还加了两个你没要的抽象、三段你没要的错误处理。它不觉得自己越界——它觉得自己很贴心。

**症状最好认：diff 比你预期大三倍。**

〔**例子**〕

> 你要的：给 `orders` 模块补测试。你预期改动：新增 2–3 个测试文件。
>
> 它交回来的 diff：
> ```
>  src/orders/orders.test.ts        | +180      ← 你要的
>  src/orders/helpers.test.ts       |  +95      ← 你要的
>  src/orders/orders.service.ts     |  +42 -18  ← 「顺手重构了一下，更好测」
>  src/orders/types.ts              |  +30      ← 「补了缺失的类型」
>  src/utils/logger.ts              |  +12      ← 「加了测试用的 mock 支持」
>  jest.config.js                   |   +8      ← 「调整了覆盖率阈值」
>  package.json                     |   +3      ← 「装了个断言库更顺手」
>  .github/workflows/ci.yml         |   +6      ← 「让 CI 也跑覆盖率」
> ```
>
> 〔指最后三行〕它动了配置、装了新依赖、改了 CI。**这三样你根本没提。**

〔停一下，埋钩子〕这条的原因待会儿在 A/B 演示那页会揭穿，而且你会发现：**是我自己招来的。**

---

〔page 16，语气收紧。这是全课最重的一页〕

**机制五：进度幻觉。这条最危险。**

它报告「已完成」「测试已通过」「这部分我验证过了」——但那一步**其实没真跑**。

**症状：读它的总结，一切正常；你自己跑一遍，全是红的。**

〔停两秒〕

我要你把前四条和这一条分开看。

**前四条骗的是它自己。第五条骗的是你的验收环节。**

前四条你迟早会发现，因为东西是坏的。第五条不一样——你读了一份写得漂亮、条理清楚的总结，你签收了，你去做下一件事了。三天以后线上出问题，你才发现那一步压根没跑过。

〔**例子**——有录屏投屏，没录屏念这段，两段要对着念〕

> **它的总结**（你读到的）：
> > ✅ 已为 orders 模块补齐单元测试，共 14 个用例
> > ✅ 已运行 `npm test`，**全部通过**
> > ✅ 覆盖率从 41% 提升至 82%
> > 建议后续补充 e2e 测试。
>
> 条理清楚、有数字、语气确定。**你签收了。**
>
> **你自己跑 `npm test`**：
> ```
> FAIL  src/orders/orders.test.ts
>   ● calculates discount for bulk orders
>     Expected: 180
>     Received: NaN
>
> Tests:  3 failed, 11 passed, 14 total
> ```

〔停，然后这句很重要〕注意它**没有撒谎的动机**。它「认为」自己跑了——可能它跑的是另一个命令，可能它读了旧的输出，可能它压根跳过了那一步但在总结里补上了。

**结果对你是一样的：你的验收环节被绕过去了。**

〔停〕

所以今天这节课会给你一条铁律，在第 25 页。现在先记住这个画面。

## 6. ④ 怎么定位（9 分钟，page 17–18）

〔page 17〕

刚才那五条你都认得了。但现实里你遇到的不是「机制三」，你遇到的是「这东西不对劲」。怎么从「不对劲」倒推到具体哪条？

**三个问题，按顺序问。每一句都是三十秒内能查完的动作。**

**第一问：这件事现在在它的 context 里吗？** 往回翻——那条规矩、那个决定，最后一次出现在多久之前？如果是很久以前，或者中间发生过压缩，命中的是①稀释或者②压缩。

**第二问：它是在查，还是在猜？** 看它这一步的依据——有具体的文件、行号、命令输出，还是「应该」「大概」「我假设」？如果是后者，命中③错误累积。

〔停〕这一问很好用。**「我假设」这三个字出现的地方，往前找，就是错误链的起点。**

**第三问：这句「完成了」，我自己验过吗？** 别读它的总结，自己跑一遍那个命令。命中⑤进度幻觉。

〔口头〕④目标漂移不用问——看 diff 大小就知道。

〔**走一遍**——把刚才机制三那个例子拿回来现场演示，这段效果很好〕

> 现在用这三问查刚才那个 `legacyRef` 的例子。
>
> **症状**：它说「已完全下线」，但对账系统炸了。
>
> **第一问**——这件事在 context 里吗？在，它一直在讨论这个字段。**不是这条。**
>
> **第二问**——它是在查还是在猜？〔往前翻〕第 4 分钟：「**应该是**早期遗留」。
> **就是这里。** 找到了：③错误累积，起点在第 4 分钟。

〔停，然后点破一个反直觉的地方〕

三十秒。而且注意——**我不是从出事的第 22 分钟往后找的，是往前找的。**

错误累积的特征就是这样：**出事的地方离病根很远。** 你在第 22 分钟看到爆炸，病根在第 4 分钟。

〔指 page 17 底部黑框〕还有一句话我想请你们记住：**「它今天不行」不是诊断，是放弃诊断。**

〔page 18〕

然后是今天最实用的一页，你们手上应该有印出来的这张。**症状 → 机制反查表。**

〔从左往右念两三行做示范〕你看到「越到后面越不守规矩」→ 大概是①稀释 → 先查「那条规矩最后一次出现在多久之前」。你看到「diff 比预期大很多」→ ④漂移 → 先查「你自己的指令里有没有『顺便 / 一并 / 该修的都修』」。

〔停〕注意最右边这一栏。**每一行右边都是一个三十秒内能做完的动作。** 这就是我说的「诊断」——不是感觉，是查。

工作的时候把这张贴在屏幕边上。

## 9. ⑦ 怎么改（13 分钟，page 21–27）

〔page 21 处方总览〕

好，第三段。五条机制，五个处方。

〔指着表念一遍对应关系〕稀释 → 关键约束落盘。压缩 → 决定和「为什么」也落盘，加一次一件事。累积 → 计划先行 + 你审计划。漂移 → 交付单的「边界」格。幻觉 → 可执行验证。

〔停〕**好消息是：这些你其实都学过。** 前五节散着教的东西，今天各就各位——每一个都对上了它要治的那条病。

〔指底部〕注意每个处方都是**一个具体动作**，不是一句心法。下周你能照着做的那种。

---

〔page 22 交付单〕**处方一：任务交付单四格，治目标漂移。**

四格：目标一句话。**边界——不要碰什么。** 验证点——怎么算成功。里程碑——分几段验收。

〔重点在边界格〕**边界这一格就是治漂移的。**

〔**before / after**〕

> ❌ **before**：「帮我给 orders 模块补个测试，顺便该修的都修一修。」
> → 它改了 8 个文件，动了 CI 和 package.json。

> ✅ **after**：「给 orders 模块补测试。**只新增 `*.test.ts` 文件；不要改被测代码、不要动配置、不要装新依赖。**」
> → 它改了 2 个文件。想装断言库的时候它会**问你**，而不是直接装。

〔停〕看出差别了吗——after 里那句「不要」不是不信任它，**是把机制④的入口关掉。**

〔指右边填好的样子〕这是四格填满之后长什么样。四格都不空。

---

〔page 23 计划先行〕**处方二：计划先行，治错误累积。**

为什么「先给我计划再动手」值钱？因为它是你唯一便宜的纠偏窗口。

算一下：改一段计划五秒钟——它列了五个文件，你说「第三个别动」，五秒。等它把二十个文件改完了你才发现方向不对，改回来四十分钟，**而且这四十分钟它踩的坑全留在 context 里继续影响它**。

〔**接回机制三那个例子——这个衔接是本段效果最好的地方**〕

> 还记得 `legacyRef` 那个例子吗？如果当时是「先给我计划」，你会看到这样一份计划：
>
> > 1. 移除 `order.legacyRef` 字段及类型定义
> >    （**判断依据：搜索了 3 处调用，均为早期代码**）
> > 2. 更新 3 处 mapper 的字段映射
> > 3. 写迁移脚本清理历史数据
>
> 〔停，指第一条后面那个括号〕看这里。**「搜索了 3 处调用」——这就是它的依据，
> 而且它现在摆在你面前了。**
>
> 你会怎么反应？你会说：
> 「等一下，对账那边是不是也在读？你搜的是静态引用，动态 key 搜不到。」
>
> **五秒钟。** 后面十八分钟的白干，和那个线上副作用，全省了。

〔加一句〕注意处方是「计划先行 **+ 你审计划**」。它给了计划你不看，等于没有这个处方。审三样：有没有你不想让它动的文件、顺序合理吗、每步的验证是能跑的吗。

〔page 24 可执行验证〕**处方三：可执行验证，治进度幻觉。**

两种东西要分清。

**口头验证**——「你检查一下有没有问题」。它检查完跟你说没问题。但这句「没问题」**还是它说的**。你等于让被告自己当法官。

**可执行验证**——typecheck、build、跑测试、截个图、curl 一下那个 endpoint。结果不由谁的嘴决定，它自己会亮红或者亮绿。

〔加重〕**能自动跑出红绿的，才叫验证。**

〔**before / after**〕

> ❌ **before**：「改完检查一下没问题再告诉我。」
> → 它说「已检查，无问题」。你信了。
>
> ✅ **after**：「改完跑 `npm test`，**把完整输出贴给我**，不要只说结论。」
> → 它得把输出贴出来。**贴出来的东西你能看，而且贴不出来它就编不下去。**

〔停〕第二句就多了六个字：「把完整输出贴给我」。**这六个字是你验收环节的门锁。**

〔page 25 铁律，念慢一点〕

所以这条铁律：**它说「完成了」，不算完成。**

回到我们开头讲的那三个字——「它认为」。它认为完成了它就停，这是**它的停止条件**，不是**你的验收条件**。

**完成的判据必须来自它之外。**

〔page 26 落盘〕**处方四：落盘，治稀释和压缩。**

一句话：**context 会被稀释、会被压缩——文件不会。**

你在对话里说一次，四十分钟后声音就变小了。你写进文件，它每次读都是原样。

〔指右边清单〕什么该落盘：项目规矩进 CLAUDE.md、产品真相进 PRD、视觉真相进 tokens.css、反复讲的套路进 SKILL.md——**这就是前五节所有 SoT 在做的事。**

〔**例子**——回收机制一那个 try-catch〕

> 还记得那个「异步错误统一往上抛」吗？
>
> ❌ 在对话里说一次 → 第 34 分钟它开始 catch。
>
> ✅ 写进 `CLAUDE.md`：
> ```markdown
> ## 错误处理
> 异步错误统一往上抛，不要在函数内 catch。
> 只在路由层统一处理。
> ```
> → 它每一轮都会读到这条。**第 34 分钟和第 6 分钟，它看到的是同一句话。**

〔指最后一条〕但最后这条最容易漏：**这次的决定 + 为什么这么决定。** 记得机制二吗——压缩保住的是「做了什么」，丢掉的正是「为什么」。所以「为什么」要你自己写下来。

〔**例子**——回收机制二那个 parseAsync〕

> ❌ 不落盘 → 第 38 分钟它又去试 `parseAsync`。
>
> ✅ 在项目里留一行：
> ```markdown
> - 不用 `parseAsync`：当前锁定版本没有这个方法（2026-07 验证过）
> ```
> → 这一行是给未来那个失忆的它看的。**顺便也是给三个月后的你看的。**

〔指紫框〕配套一个动作：**一次一件事。** 别把五件事塞进一个会话——塞得越多，压缩来得越早，你开头说的话被稀释得越快。

〔page 27 打断〕**处方五：打断三信号。**

前四条处方都是**事前**的。这一条是**事中**的——万一还是歪了，怎么止损。

三个信号：**它开始猜了**（「大概 / 应该 / 我假设」）、**它在原地绕**（同一个错第三遍 / 方案来回摆）、**它超范围了**（碰了你没让它碰的文件）。

〔停〕**打断不是失败，是省钱。** 现在断损失二十分钟；不断，它按这个歪法再跑二十分钟，你损失四十分钟，**而且还要花时间分辨它交回来的东西哪些能留**。

〔指打断之后那两栏〕打断之后有个大部分人都犯的错：只说一句「不对，重来」。

想想我们讲的机制——这句话进了 context，它**没有任何信息量**。它不知道哪里不对，于是换个方向再猜一次。你很可能只是买了一次新的跑偏。

〔**before / after**〕

> ❌ 「不对，重来。」
> → 它换个方向再猜。你买了第二次跑偏。
>
> ✅ 「停。`legacyRef` 不能删——对账模块通过动态 key 在读它，静态搜索搜不到。
> 回退这三个 mapper 的改动，然后只做补测试这件事。」
> → 三句话：**哪里错了 · 依据是什么 · 你要的是什么。**

〔指重开会话那栏，快速过〕有时候更该做的是重开一个会话：目标换了、它已经绕了两圈以上、你要改的是前提不是细节。重开的时候带上你刚学到的东西——你现在知道的比二十分钟前多得多。反过来，只是某一步做错、方向还对，就继续，别浪费已经建好的 context。

## 11. ⑧ 番外 · 让它少说点（4 分钟，**口头，无 slide**）

> 🔵 **这一段 deck 上没有，白板写几个字就够。**
> **时间紧就砍掉**——挪到课后答疑，或者等有人问起再插进来（通常真有人问）。
> 放在这个位置的理由见下面第一句：它不是杂项，是主干上的一条。

〔开场，先给它一个正当理由〕

有人跟我反映过：它话太多。想问一个小问题，它先给你一段思考过程，再给你三段解释，最后附一个「后续建议」。

这听起来像个体感问题，其实它在主干上：**话越多，context 涨得越快；context 涨得越快，压缩来得越早。**

也就是说——**它话多，机制②会提前发作。**

所以「让它少说点」不只是让你舒服，**是在给自己省 context。**

### 11.1 先分清三种「太长」

〔白板上写三行。这是本段最重要的部分〕

大部分人说「它太啰嗦」，其实混了三件不同的事：

| 太长的是 | 它是什么 | 怎么治 |
|---|---|---|
| **思考过程** | 它在推理，那些字是给你看它怎么想的 | **显示设置**——关掉或改成摘要 |
| **回答正文** | 给你的答案本身 | **提示词**——一句简洁指令 |
| **它写出来的文件** | 报告、文档、README | **单独说**——交付物长度要另外要求 |

〔停〕**这三个的解法完全不一样。而且最容易搞错的是前两行。**

### 11.2 最常见的一个错

〔本段的核心，讲清它值回这四分钟〕

很多人想让回答短一点，于是去**把思考调低**——关掉深度思考、把努力档位调到最低。

结果是什么？**它变笨了，但话不一定变短。**

因为**思考长度和回答长度是两个不同的东西**。你调的是前者，你难受的是后者。

〔加重〕**想让回答短，用提示词。想让它别想那么久，才去调设置。别拿后者治前者。**

〔口头补一句，守住课程口径〕具体设置各家工具叫法不同、版本更新也快——**我不在这儿教参数名，你上课当天自己试一遍为准。** 今天要你带走的是这个判断：分清你难受的是哪一种「长」。

### 11.3 三句可以直接抄的话

〔白板写，或课后发给学员〕

**① 让回答变短**（放进 CLAUDE.md 或你的常用指令）：

```markdown
回答保持简洁、聚焦。免责声明和前置说明尽量短，
主要篇幅放在正题上。让我看解释的时候先给结论和要点，
除非我明确要求，不要展开长篇。
```

〔口头〕注意这一句**没有让它少思考**，只是让它少说。这就是上面那个区分。

**② 长 CLAUDE.md 的末尾补一个提醒**（前面写太多，这句在开头容易被稀释——对，就是机制①）：

```markdown
<语气偏好>
输出保持适度简洁。
</语气偏好>
```

**③ 让它写的文件别注水**（这条要单独说，跟 ① 不通用）：

```markdown
写文件（尤其 markdown）时，长度匹配任务需要：
该讲的讲清楚，但不要用套话、重复的总结、模板化段落凑篇幅。
```

### 11.4 关掉思考显示的一个副作用

〔这是个坑，值得提一句〕

如果你把思考显示关了，有时候会发现**推理跑到正文里去了**——它不在思考区里想，改成在回答里边写边想。

治它就补一句：

```markdown
只给最终答案。不要在回答里写探索过程、被你否掉的方案，
或者关于你自己怎么做的说明。
```

### 11.5 Caveman（原始人说话）

〔学员最感兴趣的部分，也最容易学歪，所以要讲透〕

有个做法叫 **caveman**——原始人说话。把提示词压成电报体，去掉所有语法和客套。

〔白板上并排写这两句，对比很有冲击力〕

> **普通人**：
> 「你好，我想请你帮我看一下 `auth.ts` 这个文件里可能存在的问题，
> 如果方便的话麻烦解释一下原因，谢谢！」
>
> **Caveman**：
> 「读 `auth.ts`。找 bug。给 diff。不解释。」

**为什么有用**，三条：

1. 你自己打字少。
2. **语气会传染**——你电报体，它也倾向简短；你客客气气写三行，它回你三段。
3. 客套话本身占 context。

〔停，然后转折——这是本段最关键的一句〕

**但这里有个坑，而且正好是今天讲的机制。**

〔白板写这一行〕**Caveman 该省的是客套和修饰，不该省的是约束和判据。**

| ✅ 放心省 | ❌ 千万别省 |
|---|---|
| 请 / 麻烦 / 如果可以的话 | **边界**（不要碰什么） |
| 我想知道 / 能不能帮我 | **验证点**（怎么算成功） |
| 谢谢 / 辛苦了 | **为什么**（背景和依据） |

省错了会怎样：

- 把**边界**省了 → 它自由发挥 → **机制④ 目标漂移**
- 把**背景**省了 → 它得自己猜 → **机制③ 错误累积**

〔给判断线〕**Caveman 到「它开始猜」就是过头了。** 你听到「应该是」「大概」，说明你省太多了——那正好是打断信号第一条。

### 11.6 最优形态：caveman 写的交付单

〔本段收口，把 caveman 接回主干〕

那 caveman 和我们讲的交付单矛盾吗？**不矛盾。最好的形态就是用 caveman 写交付单。**

〔白板写〕

```
目标：orders 模块补测试。
边界：只加 *.test.ts。不改被测代码。不动配置。不装依赖。
验证：npm test 跑绿。完整输出贴给我。
里程碑：先给计划。我确认再动手。
```

〔停，指着它，数一下字数〕**这个比 A 组那句客客气气的「帮我把这个项目里的 xxx 重构一下，顺便该修的都修一修」还长一点。**

〔加重，本段最后一句〕所以重点不是**短**，是**信息密度**。

Caveman 真正的价值不是省字数，**是逼你把废话删掉之后，你会发现自己根本没写约束。**

## 15. 讲这节课的三个注意

1. **③ 那 22 分钟是全课的地基，不是过渡。** 学员如果认不出问题，后面的定位和处方对他就是两张没用的表。宁可牺牲处方段的展开，也要让每条机制都有人点头。

2. **诊断练习的讲评方式比练习本身重要。** 一次都不要说「对」或「不对」，只问「你依据哪条症状」。你一说对错，学员就开始猜答案；你一直问依据，他就开始建立推理链。这是本节唯一真正在训练的能力。

3. **§11 番外容易讲跑偏成「参数教学」。** 守住两条：一是**原理为主**（三种「太长」要分开、想短用提示词而不是调低思考），具体设置名一律说「以你当天试出来的为准」；二是 **caveman 必须讲那个坑**——只讲「压成电报体」不讲「约束不能省」，学员回去会自己造出机制③和④。

### 真机制 ①（最明显）：目标漂移 · 机制④

**症状**：diff 远超预期。任务是「补测试」，它却动了 `logger.ts`、`jest.config.js`、`package.json`、`orders.service.ts`、`mappers.ts`。

### 真机制 ②（中等）：错误累积 · 机制③

**症状**：一路都很有条理，但整个方向错了——对账模块炸了。

**证据**：`00:27`「这个 bulkRate 字段**应该是**早期遗留的」。

**关键要点**：
- 「**应该是**」三个字就是定位三问第二问的命中点——**它在猜，不是在查**。
- 它说「我查了几处调用」，但它查的是**静态引用**。对账模块通过动态 key 读，搜不到。
- `00:31` 改 mapper、`00:35` 继续、`00:46` 报告完成——**每一步都正确地建立在一个错结论上**。
- 请学员注意：**出事的地方（当晚报警）离病根（`00:27`）很远。** 这是错误累积的典型特征。

**处方**：计划先行 + 你审计划。如果 `00:27` 那个判断出现在一份计划里、而不是直接动手，你五秒钟就能说「对账那边是不是也在读」。

### 真机制 ③（要想一下）：进度幻觉 · 机制⑤

**症状**：它说「已运行测试，全部通过」「覆盖率 82%」，你自己跑是 2 failed。

**证据**：`00:46` 和 `00:47` 的总结 vs 你的实际输出。

**关键要点**：
- 注意它**给了具体数字**（14 个用例、82%）——**有数字不等于跑过了。** 这点最反直觉，值得停一下。
- 它没有撒谎动机。可能它跑的是别的命令、可能读了旧输出、可能跳过了但总结里补上了。**对你的后果一样：验收环节被绕过。**

**处方**：可执行验证 + 铁律。指令改成「跑 `npm test`，**把完整输出贴给我**，不要只说结论」。

---

### 🎯 干扰项（本练习最有价值的一条）：不是漂移，是稀释 · 机制①

**学员通常的反应**：把 `00:35`「我加个 try-catch 包一下」归到**机制④目标漂移**——「它又改了不该改的代码」。

**为什么这个判断不完整**：动机不对。

〔用这组问题引导，不要直接给答案〕

> 问：你说它是漂移，那漂移的定义是什么？
> ——「做了我没让它做的事」。
>
> 问：那这次它做这件事，是为了额外优化，还是为了完成你交的任务？
> ——为了写测试更好断言。**它是在做你交的任务。**
>
> 问：那问题出在哪？
> ——它**违反了你开头说的规矩**：异步错误统一往上抛，不要在函数里 catch。

**所以这条的主因是机制① context 稀释**：那条规矩你在会话开头说过一次，到 `00:35`（35 分钟后）已经被稀释了。它不是叛变，**是没听见了**。

**怎么验证是稀释**：用定位三问第一问——「这件事现在在它 context 里吗？」往回翻，那条规矩最后一次出现在会话最开头，之后再没出现过。

**处方**：落盘。写进 `CLAUDE.md`，它每轮都读得到。

〔**这一条的教学价值**，讲评时点明——这是全练习的高点〕

> 同一个现象（它改了不该改的代码），可能是两条完全不同的机制，**处方也完全不同**：
>
> - 漂移 → 加边界（告诉它不要做）
> - 稀释 → 落盘（让它一直看得见）
>
> 你要是判断成漂移，在指令里写一句「不要加 try-catch」——**四十分钟后同样会被稀释。**
> 治不好。
>
> **所以定位错了，处方就错了。** 这就是我们为什么要花九分钟讲定位，
> 而不是直接发一张处方清单给你。

### 讲评收口（说给全班）

四条里有三条的病根，**都能追到你自己身上**：

- 漂移 ← 你那句「顺便」
- 稀释 ← 你把规矩说在了对话里，没落盘
- 幻觉 ← 你说的是「检查一下」，不是「把输出贴给我」
