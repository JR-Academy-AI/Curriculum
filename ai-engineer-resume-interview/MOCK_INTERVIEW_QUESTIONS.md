# AI Engineer 月度模拟面试 — 题库（8 candidate 轮答 · 现场围观版）

> 场景：每月一场，8 位学员上场当 candidate，其余学员围观。**围观者是主要受众** —— 每题除了筛人信号，额外给「围观者带走什么」。
>
> 题目锚点来自本目录讲座 deck 的真实内容：`src/components/slides/S23_InterviewPipeline.tsx`（面试 5 环节 + 各环节红旗）、`S24_TopQuestions.tsx`（15 道高频题）、`S26c_SystemDesignRAG.tsx`（内部文档问答案例）、`PRD.md`（P1–P10 技术分层）。
>
> 题库格式沿用 `jr-academy-memory/hr/roles/{role}/interview.md`：每题「考察点 / ✅好信号 / 🚩危险信号 / 追问」。
>
> ⚠️ 本场是**教学活动**，不是招聘。不打淘汰分，不留学员真实姓名评语在本文件里。

---

## 怎么用这 10 题

三档难度，按 candidate 水平派题，不要按顺序硬发：

| 档 | 题号 | 单人时长 | 派给谁 |
|----|------|---------|--------|
| A · 暖场 + 简历深挖 | Q1–Q3 | 5 分钟 | 前 3 位 / 偏紧张的 / 刚学完 Phase 1-2 |
| B · 核心区分度 | Q4–Q7 | 6–8 分钟 | 中间 4 位 / 简历上真写了 LLM 项目的 |
| C · 高阶 | Q8–Q10 | 8–10 分钟 | 最后 1 位 + 全场共答 |

**8 人 × 10 题的分配建议**：Q1–Q8 各派 1 人（8 人满）；**Q9 当全场白板共答**（一人主答、围观者补刀，最有教学价值）；**Q10 当收尾群问**（每人一句话，快问快答，气氛收得住）。Q9/Q10 也可留作机动 —— 有人 3 分钟就答完了，直接加一题。

**每题节奏**：candidate 答 → 你追问 2 次（追问才是照妖镜，第一答几乎人人能背）→ 你当场点评 1 分钟给围观者。

## A 组 · 暖场 + 简历深挖

**Q1.** 介绍你简历上那个 LLM 项目。然后回答我一个问题：**如果把里面的模型换成便宜 10 倍的小模型，你的系统哪一环会先崩？**

- **考察点**：是不是真做过。真做过的人知道自己系统的瓶颈在哪；背项目的人只会复述架构图。
- ✅ 能定位到**具体环节**并说出机理 —— 比如「structured output 会先崩，小模型指令遵循差，JSON schema 解析失败率上去，retry 一多反而更贵」，或「长上下文 recall 掉，多跳推理答不对」。
- 🚩 只会说「效果会变差」但说不出哪里差；把架构图从头背一遍不回答问题；从没想过这个问题。
- **追问**：① 你怎么**验证**是它先崩的，而不是你猜的？ ② 那你当初为什么选现在这个模型，做过对比吗？
- **围观者带走**：面试官问你项目，真正在问的是「你有没有对自己的系统建立因果模型」。架构图谁都会画，瓶颈只有真跑过的人知道。

---

**Q2.** 客户说：我们内部有 5 万篇文档，想让 AI 能回答员工的问题。你选 RAG 还是 fine-tune？

追加：老板补一句「我要模型**真的学会**我们公司的说话语气」，你的方案变吗？

- **考察点**：deck 里明写了，二面最常见的红旗就是「**RAG 跟 fine-tune 分不清**」。这题专门抓这个。
- ✅ 把两件事拆开 —— **RAG 管知识**（可更新、可引用溯源、能做权限隔离）、**fine-tune 管风格 / 格式 / 指令遵循**；两者不互斥，语气那个需求恰好是 fine-tune（或干脆 few-shot + system prompt 就够）。会反问「文档多久更新一次」。
- 🚩 「fine-tune 更准所以选 fine-tune」；认为 fine-tune 能解决**知识更新**（文档改了要重训？）；听到「学会语气」就推翻整个方案。
- **追问**：① 文档每天新增 1000 篇，fine-tune 方案怎么办？ ② 如果只准选一个，先做哪个？
- **围观者带走**：RAG 和 fine-tune 不是二选一的竞品，是解决**不同问题**的两个东西。一个给知识，一个给行为。分不清这个，二面基本就挂了。

**Q3.**【情景】你的 RAG 上线了。用户搜 `ERR_2043 怎么修`，返回的全是无关的通用报错文档。**给我三个可能原因，并且按你会先查哪个排序。**

- **考察点**：debug 的**手感**。不是问知识点，是问「出了问题你第一步干嘛」。
- ✅ 说得出机理并排了序，例如：① 纯 dense 检索 —— error code 是罕见 token，embedding 抓不住它，需要 BM25 / hybrid search 兜；② chunk 切坏了 —— 错误码和解决方案被切进不同 chunk；③ 没有 rerank —— 正确文档在 top-50 里但排不进 top-5。**关键加分**：说「我先去看检索日志，看 top-50 里到底有没有那篇文档」—— 先定位是**召回**问题还是**排序**问题，再动手。
- 🚩 不看数据直接开药方（「换个更强的 embedding 模型」）；三个原因都是猜的、说不出为什么是这个顺序；不知道 error code 这类罕见 token 是稀疏检索的主场。
- **追问**：① 如果 top-50 里根本没有那篇文档，说明是什么问题？（召回，不是排序 —— 别去调 reranker）② 中英混合的 query 怎么办？
- **围观者带走**：`hybrid search = dense + sparse` 不是为了炫技。**dense 抓语义，BM25 抓专有名词、产品型号、错误码**。你的用户搜的恰恰全是这些。

## B 组 · 核心区分度（这四题最能分出「上过 prod」和「跑过 demo」）

**Q4.** 你怎么知道你的 RAG 是好的？

追加：假设我告诉你，你的 faithfulness 从 92% 掉到了 78%。**你第一步做什么？**

- **考察点**：有没有 eval 意识。这是**整场区分度最高的一题** —— 做过玩具项目的人到这里必卡。
- ✅ 有 golden set（讲座 deck 的锚点是 100 条 query）；知道 RAGAS 三件套 **Context Recall / Faithfulness / Answer Relevance** 各自测什么；掉分后**先分层定位** —— 去看 context recall 有没有跟着掉：跟着掉 = 检索侧出问题（索引、chunk、同步），没跟着掉 = 生成侧幻觉（prompt 改了？换模型了？）。会问「最近改了什么」。
- 🚩 「我们人工抽查了几条」；没有 baseline 就说效果好；分不清**检索失败**和**生成幻觉**，上来就调 prompt。
- **追问**：① 你的 golden set 从哪来的，谁标的？ ② 每次改完 prompt 都跑一遍 eval 吗，还是凭感觉上？
- **围观者带走**：**没有 eval 的 LLM 应用 = 没有测试的代码**。区别是它还会骗你说自己是对的。你简历上写「优化了 RAG 效果」，面试官下一句一定是「怎么衡量的」。

**Q5.**【情景】你的 AI 客服跟一个用户说「可以全额退款」。但公司政策是**只有 7 天内**才能退。用户截图发到了社交媒体上。

现在复盘：**你怎么保证这事不再发生？**

- **考察点**：幻觉治理是不是分层的系统工程，还是一句 prompt。有商业后果的题，也逼学员意识到「AI 说错话是要赔钱的」。
- ✅ 分层给方案：**① grounding** —— 答案必须来自检索到的政策文档，不许自由发挥；**② structured output** —— 强制输出带 citation，答不出引用就不许答；**③ eval gate** —— 上线前用 golden set 拦住这类 case；**④ 兜底** —— 涉及退款/金额这类高风险意图直接路由给人工。**关键加分**：先问「**是模型编的，还是它检索到了一篇过时的旧政策文档**」—— 这两个的修法完全不同。
- 🚩 「我在 prompt 里加一句『不要瞎说』」然后就没了；只靠 prompt 不上系统性护栏；没意识到检索到脏数据也会导致「看起来像幻觉」。
- **追问**：① 如果是检索到了 2019 年的旧政策文档，你的 grounding 还救得了你吗？（救不了 —— 这是数据治理问题）② 哪些意图你会直接不让 AI 答？
- **围观者带走**：幻觉不是一个 prompt 能解决的 bug，是**四层防线**：grounding → 结构化约束 → eval 闸门 → 人工兜底。而且「AI 胡说」和「AI 忠实地复述了一份过期文档」，长得一模一样，修法完全相反。

**Q6.**【情景】你的 agent 卡进了一个工具调用循环，一晚上烧了 200 刀 token。**现场说：你怎么定位，怎么防止再发生？**

- **考察点**：agent 的**可观测性**。会不会用 trace，还是只会 print。
- ✅ 定位：拉 trace（LangSmith 之类）看**完整的 tool call 序列** —— 它到底在反复调哪个工具、参数是不是每次都一样。防止：`max_iterations` 上限 + **token / 成本预算**熔断 + reflection step。**关键加分**：意识到**根因常常是工具描述写烂了** —— 模型看不懂这个 tool 该怎么用、返回值代表什么，于是反复试。改 tool description 比加限制更治本。
- 🚩 「加个 try catch」；「加个 max retry」就完事，不去看它为什么循环；不知道 agent 要 trace，还在 print 大法。
- **追问**：① single agent + tools 和 multi-agent，你怎么选？（**任务能线性拆解 → single + tools**；**有并行 / 需要角色协作 → multi-agent**。别一上来就 multi-agent，那是 debug 地狱）② 你怎么给 agent 设成本上限？
- **围观者带走**：agent 出问题，99% 的时间花在**看它到底调了什么**。没有 trace 的 agent 就是黑盒。另外：多 agent 不是更高级，是更难 debug —— 面试时别为了显得厉害就说 multi-agent。

**Q7.** 为什么要用 function calling，而不是让模型输出一段 JSON 字符串、你自己 parse？

追加：那 **MCP** 又解决了 function calling 没解决的什么问题？

- **考察点**：分不分得清**协议层**和 **API 层**。deck 里 MCP 是明确的高频题（"What's MCP and why does it matter?"）。
- ✅ function calling：schema 约束住输出，少 retry、省 token、类型安全，不用写正则救场。MCP：**它是协议，不是 API** —— 把 tool 从「绑死在某个应用里」解耦成「任何 client 都能连的 server」，写一次 tool 到处复用；Anthropic 提出、现在事实标准。
- 🚩 「MCP 就是 function calling 的新叫法」；说不出协议和 API 的区别；只会说「MCP 很火」但讲不出解决了什么痛点。
- **追问**：① 你自己写过 MCP server 吗，暴露了什么 tool？ ② 什么场景下你**不**需要 MCP，function calling 就够？
- **围观者带走**：面试里被问新技术，答「它很火」= 没答。永远回答「**它解决了什么，之前的方案痛在哪**」。MCP 的答案是：tool 的复用性。

## C 组 · 高阶

**Q8.**【情景】你的应用每天 100 万次 LLM 调用。CFO 找你：**token 账单砍一半，质量不许降。** 给我方案，按 ROI 排序。

- **考察点**：production 成本意识。deck 里明写「**不知道 prompt caching**」是 System Design 环节的红旗。
- ✅ **第一反应是先问「我的 token 到底花在哪」** —— 不看 breakdown 就开方案的都是背题。然后按 ROI 排：**① prompt caching**（system prompt / 长文档前缀重复率高时，缓存命中部分接近 90% 折扣，改动最小、收益最大）→ **② model routing**（简单意图走小模型，复杂的才上大模型）→ **③ semantic cache**（高频重复 query 直接命中）→ **④ Batch API**（能异步的任务约 50% 折扣）→ **⑤ prompt 精简**（收益最小，别一上来就抠 prompt）。
- 🚩 张口就「换个便宜模型」（质量不许降，你违约了）；没听过 prompt caching；不问 cost breakdown 直接甩五条通用建议。
- **追问**：① 你怎么知道 prompt caching 对你有效？（看前缀重复率 / cache hit rate）② 砍完之后你怎么证明质量没降？（→ 又回到 Q4 的 eval，可以现场把两题串起来讲）
- **围观者带走**：省钱的顺序是**先改架构、再换模型、最后抠 prompt**。而且任何「优化」都得有 eval 兜着，否则你只是在偷偷降质量。

**Q9.**【全场白板共答】设计一个公司内部文档问答系统：**5 万篇 Notion 文档，1 万名员工。**

给你 5 分钟画架构。然后我只深挖一件事：**权限怎么做？**

- **考察点**：System Design 的完整度，以及一个**几乎人人踩的陷阱**。
- ✅ 架构说得出增量同步（webhook 监听文档变更，不是每天全量重跑）、hybrid search + rerank、强制 citation 可跳原文。**权限是杀手锏**：ACL 必须**嵌进 metadata，检索时按 user_id 做 filter**。
- 🚩 **典型死法：检索完再过滤。** top-5 拿出来，一过滤权限，剩 0 条，用户看到「没找到」—— 但文档明明存在。正确做法是 filter 要发生在检索**内部**。
- 🚩 其他：不提权限直接开讲 embedding 模型选型；没有增量同步（文档改了一天后才生效，用户就不信这个系统了）。
- **追问**：① 员工离职了，他的文档权限怎么撤？索引里那些 embedding 怎么办？ ② 中英混合文档，你的 chunk 策略变吗？
- **围观者带走**：企业级 RAG，**权限不是加分项，是生死线** —— 让实习生搜到了老板的薪资表，这个项目当天下线。而且记住那个陷阱：**先过滤，再检索**。检索后过滤 = top-k 被过滤空。
- **建议玩法**：这题让一个人主答，答完开放围观者补刀「你漏了什么」。补出 ACL 陷阱的那个人，今晚的 MVP。

**Q10.**【收尾群问 · 每人一句话】你日常怎么用 AI 写代码？**说到具体工具名，再说一个你让它做砸了的例子。**

- **考察点**：deck 里明写，简历上出现「**AI coding assistance**」这种泛描述是筛简历环节的直接红旗。这题当场验证他是真用还是在包装。
- ✅ 说得出具体工具（Cursor / Claude Code / Aider / Cline / Windsurf / Continue 等）+ 具体 workflow（先让它读 codebase 出 plan、小步 diff、自己 review 每一行）+ **诚实说出一次翻车**并讲怎么补救的。
- 🚩 「我用 AI 提升了效率」—— 说不出工具名；「AI 写的我都直接 merge」（没人敢要你）；反过来「我从不用 AI」（这是 AI Engineer 岗位，你在说什么）；编一个听起来很完美的失败案例。
- **围观者带走**：面试官不怕你用 AI，怕的是**你不知道它什么时候会骗你**。「我让它重构，它把测试一起改成 pass 了」这种回答，比任何「我精通 AI 工具」都值钱。

**Q11.【加题】** 假设你是 5 人小团队的 tech lead，全组都在用 AI coding 工具写代码。三个月后你怎么知道**代码库质量没有悄悄变差**？给我具体机制，不是"我会 review"这种空话。

- **考察点**：个人会用 AI coding 工具（Q10 考的）和**团队层面能管住质量**是两个完全不同的能力层级，这题专门考后者——有没有真的带过团队、想过治理问题。
- ✅ 分层给机制：**① 有统一约定文档**（团队共享的 CLAUDE.md/AGENTS.md 之类，写死命名规范/禁用库/架构红线，不让每个人的 AI 各按各的"最佳实践"发挥）→ **② AI 生成的 diff 走一样的 PR review，不因为测试绿了就免检**（重点抓：测试断言被偷偷改、多余的"顺手优化"、看似冗余实则有意义的代码被删）→ **③ diff 大小设上限**（超过阈值强制拆分，40 个文件的 diff 没人真审得动）→ **④ 追踪 AI 辅助改动的回滚率/热修率**，把"质量感觉还行"变成一个能看趋势的数字 → **⑤ 定期抽查已合并的 AI 改动**（不只是合并那一刻审，隔一个月回头再抽查，抓审查疲劳漏掉的东西）。
- 🚩 只会说"我会认真 review"、"设个 code owner"这种正确但空洞的话，没有具体机制；没意识到测试绿≠正确；把 AI 生成的代码当"不需要跟人写的代码一样严格 review"。
- **追问**：① 如果一个工程师说"这段 AI 写的我没完全看懂，但测试过了"，你怎么处理？（**这才是关键**——正确答案是鼓励他说出来、一起过一遍，而不是默认"测试过了就行"，团队文化上要允许说"没看懂"）② 权限/鉴权/计费这类高风险代码，AI 辅助的规则要不要不一样？
- **围观者带走**：个人会用 AI coding 工具只是及格线，**带团队的人要考虑的是治理**——统一约定、审查不降级、diff 限流、数据化跟踪、定期回头查。而且最容易被团队文化忽略的一点是：**要让"我没完全看懂这段 AI 写的代码"变成一句能安全说出口的话**，而不是大家都不好意思承认自己在盖橡皮图章。

## 现场评分（4 维度 · 围观者也能当评委）

不打淘汰分，让围观的人拿着这张表跟着评，参与感和学习效果都会好很多：

| 维度 | 看什么 | 1 分 | 5 分 |
|------|--------|------|------|
| **结构性** | 答之前有没有先拆问题 | 想到哪说到哪 | 先澄清需求，再分层作答 |
| **技术深度** | 追问 2 次之后还站得住吗 | 第一问就见底 | 越挖越有东西，能讲机理 |
| **数据支撑** | 有没有具体数字 / 指标 | 全是「更好」「更快」 | recall@5、p95、cost/query 张口就来 |
| **诚实度** | 不会的时候怎么办 | 硬编一个听起来对的答案 | 「这块我没做过，但我会这样查」 |

> **诚实度这一栏，你现场要重点讲。** 面试里编造一个技术细节，被追问两层必然穿帮，而且是一票否决 —— 比直接说「不知道」严重得多。这也正好是公司自己的红线。
